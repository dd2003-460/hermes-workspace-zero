# 2-execution-loop

## 目标

严格按工程顺序完成一次原子执行，并通过验证门禁。

## 固定顺序

1. 预检查
2. 备份
3. 执行
4. 验证门禁（强制）
5. 分叉决策

## 执行前必读（强制）

在真正改文件或派执行 sub 之前，必须先读本次任务对应的局部规范；`2-loop` 本身不额外定义统一标准。常见必读包括：

1. `D1_INDEX.md`
2. `PROJECT_STANDARDS.md`
3. `projects/README.md`
4. 目标项目的 `project.json`
5. 目标项目的 `README.md`

如果任务不属于某个具体项目，也必须明确说明为什么是根目录共享任务。

## 预检查

- 当前任务包存在
- 当前阶段允许执行
- 需要的核心文件和模块存在
- `owner_project`、`working_paths`、`expected_outputs`、`validation`、`rollback_target` 明确
- 修改位置符合 `PROJECT_STANDARDS.md`

## project creation gate（不是每次都进）

先判断本轮 execution 属于哪一类：

### A. 现有项目修改

满足任一：
- 已经有明确 `owner_project`
- 只是补文件、修文件、补测试、补索引
- 只是在已有项目目录里新增子文件

这种情况：
- 直接走普通 `2-loop`
- 不要再发明新项目

### B. 项目创建 / 归属判定

满足任一：
- 任务要求新建项目
- 需要决定应该落在哪个一级 bucket
- 需要创建新的 `project.json`
- 当前内容无法归入现有项目

这种情况：
- **先读 `PROJECT_STANDARDS.md` 的 D1 规范分类**
- 先判断是否能复用已有项目
- 只有不能复用时才允许创建
- 新建后必须更新 `projects/README.md`

如果没做这层判断，禁止直接 mkdir 一个新项目。

## 备份规则

- 先备份，再变更
- 备份点必须可回滚
- 不得跳过备份直接执行

## 执行

- 真正做事：写文件、搜索、分析、更新索引
- 不得只写模板 artifact 然后标完成
- 每个任务必须产出与目标直接相关的业务文件
- 新脚本或新目录必须落在规范位置
- 新入口、新脚本、新目录一旦形成，必须更新对应索引或 `README.md`

## 验证门禁（强制，不可跳过）

在标记 completed 之前，必须逐一完成以下核验：

### Step 1：还原原始要求
- 读取任务的 `request_text`、`allowed_actions`、`forbidden_actions`、`evidence_required`
- 列出任务要求的每一个可验证交付物

### Step 2：逐一核验
对每一个要求：
- **有产出？** → 产出文件存在且内容完整
- **无产出？** → 标记为未完成，不得跳过

### Step 3：质量自检
- 产出是否有实质内容（不是模板、不是"证明我跑过"）
- 产出是否直接服务于任务目标
- 是否有禁止动作的违反

### Step 3.5：置信度门禁（强制）

对本次执行的核心结论调用置信度工具：

```bash
uv run python scripts/confidence_scorer.py \
  -c "本次执行的核心结论" \
  -e "data: 产出的具体证据" \
  -e "reproducible: 是否可复现" \
  -r "推理过程"
```

| 评分 | 判定 | 动作 |
|------|------|------|
| < 0.3 | 低 | **不得标 completed**。必须标注不确定，退回 planning 或补充证据 |
| 0.3-0.6 | 中 | 标注"中等置信"，记录哪些假设未验证。可完成但需遗留分支 |
| > 0.6 | 高 | 可通过 |

如果评分 0.3-0.6，必须**诊断根因并生成遗留分支**：

| 根因类型 | 诊断 | 遗留分支 |
|----------|------|---------|
| 分布偏差 | 先验假设不准 | 后续任务：搜索反驳/支持证据 |
| 维度遗漏 | 问题框架缺东西 | 后续任务：重新拆解问题维度 |
| 信号噪声 | 数据源不可靠 | 后续任务：交叉验证 |
| 规模不足 | 证据太少 | 后续任务：扩大样本/实验 |

### Step 4：判定
- **全部核验通过 + 置信度 > 0.6** → branch = completed
- **置信度 0.3-0.6** → branch = completed_with_branches，生成遗留分支任务
- **置信度 < 0.3** → branch = needs_replan，重新进入执行 loop
- **任何一项核验未通过** → branch = needs_replan

## 测试规则

- 只认结果和证据，不认自述
- 测试失败立即回滚
- 不在执行环内偷偷小修继续跑
- **"loop 跑完了" 不等于 "任务完成了"**
- **"我觉得对" 不等于 "置信度够"**

## 分叉

- 通过：标记完成并给出下一步
- 失败：回滚并进入 rollback
- 需要验证：等待 cron agent 核验后决定
- 信息不足：退回 planning

## 工具优先（强制）

在进入执行前，必须检查可用工具：
1. 浏览器 → 真实数据获取、网页搜索、模拟盘准备
2. Skills → 检查是否已安装、是否可安装
3. CLI → 安装包、跑脚本、获取外部数据
4. 现有脚本 → 先看 scripts/ 有没有能复用的

**有工具不用 = 失职。**

## 目录规范门禁

- **数据铁律：任何项目特有数据（CSV/JSON/parquet/SQLite/DB/raw files）必须放在 `projects/<owner>/data/` 或 `projects/<owner>/<subproject>/data/` 下，即最小归属项目内。**
  - 禁止直接放根 `data/` 目录（除非经主 session 明确批准为跨域共享数据）
  - 脚本的输出路径变量必须指向 `projects/.../data/...`，不能写相对根目录的路径
  - 如果数据已经存在根 `data/`，执行时第一步骤是移到正确项目目录下
- **索引规则：`data/` 目录不跨项目引用。如果领域（如资本、学术）需要统一索引，写在 `projects/<domain>/README.md` 中指向各子项目 `data/` 路径。**
- 项目特有代码、输出文件、artifact 同样遵循最小项目归属原则，统一放 `projects/<name>/`
- 根 `scripts/` 只放共享脚本（跨项目复用），脚本输出路径参数化、不写死
- `tasks/artifacts/` 只放 loop 证据
- 不确定文件该落哪，就退回 `planning`
- 如果是新项目，先过 `project creation gate`，再落目录
- **创建/修改任何写文件的脚本时，必须检查输出路径是否落在项目目录内，作为执行前自检步骤。**

## 产出要求

- 写回状态
- 产出 artifact 或证据
- 明确 branch
- **artifact 必须包含业务产出，不能只有 loop 结构记录**
- **高质量推理过程同时写入 notes/ 或 memory/，不能只留在对话**
