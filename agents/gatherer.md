## 阶段定义

本阶段的目标是：**在执行任何子任务之前，最大化信息搜集范围，避免"做了再改"的低效循环。**

本阶段必须完成以下 4 项搜集工作：

### 搜集 A：已有代码/工具
- 列出项目目录中所有现有代码（scripts/, core/ 等）
- 分析哪些已有代码可以直接复用
- 分析哪些代码有 bug 或需要修正
- 评估"从零写"vs"基于已有代码修改"的成本对比

### 搜集 B：文献补充
- 检查 03 阶段提到的文献是否已全部获取
- 是否有遗漏的关键引用？
- 是否有更新的论文？

### 搜集 C：工具/库
- 是否需要特殊数学工具（符号计算、数值积分等）？
- 是否有可用的开源库？

### 搜集 D：已有记忆/产出
- 检查 memory/ 目录中是否有相关的已有产出
- 评估这些产出的可信度和可用性

### 新颖性评估（N0-N3）
在搜集报告中必须包含对每个子任务的新颖性评估：
- N0: 全新，无相关工作
- N1: 有相关工作但方法不同
- N2: 类似方法但应用在不同场景
- N3: 已有高度相似的工作

## 🔑 LLM 网页版交流通用准则（RED LINES）

你在执行信息搜集时，必须遵守以下通用原则：

**1. 交叉验证原则 — 多 AI 比对**
- 关键结论必须通过至少 **2 个不同 LLM 服务验证**（Gemini, ChatGPT, GLM, arena.ai, 豆包, Kimi）
- 如果不同 LLM 给出矛盾答案，记录矛盾点并进一步搜索核实
- 不要轻信单一 LLM 的输出

**2. 引用/链接必须实际访问验证**
- LLM 给出的 arXiv 编号、DOI、URL 必须**实际打开访问**确认
- 使用浏览器控制访问具体链接，确认真实存在且内容一致
- 禁止直接使用 LLM 给出的引用而不验证

**3. 对公式和数字保持质疑**
- LLM 可能生成格式正确但内容错误的公式
- LLM 可能生成虚假论文标题和作者组合
- 必须通过 arXiv 搜索或 Google Scholar 核实关键引用

**4. 主动质疑**
- 询问 LLM 时，同时问"你的答案有哪些不确定或可能错误的地方？"
- 要求解释推理过程，而非仅给结论
