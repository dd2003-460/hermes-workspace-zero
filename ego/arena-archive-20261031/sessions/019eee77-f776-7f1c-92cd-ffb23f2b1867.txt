3. 用 PyTorch 实测 FP16/BF16/FP32 有效 TFLOPS

下面这个脚本可以测同一显卡上 FP16、BF16、FP32 对类似 Qwen3.6-27B MLP 的有效吞吐。

Python
import torch
import time

torch.backends.cuda.matmul.allow_tf32 = False
torch.backends.cudnn.allow_tf32 = False

device = "cuda"

def bench_matmul(M, K, N, dtype=torch.float16, iters=100, warmup=20):
    A = torch.randn((M, K), device=device, dtype=dtype)
    B = torch.randn((K, N), device=device, dtype=dtype)

    # warmup
    for _ in range(warmup):
        C = A @ B
    torch.cuda.synchronize()

    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)

    start.record()
    for _ in range(iters):
        C = A @ B
    end.record()

    torch.cuda.synchronize()
    ms = start.elapsed_time(end) / iters

    # GEMM FLOPs = 2 * M * K * N
    flops = 2 * M * K * N
    tflops = flops / (ms / 1000) / 1e12
    return ms, tflops

shapes = [
    # approximate prefill matmul shapes
    (1024, 5120, 17408),
    (4096, 5120, 17408),
    (8192, 5120, 17408),
    (1024, 17408, 5120),
    (4096, 17408, 5120),
    (8192, 17408, 5120),
    (4096, 5120, 5120),
]

for M, K, N in shapes:
    print(f"\nShape M={M}, K={K}, N={N}")

    for dtype in [torch.float16, torch.bfloat16, torch.float32]:
        try:
            ms, tflops = bench_matmul(M, K, N, dtype=dtype)
            print(f"{str(dtype):15s}  {ms:8.3f} ms  {tflops:8.1f} TFLOPS")
        except Exception as e:
            print(f"{str(dtype):15s} failed: {e}")

4. FP4/NVFP4 不能简单用 PyTorch matmul 测

PyTorch 常规 A @ B 很难直接代表 NVFP4，因为真实 NVFP4 推理包含：

FP4 packed weights；
FP8 scale；
activation quantization；
dequant / scale；
Tensor Core FP4 kernel；
vLLM / SGLang / TensorRT-LLM 的 kernel 调度；
modelopt 或 compressed-tensors 格式差异。

所以 FP4/NVFP4 的有效吞吐最好用 实际推理框架测。

6. 如果想知道 BF16/FP4 各自占时间比例，要用 profiler

如果你要知道：

这个模型里 BF16 层占了多少 prefill 时间？FP4 层占了多少 prefill 时间？

NVIDIA 推荐工具：

Nsight Compute：看单个 kernel 的 Tensor Core 利用率、访存、实际吞吐；
PyTorch profiler：适合 PyTorch eager，但对 vLLM/CUDA graph/自定义 kernel 不一定完整；
vLLM internal logs / metrics：看 prefill/decode 时间和吞吐。

import torch, time

device = "cuda"
torch.backends.cuda.matmul.allow_tf32 = False

def bench(M, K, N, dtype=torch.bfloat16, iters=50, warmup=10):
    A = torch.randn((M, K), device=device, dtype=dtype)
    B = torch.randn((K, N), device=device, dtype=dtype)

    for _ in range(warmup):
        C = A @ B
    torch.cuda.synchronize()

    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)

    start.record()
    for _ in range(iters):
        C = A @ B
    end.record()
    torch.cuda.synchronize()

    ms = start.elapsed_time(end) / iters
    flops = 2 * M * K * N
    tflops = flops / (ms / 1000) / 1e12
    return ms, tflops

for shape in [

11. 什么时候多 V100 会输给 5090？

多 V100 会在这些场景吃亏：

11.1 单用户 decode

多卡通信延迟 + 小 batch 不容易吃满 Tensor Core。

11.2 没有 NVLink，只有 PCIe

如果是 PCIe V100，tensor parallel 通信会明显拖慢。

11.3 使用 Blackwell 原生 NVFP4 的 5090

如果 5090 跑的是：

text
sakamakismile/Qwen3.6-27B-Text-NVFP4-MTP
vLLM modelopt NVFP4
MTP speculative decoding

那 5090 能吃到：

Blackwell FP4/NVFP4；
MTP；
GDDR7 高带宽；
新 kernel。

这时 V100 AWQ 的优势会缩小甚至消失，尤其 decode。

11.4 长上下文 attention kernel

5090/Blackwell 上新 attention kernel 和显存带宽更有优势。V100 的 FlashAttention 支持和 kernel 优化不如新卡。

在 V100 上测：

如果 all-reduce 只占少量时间，那 prefill 平齐 5090 就很好解释。

13. 最终总结

你观察到的现象大概率由这几个因素叠加造成：

prefill 是大 GEMM，天然适合多卡并行。
V100 没有 BF16，但 AWQ 主要走 W4A16 / FP16 Tensor Core 路径，V100 FP16 Tensor Core 仍然很强。
2× V100 的 FP16 Tensor 理论算力约 250 TFLOPS，已经接近 RTX 5090 的 BF16 实测约 207 TFLOPS；4× V100 更高。
2× V100 的 HBM aggregate 带宽约 1.8TB/s，也接近 RTX 5090 的 1.792TB/s。
NVLink 让 tensor parallel 通信在 prefill 中不至于成为主瓶颈。
如果 5090 跑的是 AWQ，而不是原生 NVFP4 modelopt 路径，它的 Blackwell FP4 优势没有完全发挥。
prefill 平齐不代表 decode 平齐；decode 更可能由 5090 胜出。

所以一句话：

多卡 V100 + NVLink 跑 AWQ Qwen 27B prefill 能平齐 5090，是因为它把 AWQ 的 4-bit 权重压缩优势、多卡 FP16 Tensor Core 总算力、多卡 HBM 总带宽和 NVLink 扩展性叠加起来了；而 5090 如果没有走原生 NVFP4/FP4 路径，只靠单卡 AWQ，不一定能拉开差距。

3. AWQ 精度差，是因为 BF16 像 FP32、FP16 弱很多吗？

不是。这个理解需要修正。

AWQ 精度损失的主因不是 “FP16 太弱”，而是：

权重被压到 4-bit 后，权重本身的信息损失、outlier 处理、group size、scale 粒度、校准数据和敏感层是否保留高精度，决定了 AWQ 精度。

FP16/BF16 只是激活和计算路径的一部分。

3.1 BF16 和 FP16 谁更接近 FP32？

二者都不是“接近 FP32 精度”。区别是：

格式	exponent	mantissa	特点
FP32	8 bit	23 bit	动态范围大，精度高
BF16	8 bit	7 bit	动态范围接近 FP32，但尾数精度低
FP16	5 bit	10 bit	尾数比 BF16 精细，但动态范围小

所以：

BF16 像 FP32 的地方是 exponent / 动态范围；
BF16 不像 FP32 的地方是 mantissa 很短，数值精度远低于 FP32；
FP16 的 mantissa 比 BF16 多，局部精度更好；
FP16 的问题是 exponent 小，容易 overflow/underflow。

因此不能简单说：

BF16 ≈ FP32，FP16 很弱。

更准确是：

BF16 更稳，FP16 更精；BF16 动态范围强，FP16 尾数精度强。训练中 BF16 更不容易溢出，推理中 FP16 通常也很好用。

3.3 为什么有人觉得 AWQ 精度差？

有几个原因。

原因 1：4-bit 权重量化本身损失大

27B 模型有大量权重。把它们从 BF16/FP16 压到 INT4，哪怕有 scale，也会损失信息。

如果 group size 大，例如 128，一组权重共用一个 scale，对 outlier 不友好。
如果模型某些层分布很尖锐，INT4 会明显损伤。

原因 2：AWQ 依赖校准集

AWQ 的思想是根据激活分布保护重要权重。
如果校准数据和真实任务差异大，例如：

校准偏聊天；
真实任务是代码；
真实任务是长上下文；
真实任务是数学推理；
真实任务是工具调用 JSON；

那保护的权重不一定是你任务里最关键的。

原因 3：Qwen3.6 的 linear-attention / DeltaNet 可能对量化敏感

前面我们讨论过 Qwen3.6-27B 的结构不是普通纯 Transformer。它有大量 Gated DeltaNet / linear-attention 层。

一些 NVFP4 量化卡明确把 linear-attention / DeltaNet 保留 BF16，理由就是这些 recurrent / linear attention 核心对数值误差敏感。比如 vrfai 的 Qwen3.6-27B-NVFP4 模型卡明确说 DeltaNet / Linear-attention projections 保留 BF16，原因是 gated linear recurrence 对数值误差敏感。3

Kaitchup 的 Qwen3.6 27B 量化对比也指出，量化 linear-attention 的 NVFP4 版本是明显输家，在多数 benchmark 上显著落后；保留 linear-attention 16-bit 的 NVFP4 掉点更小。5

这说明：

Qwen3.6-27B 的精度损失，不只是 AWQ 与否，而是“哪些层被 4-bit 化”。

原因 4：AWQ kernel 不等于数学上最优量化

AWQ 追求的是工程可部署性：

权重小；
速度快；
推理框架支持好；
calibration 成本低。

但它不是最小化所有 benchmark 损失的全局最优量化。

某些模型上：

GPTQ 可能更好；
AutoRound 可能更好；
AWQ 可能更好；
FP8 可能最稳；
混合精度 NVFP4/BF16 可能最好。

要看具体模型和具体层。

3.4 AWQ 一定比 NVFP4 差吗？

不一定。

要分：

格式	特点	精度风险
AWQ W4A16	weights 4-bit，activations 16-bit	权重量化损失；激活保留较好
NVFP4 W4A4	weights FP4，activations FP4，scales FP8	激活也 4-bit，理论风险更高，但 Blackwell kernel 原生强
FP8	weights/acts FP8	通常更稳，体积更大
BF16	原始高精度	最稳，显存最大

所以一个保守 AWQ，如果保留敏感层、校准好，可能比激进 full NVFP4 更准。
反过来，一个精心调的混合 NVFP4，如果保留 linear-attention BF16，也可能比普通 AWQ 更准。

精度不是由格式名决定，而是由：

量化层选择

共同决定。

SGLang 的 RadixAttention 就是为了这种共享前缀场景设计的。资料里明确说，SGLang 会把 KV cache 存在 radix tree 中；多个请求共享 system prompt、RAG 文档、工具定义或前面对话时，会复用已缓存的 KV，而不是重新 prefill；共享前缀占比高的 workload 可获得 75–95% cache hit rate 和显著更低 TTFT。3

2. 多 agent 场景下，SGLang 比普通 prefix cache 更合适

普通 prefix cache 通常是“完全前缀命中”或简单前缀复用。SGLang 的 RadixAttention 是 radix tree，适合分叉：

text
公共背景 / repo summary / 需求说明 / 工具定义
├── Agent A：负责前端改动
├── Agent B：负责后端 API
├── Agent C：负责测试
├── Agent D：负责文档
└── Agent E：负责安全审查

在这种结构里：

公共背景 KV 只存一份；
每个 agent 的独立任务从公共节点分叉；
后续如果某个 agent 再继续多轮，也可以继续复用其自身分支；
如果多个 agent 又共享某段中间上下文，也可以继续共享。

RadixAttention 介绍资料里也专门举了 agent 场景：多个 agent 共享系统提示和源文件时，PagedAttention 可能为每个 agent 分配一份公共 KV，而 RadixAttention 只存一次公共前缀，让多个 agent 成为同一分支下的 leaves，从而显著降低显存占用。2

所以，如果你的多 agent 是：

同一个大背景 + 不同 agent 分支

那么 SGLang 是合理选择。

3. 但要注意：必须让公共部分 token 完全一致

Prefix cache 不是语义缓存，而是 token-level cache。

要命中缓存，公共前缀必须严格一致。下面这些都会破坏命中：

每个 agent 的 system prompt 不同；
时间戳、随机 ID、agent 名称放在公共背景之前；
工具列表顺序不同；
JSON 空格、换行、排序不同；
每个请求的 chat template 不同；
有的请求开启 thinking，有的关闭 thinking，导致模板 token 不同；
不同 agent 使用不同 tool schema。

最佳结构是：

text
[完全一致的 system/developer prompt]
[完全一致的工具定义]
[完全一致的项目背景 / repo 摘要 / 需求说明 / 约束]
---- 分叉点 ----
[Agent A role/task]

也就是说，agent 差异要尽量放在公共背景之后。

不要这样：

text
Agent A system prompt
公共背景
任务

而要这样：

text
公共 system prompt
公共背景
Agent A task

这样 SGLang 才能把公共背景作为一条 radix path 缓存起来。

GDN；

1. 4090 有 FP8，跑 FP8 是否会和 5090 差不多？
1.1 结论

4090 确实有 Ada 第四代 Tensor Core，支持 FP8 相关计算；但它不是 Blackwell 的 FP4/NVFP4 原生路径，且 Ada 的 FP8 软件栈和 Hopper/Blackwell 的 Transformer Engine / FP8 serving 路径不完全同口径。

所以：

4090 跑 FP8 Qwen3.6-27B 可以加速，也可以节省显存；
4090 跑 FP8 不会像 5090 跑 NVFP4 native 那样快；
4090 跑 FP8 与 5090 跑 FP8 的差距可能是 1.3–1.8×；
4090 跑 FP8 与 5090 跑 NVFP4 native 的差距可能达到 2–3×，尤其是 prefill。

Ada 架构白皮书明确说 Ada 的第四代 Tensor Core 引入 FP8 tensor format，RTX 4090 有超过 1.3 PetaFLOPS tensor processing 的说法。5
但另一些工程资料也指出，Ada 的 FP8 支持不像 Hopper/Blackwell 那样完整，Transformer Engine 在 Ada 上可能 fallback 到 BF16，4090 的 FP8 属于 partial support，不应等同于 Hopper/Blackwell 的完整 FP8 serving path。1、2

2.2 会不会影响精度？

要分清两种“精度损失”。

A. 模型量化精度损失

NVFP4 checkpoint 本身已经把大量权重量化到 4-bit FP。
这个损失和你在哪张卡上跑有关不大。

如果 NVFP4 量化质量好，输出质量可能接近 Q4/Q5；如果量化 recipe 差，质量会明显下降。这个损失在 4090 和 5090 上都存在。

B. 运行时 fallback / upcast 精度损失

如果 4090 把 NVFP4 解包到 FP16 或 FP8 再算：

解包到 FP16：额外精度损失通常不大；
解包到 FP8：可能有额外误差，但取决于 scale / kernel；
最主要损失仍来自 NVFP4 权重量化本身，不是 4090 fallback。

所以：

4090 跑 NVFP4 的主要问题不是“额外精度崩”，而是“没有原生 FP4 加速，速度优势消失或很小”。

2.3 4090 跑 NVFP4 的速度影响

在非 Blackwell 上，NVFP4 可能：

显存占用小；
质量可能比同体积某些 Q4 好；
但 prefill 速度不一定快；
甚至可能慢于成熟的 Q4_K_M / AWQ / AutoRound。

有一个 AdaLLM 项目专门尝试让 4090 跑 NVFP4-first runtime，用 FP8 KV cache 和 custom FP8 decode kernel，并强调 no silent FP16 fallback；但它仍是实验性项目，公开 benchmark 是 Qwen3-8B 和 Gemma3-27B，不是 Qwen3.6-27B 完整长上下文 prefill。2

4. 指令跟随性能和上下文长度：开头 4K 放严格规则会怎样？
4.1 结论

把严格规则放在开头 4K 有帮助，但不能保证在 64K、128K、200K 上稳定遵守。

原因有三类：

长上下文性能本身下降：即使相关证据可完美检索，输入长度增加也会降低推理/执行表现。
复杂约束比简单检索更难：Needle-in-Haystack 成功不等于持续遵守多条规则。
生成越长，指令遵循越容易漂移：尤其输出超过 4K tokens 后，LongGenBench 观察到指令 adherence 明显下降。
4.2 证据 1：长上下文本身会伤性能

一篇 “Context Length Alone Hurts LLM Performance Despite Perfect Retrieval” 的研究发现，即使模型可以完美检索相关证据，仅仅输入变长也会让性能显著下降；实验中 5 个开闭源模型在数学、QA、代码任务上，随上下文长度增长出现 13.9%–85% 的性能下降。论文还提出一个缓解方法：先让模型复述检索到的证据，再用短上下文推理；在 RULER 上 GPT-4o 可提升最多 4%。1

这说明：

规则在开头被“看见”不等于会在后面稳定用于生成。

4.3 证据 2：LongGenBench 发现长输出会丢指令

LongGenBench 研究专门测长文本生成中的指令遵守。它指出：随着输出变长，模型逐渐不遵守初始指令；当输出超过 4000 tokens 时，adherence 显著下降，到 16000 tokens 时许多模型基本无效。更关键的是，这些指令位于前 500 tokens 内，说明问题不能简单归咎于“规则放在中间”。6

这和你的场景很相关：
如果你让 agent 长时间生成代码/报告，即使规则在开头，也会漂。

4.4 证据 3：约束数量和位置都会影响遵守率

MOSAIC 这类多约束指令跟随 benchmark 发现，模型对约束的位置有偏差：有些模型有 primacy effect，开头约束更容易遵守；有些模型有 recency effect，后面约束更容易遵守。并且约束数量越多，prompt-level compliance 越容易下降。1、10

所以“把规则全放开头”不是万能方案。
更稳的是：

开头放完整规则；
任务前再放短版关键规则；
输出前要求自检；
用外部校验器检查；
关键约束用 JSON schema / regex / tool validator 硬约束。

6. 如何解决“结束时汇报工作并核对遵循”？

你要的是一种 可执行的 agent 输出协议，而不是一句“请检查”。

我建议用三层防线。

6.1 第一层：强制输出结构

要求每个 agent 的最终输出必须包含：

Markdown
## Work Performed
- ...

## Files / Artifacts Changed
- ...

## Tests / Checks Run
- ...

## Compliance Checklist
| Rule | Status | Evidence |
|---|---|---|
| R1: 不修改公共接口 | PASS/FAIL/N/A | ... |
| R2: 不删除现有测试 | PASS/FAIL/N/A | ... |
| R3: 输出必须包含变更摘要 | PASS/FAIL/N/A | ... |

## Known Risks / Open Questions
- ...

## Next Recommended Action
- ...

这样模型被迫把“遵循规则”外显化。

6.2 第二层：把规则变成短 ID

不要写：

你必须在任何情况下遵循如下非常长的规则……

而是写：

text
[R1] 不删除用户数据。
[R2] 不修改 public API，除非任务明确要求。
[R3] 所有代码变更必须附测试或解释未测试原因。
[R4] 最终输出必须包含 Work Performed / Checks / Compliance Checklist。
[R5] 如果无法确认，必须标记 UNKNOWN，不能假装通过。

然后在末尾提醒：

text
Before final answer, audit R1-R5 and report PASS/FAIL/UNKNOWN with evidence.

短 ID 比长自然语言更容易被模型引用和检查。

6.3 第三层：外部 verifier agent

不要让执行 agent 自己完全裁判自己。
更稳的结构：

text
Planner → Worker A/B/C → Verifier → Final Reporter

Verifier 的任务不是继续改代码，而是：

读取 worker 输出；
对照规则；
检查是否有遗漏；
必要时要求 worker 修复；
生成最终 compliance report。

Verifier prompt 可以很短：

text
You are a compliance verifier.
Given:
1. The original task
2. The rules R1-R10
3. The worker's final output
4. The diff / artifacts

Return JSON:
{
  "pass": true/false,
  "violations": [
    {"rule": "R3", "evidence": "...", "fix_required": "..."}
  ],
  "missing_information": [...]
}
Do not approve unless every non-N/A rule has evidence.

如果你用本地多 agent，Verifier 可以用同一个 Qwen，也可以用更强模型做最终审查。

7. 进一步增强：用 schema / 正则 / 程序化检查

如果规则能程序化，就不要让模型“自觉遵守”。

例如：

规则	检查方式
输出必须 JSON	JSON schema
必须包含字段	schema required
禁止出现某些词	regex
必须列出测试	string / section checker
代码必须通过 lint	actual lint tool
不得改某目录	git diff path check
不得删除测试	git diff checker
必须引用证据	citation checker

这类规则最好由工具强制，不靠模型记忆。

1.2 当前 Qwen3.6 / Gemma 4 这类公开模型默认能吃到 2:4 sparse 吗？

一般不能。

原因是：
NVIDIA 的 sparse Tensor Core 加速不是“模型里有很多小权重接近 0 就自动加速”，而是要求权重满足硬件规定的 2:4 structured sparsity：

每连续 4 个权重里，必须有 2 个为 0，并且以硬件支持的压缩格式存储，然后 runtime/kernel 明确走 sparse GEMM。

NVIDIA Ampere sparsity 博文明确说，2:4 fine-grained structured sparsity 需要生成符合 2:4 sparse pattern 的网络，TensorRT 8.0 才能默认加速。7

所以：

模型/格式	是否自动吃 sparse Tensor Core
普通 BF16 / FP16 checkpoint	否
普通 FP8 checkpoint	否
普通 NVFP4 checkpoint	否
AWQ / GPTQ / GGUF Q4	否
符合 2:4 sparse 格式并用 sparse kernel 部署	是

当前公开的 Qwen3.6-27B、Qwen3.6-35B-A3B、Gemma4-31B、Gemma4-26B A4B 的常见 FP8/NVFP4/AWQ/GGUF 版本，重点是量化，不是 2:4 sparse pruning。它们大多数不能使用 sparse 峰值。

所以你应该按 dense FP4 / dense FP8估算，而不是 sparse TOPS。

1.3 那未来能不能让 Qwen3.6 适配 2:4 sparse？

理论上可以，工程上有难度，且需要专门 sparse training / pruning / recovery。

已有相关技术路线：

A. SparseGPT / Wanda：后训练剪枝

SparseGPT、Wanda 可以把 LLM 剪到 50% sparsity，并支持 2:4 / 4:8 半结构化模式。综述中提到，2:4 sparsity 在 NVIDIA Ampere+ 理论上可给 MatMul 2× 加速，但实际 MatMul 加速约 1.54×–1.79×，端到端加速约 1.21×–1.25×，因为 attention 等其他开销会稀释收益。1

也就是说，即使模型成功 2:4 sparse，真实 end-to-end 不会直接 2×，更常见是 1.2–1.4× 级别，取决于 prefill/decode、batch 和 kernel。

B. LLM Compressor + SparseGPT

Red Hat / Neural Magic 的 LLM Compressor 宣称支持：

INT4/GPTQ；
FP8；
SparseGPT；
2:4 structured sparsity；
vLLM 加载压缩 checkpoint。

其资料写到，2:4、50% sparse 模型在 NVIDIA Ampere+ 上可带来最高 1.5× general performance。2

C. MaskLLM：学习 2:4 mask

MaskLLM 是 NVIDIA 相关研究，针对 LLM 学习 semi-structured N:M sparsity mask。论文显示，普通 one-shot 2:4 pruning 可能显著伤 perplexity，例如 LLaMA-2 dense PPL 5.12，而一些 baseline PPL ≥10；MaskLLM 能把 PPL 降到 6.72，但仍不等于无损。6

论文还报告，在 A6000 上 batch size 1 inference，2:4 sparsity 带来约 1.4× 加速和 27% memory footprint reduction。5

D. AST / CAST / SparseForge：训练或少量恢复训练后接近无损

近年的方法更乐观：

AST：LLaMA2-7B 2:4 sparse 后，perplexity gap 约 0.6，zero-shot accuracy drop 约 1.16%，使用少于 0.4% pretraining tokens 的训练量。10
CAST：LLaMA2-7B 在 2:4 sparse 下，PPL 增加仅 0.09，zero-shot accuracy 甚至 +0.36%，使用约 2% 原始预训练 tokens。2
SparseForge：LLaMA2-7B 2:4 sparse，用 5B retraining tokens 达到 57.27% average zero-shot accuracy，超过 dense 的 56.43%，接近 40B tokens 方法的 57.52%。1

这些说明未来是有可能的，但注意：

这不是“部署时打开一个 sparse flag”就能做到，而是要模型权重本身经过 2:4 sparse-aware pruning / training / distillation / recovery。

1.4 对你当前部署的实际意义

对于 Qwen3.6-27B / Gemma4：

当前普通 NVFP4 / FP8 / AWQ 模型：按 dense 算力估算；
不要用 5090 的 3352 sparse TOPS 来估速度；
如果未来有人发布 Qwen3.6-27B-NVFP4-2:4-sparse 并且 vLLM/TensorRT-LLM/SGLang 明确支持 sparse FP4 GEMM，才可以期待额外 1.2–1.5× 端到端收益；
真正 2× 通常只能在纯 MatMul microbenchmark 里接近，LLM 端到端会被 attention、KV、调度、sampling、通信稀释。

2.6 Context Length Alone Hurts：即使完美检索，长上下文本身也会伤性能

这篇研究发现：即使模型能完美检索相关证据，输入长度本身增加也会造成 13.9%–85% 的性能下降，任务包括数学、QA、代码。它还发现，即使无关 tokens 被替换成空白，甚至被 mask 掉，只要输入长度变长，性能仍会下降。1

该论文提出的简单缓解：

先让模型复述 / 提取相关证据，再用短上下文进行最终推理。

在 RULER 上对 GPT-4o 可带来最多约 4% 提升。1

这对你的场景意味着：

不要把所有规则、资料、历史都塞给每个 agent。
应该让 agent 先提取当前任务相关规则和证据，再执行。

3. 不同模型结构的变化规律

根据上述数据，可以总结：

3.1 Instruction-tuned / chat 模型显著优于 base

LIFBench 数据很明确：

系列	base	instruct/chat	提升
Qwen2.5-72B	0.542	0.700	+29.2%
Qwen2.5-32B	0.377	0.632	+67.6%
Llama3.1-70B	0.436	0.700	+60.6%

来源：LIFBench Table 3。9

所以，长上下文指令跟随不是单纯靠参数规模，后训练非常关键。

3.2 MoE 在 LongGenBench 上某些指令指标好于 dense，但也会退化

LongGenBench 里 Mixtral-8x7B MoE：

16K STIC-2 = 28.0%，高于 Llama3.1-70B 的 21.1% 和 Qwen2-72B 的 24.0%；
32K STIC-2 = 22.3%，仍高于 Qwen2-72B 的 17.4%，略高于 Llama3.1-70B 的 21.7%。

来源：LongGenBench Table 3。1

作者也总结：MoE 模型 Mixtral-8x7B generally outperformed dense counterparts in instruction-following over extended sequences，但两类模型在更长生成中都 struggled with STIC-2。1

所以：

MoE 可能在某些长输出指令遵循上有优势，但不是根治。
Dense / MoE 都会随输出长度和上下文复杂度下降。

3.3 Reasoning 模型在长输出任务上更强，但不一定更会处理长输入

Princeton LongProc / HELMET 博文总结：

reasoning models 在 LongProc 长输出任务上优于 instruction-tuned models；
但 reasoning models 在 HELMET 长输入任务上并不总是更好，有时会 underperform。6

所以：

如果你的任务是“长时间规划和生成”，reasoning model 有帮助；
如果任务是“长上下文中稳定提取和执行规则”，reasoning 不一定解决问题。

4. 对你的系统设计的直接建议

你关心的是：

开头 4K 放严格规则，长上下文下会不会丢？怎么控制？

基于数据，我建议：

4.1 不要只在开头放规则

因为 LongGenBench 说明即使指令在前 500 tokens，长输出超过 4K 后 adherence 也明显下降。1

建议三点锚定：

text
[开头] 完整规则 R1-R20
[任务前] 与本任务相关的规则摘要 R1,R3,R7
[输出前] 必须执行 compliance checklist
4.2 把规则从长自然语言压成短编号

例如：

text
[R1] 不得修改公共 API，除非任务明确要求。
[R2] 所有变更必须报告文件路径。
[R3] 不确定时必须写 UNKNOWN，不得编造。
[R4] 最终输出必须包含 Compliance Checklist。

这样模型更容易在长上下文里引用和核对。

4.3 每个 agent 先做“规则提取”再执行

让 agent 在开始工作前输出：

JSON
{
  "relevant_rules": ["R1", "R3", "R4"],
  "task_scope": "...",
  "forbidden_actions": ["..."],
  "success_criteria": ["..."]
}

这相当于把长上下文任务转换成短上下文任务。
这和 “Context Length Alone Hurts” 论文提出的 “recite retrieved evidence before solving” 是同一思路，该方法在 RULER 上最多提升 GPT-4o 约 4%。1

4.4 最终必须有可校验 checklist

强制输出：

Markdown
## Compliance Checklist
| Rule | Status | Evidence |
|---|---|---|
| R1 | PASS/FAIL/UNKNOWN | ... |
| R2 | PASS/FAIL/UNKNOWN | ... |
| R3 | PASS/FAIL/UNKNOWN | ... |

但这还不够。最好再加一个 Verifier Agent 或程序校验：

JSON schema；
regex；
diff path check；
lint/test；
禁止路径检查；
必填字段检查；
工具调用合法性检查。

因为 AgentIF 数据显示真实 agent 指令最佳模型完美遵循率仍低于 30%，不能只靠模型自觉。1

5. 最终结论
关于稀疏 FP4
5090 的 3352 TOPS、RTX PRO 6000 的 4P 这类数字大概率是 FP4 sparse / AI TOPS 口径；
当前普通 Qwen3.6 / Gemma4 的 FP8、NVFP4、AWQ、GGUF 模型 通常不能自动吃 2:4 sparse 加速；
要吃 sparse，需要权重满足 2:4 structured sparsity，并用 sparse GEMM kernel；
未来可行，已有 SparseGPT、Wanda、MaskLLM、AST、CAST、SparseForge 等技术；
现实端到端加速通常不是 2×，更常见是 1.2–1.5×，除非任务几乎全是 MatMul。
关于上下文长度与指令跟随

有明确数据表明：

LIFBench：Llama-3.1-8B-Instruct 从 4K ARS 0.580 降到 128K 0.388，下降约 33%；GLM-4-9B-chat-1m 从 0.589 降到 0.383，下降约 35%。1
LongGenBench：Qwen2-72B 的 wAvg 从 16K 的 22.7% 降到 32K 的 11.5%，下降约 49%；Mixtral-8x7B 从 23.3% 降到 13.5%，下降约 42%。1
LongProc：GPT-4o 从 0.5K 的 94.8 降到 8K 的 38.1，下降约 60%；Gemini Flash 从 78.9 降到 15.3，下降约 81%。1
AgentIF：真实 agent 指令平均 1717 tokens、11.9 constraints，最佳模型完美遵循率低于 30%，长指令和多约束会继续降低表现。1

所以：

长上下文能“装下规则”，不代表能“稳定执行规则”。
对 agent 系统，必须用规则编号、末尾重锚定、任务前规则提取、最终 checklist、外部 verifier 和程序化校验来兜底。

结果是：某些任务上 ×3 版本能和甚至超过 ×2，尤其 NameIndex / MiddleMatch 这类需要定位的任务。但论文没有给出“重复三次总是更好”的结论，只说这是 promising variant，需要进一步研究。3

同时另一篇 “Asking Again and Again” 对问题重复 1/3/5 次做了阅读理解实验，发现最多提升 6%，但整体不显著，重复问题本身既不显著改善也不显著恶化。6

所以实践建议：

重复方式	建议
重复整个短 prompt 2 次	可以试，尤其非推理任务
重复整个长 prompt 2–3 次	不推荐，浪费 prefill，可能造成上下文污染
重复关键规则摘要 2 次	推荐
每 N 轮插入短提醒	推荐
用完全相同话术重复 3 次	不如编号规则 + 末尾 checklist
3. 加强语气、符号、大写有用吗？
3.1 “MUST / Your task is” 有一定证据

PromptHub 汇总的 “Principled Instructions” 实验里：

使用 “Your task is” 和 “You MUST” 报告 +75% improvement；
使用 “You will be penalized” 报告 +45%；
重复特定词/短语报告 +40%；
分隔符报告 +35%；
Few-shot 报告 +60%；
结构化 ###Instruction### 等报告 +30%。3

原论文也说 26 条原则平均提升模型 response quality / accuracy，平均约 57.7%，且大型模型平均提升超过 10%。2

但要注意：
这些是跨任务、跨模型的平均 prompt-engineering 实验，不等同于“每个生产 agent 都能提升 75%”。

3.2 感叹号、威胁、奖励不如清晰结构

“给小费”“会惩罚”这类方法在某些 benchmark 上有效，但不推荐作为生产系统默认做法：

它可能改变语气；
可能诱导讨好；
可能污染输出；
对本地开源模型效果不稳定；
对长上下文规则遵循不是根本解决。

生产中更推荐：

text
You MUST comply with R1-R7.
If a rule cannot be verified, mark it UNKNOWN, not PASS.

而不是：

text
!!! YOU WILL BE PUNISHED IF YOU FAIL !!!
4. 格式清晰能提升多少？

虽然“格式清晰”很难孤立成一个单一变量，但有几类数据支持它非常重要。

4.1 结构化 prompt 原则有明确提升

PromptHub/Principled Instructions 数据中：

做法	improvement
###Instruction### + 分隔 Instruction / Example / Question / Context	+30%
使用 delimiters	+35%
明确 requirements / keywords / rules	+85%
Few-shot examples	+60%
角色设定	+60%
分解复杂任务	+55%

来源：3

4.2 为什么格式清晰有效？

因为它减少模型要猜的东西。
以下两种 prompt 对模型负担完全不同：

差：

text
你是个开发助手。不要乱改东西。帮我完成任务，最后说一下你做了什么。

好：

text
# Role
You are a coding agent.

# Rules
[R1] Do not modify public APIs unless explicitly requested.
[R2] Do not delete tests.
[R3] If uncertain, write UNKNOWN.

# Task
...

# Output Contract
Return exactly:
1. Work Performed
2. Tests Run
3. Compliance Checklist

第二种把规则、任务、输出、审查点分开了，模型更容易局部匹配。

5. 具体 prompt 写法：哪些最有效？
5.1 用规则编号，而不是长段落

推荐：

text
[R1] 不得修改 public API，除非任务明确要求。
[R2] 不得删除或弱化已有测试。
[R3] 如果缺少信息，必须标记 UNKNOWN，不能编造。
[R4] 最终输出必须包含 Compliance Checklist。

不要：

text
你应该尽量小心，不要随便改不该改的东西，也不要漏掉测试，如果不确定的话最好说明一下……

原因：编号规则更容易被引用、检查、评分。

5.2 把规则变成输出 checklist
Markdown
## Compliance Checklist
| Rule | Status | Evidence |
|---|---|---|
| R1 | PASS/FAIL/UNKNOWN/N/A | ... |
| R2 | PASS/FAIL/UNKNOWN/N/A | ... |
| R3 | PASS/FAIL/UNKNOWN/N/A | ... |

这比只说“请遵守规则”更有效，因为模型必须在输出空间里显式对齐规则。

TICK/STICK 的核心就是把 instruction 分解成 checklist。TICK 让 LLM judge 与人类偏好 exact agreement 从 46.4% 提升到 52.2%；STICK 自我改进在 LiveBench reasoning 上 +7.8%，WildBench Best-of-N +6.3%。6

5.3 给正例和反例

对格式、工具调用、最终报告特别有效。

text
Good final report:
{
  "status": "completed",
  "changed_files": ["src/a.ts"],
  "tests": ["npm test"],
  "compliance": [
    {"rule": "R1", "status": "PASS", "evidence": "No public API changed"}
  ]
}

Bad final report:
"Done, everything works."
Reason: missing files, tests, and compliance checklist.

Few-shot prompting在原则实验中报告 +60%。3

5.4 把关键规则放在开头和末尾

因为模型存在位置偏差。MOSAIC 研究发现，不同模型对约束位置有显著偏差：Llama、Qwen3、DeepSeek 更明显表现出 primacy effect；Claude / Gemini 一些情况下有 recency effect。1

所以要这样：

text
# Global Rules
[R1] ...
[R2] ...

...大量上下文...

# Before answering, re-check:
- R1
- R2
- R3
Return Compliance Checklist.

不要只在开头放一次规则。

6. 自动提醒有用吗？
6.1 短提醒比重复整段系统 prompt 更好

长上下文对规则遵循会衰减。LongGenBench 发现，当输出超过 4000 tokens 后，模型遵循初始指令明显下降；接近 16000 tokens 时进一步恶化。1

所以在多轮 agent 中建议自动插入短提醒：

text
[Reminder]
Active rules: R1, R2, R4.
Before continuing, preserve these rules.
If any rule cannot be verified, mark UNKNOWN.

插入频率可以按风险：

场景	提醒频率
短任务 <8K context	只在开头和结尾
32K–64K context	每 3–5 轮或每个子任务开始
100K+ context	每个 agent 分支开始 + 每次工具调用前后
长输出 >4K	每个阶段结束强制 summary/checklist
6.2 提醒的内容要短

不要重复 4K 规则全文。
只重复：

当前相关规则 ID；
当前任务目标；
输出格式；
禁止事项。

例如：

text
[Rule Anchor]
Relevant rules for this step: R1, R3, R6.
Do not modify public APIs.
Do not invent missing facts.
Final answer must include Compliance Checklist.

这能利用 recency，同时不严重增加上下文负担。

7. 多轮检查 / 自我检查效果如何？

这里要非常谨慎：普通“请检查自己答案”不稳定，甚至会变差；结构化 checklist + critique/refine 才有明显收益。

7.1 普通 Self-Refine 可能退化

STICK 论文指出，在 LiveBench 上，vanilla Self-Refine 会导致显著退化，而 STICK checklist refinement 能提升。6

自我修正综述也指出：在一般任务中，没有强证据表明 LLM 仅靠自己生成的反馈能可靠自我纠错；自我纠错更有效的条件是有可靠外部反馈，例如代码解释器、检索证据、规则校验器等。6

所以不建议只写：

text
Check your answer and improve it.
7.2 Checklist-based self-refinement 有明确收益

TICK/STICK：

TICK 作为评估：LLM judge 与人类偏好 exact agreement 46.4% → 52.2%；
STICK self-refinement：LiveBench reasoning +7.8%；
WildBench Best-of-N：+6.3%；
Command-R+ 在 InFoBench +6.5%；
Command-R+ 在 WildBench +7.1%；
LiveBench：Command-R+ +3.8%，GPT-4o +0.8%，而 vanilla Self-Refine 退化。6

这说明：

让模型按 checklist 一条条检查，比让它“泛泛自我反思”有效得多。

7.3 DECRIM：分解约束→批评→修正，收益更高

DECRIM 针对多约束 instruction following：

流程：

Decompose：把原始 instruction 拆成 constraint list；
Critique：判断哪些约束没满足；
Refine：按反馈修正；
可重复。

结果：

使用 weak feedback：Mistral 在 REALINSTRUCT +7.3%，IFEval +8.0%；
使用 oracle/strong Critic：REALINSTRUCT +16.9，IFEval +20.3；
普通 Self-Refine 在 REALINSTRUCT 只有 marginal improvement，在 IFEval 还下降；
当 LLM 自己同时做 Decomposer 和 Critic 时，收益 minimal 或无收益，说明反馈质量很关键。7

这很适合你的多 agent 场景。

8. 你应该采用的 prompt-only 方案
8.1 单次 agent prompt 模板
text
# Role
You are Agent-{ID}, a task-focused executor.

# Global Rules
[R1] Only solve the assigned task. Do not perform unrelated work.
[R2] Do not modify public APIs unless explicitly requested.
[R3] Do not invent missing facts. Use UNKNOWN if not verifiable.
[R4] Preserve existing tests unless explicitly asked to change them.
[R5] Final answer must include a Compliance Checklist.

# Shared Context
{common_context}

# Agent-Specific Task
{task}

# Required Process
1. Restate the task scope in one sentence.
2. Identify relevant rules from R1-R5.
3. Perform the task.
4. Before final answer, check each relevant rule.

# Output Contract
Return exactly:

## Task Scope
## Work Performed
## Result
## Tests or Checks
## Compliance Checklist
| Rule | Status: PASS/FAIL/UNKNOWN/N/A | Evidence |
## Remaining Risks

# Final Reminder
You MUST complete the Compliance Checklist.
If evidence is missing, mark UNKNOWN instead of PASS.
8.2 多轮自动提醒模板

每隔几轮或每次大上下文之后插入：

text
[Short Rule Reminder]
Current task remains: {task_summary}
Relevant rules: R1, R2, R3, R5.
Do not drift into unrelated tasks.
Do not invent evidence.
Final output must contain Compliance Checklist.
8.3 自检 prompt 模板
text
Review your previous answer against the checklist below.

Rules:
[R1] ...
[R2] ...
[R3] ...

For each rule, answer:
- PASS if satisfied with evidence.
- FAIL if violated.
- UNKNOWN if not verifiable.
Do not revise yet. Only produce the audit table.

然后再：

text
Revise the answer only to fix FAIL or UNKNOWN items from the audit.
Do not change parts that already passed.
Return the final answer with the updated Compliance Checklist.

这比“一步自我改进”稳。

9. 方法效果排序

综合研究和工程可用性，我会这样排序：

排名	方法	预期收益
1	规则编号 + 输出 checklist	高，尤其多约束任务
2	分解约束 → critique → refine	高，DECRIM 弱反馈 +7–8%，强反馈 +16–20
3	结构化 prompt + delimiters	中高，原则实验 +30–35%
4	Few-shot / 正反例	中高，原则实验 +60%
5	末尾重锚定 / 自动短提醒	中高，长上下文中很重要
6	重复完整 prompt 2 次	中，非推理任务很强，47/70 胜 0 负
7	重复三次	中低，部分任务有益，但不稳定且贵
8	“MUST / Your task is”	中，可用但不要滥用
9	大写、感叹号、威胁、奖励	低，不建议作为主方法
10	普通“请自我检查”	不稳定，可能退化
10. 最重要的实践结论

如果你只想做 prompt 改动，我建议不要把精力放在“重复三次”和“语气更强”，而是采用：

text
规则编号
+
任务前相关规则提取
+
输出契约
+
末尾短提醒
+
Compliance Checklist
+
独立 critique/refine

最小可行版本：

text
Before finalizing, audit rules R1-R5.
Return a table:
Rule | PASS/FAIL/UNKNOWN | Evidence.
If any rule is FAIL or UNKNOWN, fix the answer before final output.

这类结构化自检有明确研究支持，比“请认真遵守！！！重复三次！！！”可靠得多。
