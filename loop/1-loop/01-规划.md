# 1-loop — 信息搜集 + 任务分解（实现版）

## 执行流程

### 阶段 A：信息搜集

执行以下动作，收集完整上下文：

1. **意图提取** — 从用户原始表述中提炼核心意图，区分"说的"和"真正想要的"
2. **目标定义** — 将意图转化为可衡量的成功标准
3. **约束梳理** — 列出时间、算力、数据、工具、不可违反的规则
4. **外部信息搜集** — 通过搜索/网页/API 获取必要的外部数据、文献、参考
5. **方法路径确定** — 根据问题类型确定技术路线和工具链

**信息搜集的输出不是文件，而是对 plan.md 的输入。**

### 阶段 B：任务分解 + Review 策略规划

基于信息搜集的结果，生成 `plan.md`：

1. 按子任务分解目标，每个子任务必须定义：
   - ID（T1, T2...）
   - 类型（code / paper / data_prediction / research / other）
   - 输入输出文件路径
   - Review 策略（根据任务类型从 Review 矩阵中选择）
   - 依赖关系
   - 失败修复预案

2. Review 策略定义（直接映射到 2-loop 的验证矩阵）：
   - code 类型 → 直接测试 + LLM 交叉 review
   - paper 类型 → 网页 LLM review + 人工关键论点确认
   - data_prediction 类型 → 实际数据验证 + LLM 方法论确认
   - research 类型 → 外部信息交叉验证 + LLM 逻辑完整性确认
   - other 类型 → 定义特定验证方式 + LLM 交叉确认

3. 执行计划：确定并行子任务的执行顺序和并发限制

### 产出

`<project>/plan.md` — 包含完整的意图、目标、约束、外部信息、方法路径、子任务 DAG、Review 策略定义、失败修复预案、执行计划。

### 人类确认门（PLAN_REVIEW）

plan.md 完成后，**必须触发人类确认**：

```
[2-loop 启动确认]
───────────────────
plan.md 已就绪，请审阅：

1. 意图/目标是否对齐？
2. 约束是否完整？
3. 方法路径是否可接受？
4. 子任务分解粒度是否合理？（>3 的子任务应已进一步分解）

输入确认：
- APPROVE → 启动 2-loop，按 plan.md 执行
- MODIFY → 给出修改意见，回到 1-loop 修订 plan.md
- STOP → 终止任务
───────────────────
```

**注意**：
- 这是计划阶段的唯一人类确认门。2-loop 执行过程中不再阻塞人类确认。
- 确认不是批准每个子任务，而是批准"计划本身"。计划不合理的任务会自然被 2-loop 的 Review 机制淘汰。
