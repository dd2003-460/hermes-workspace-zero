# 1-loop：规划循环（精简版）

> 主 agent 通过此循环将模糊需求转化为可执行计划。5 步循环，验证不通过则回到信息搜集。

## 前置：预检（主 agent 执行）

**进入条件**：收到用户任务描述（可能是模糊的）
**退出条件**：确认需要执行 1-loop，或需求足够清晰可直接进入 2-loop

**操作步骤**：
1. 评估需求清晰度：目标是否可判断成功？约束是否明确？是否有可执行的分步方案？
2. 如果模糊 → 进入 1-loop Step 1
3. 如果清晰 → 跳过 1-loop，直接进入 2-loop

**备份触发**：主 agent 确认进入 1-loop 后，执行 git backup：
```
git add -A && git commit -m "[1-loop] backup: pre-planning"
```

---

## Step 1：信息搜集（主 agent 调度 subagent）

**进入条件**：预检判定需求模糊，需要更多信息
**退出条件**：收集到足以进行任务分解的信息

**操作步骤**：
1. 列出需要搜集的信息清单（技术可行性、现有代码结构、相关研究、依赖关系等）
2. 调用 subagent（researcher）执行搜集
3. 整理搜集结果，判断是否覆盖所有关键问题

**信息检查清单**：
- [ ] 现有代码/文档是否可以复用？
- [ ] 是否有相关研究/论文/工具？
- [ ] 技术约束和依赖是否明确？
- [ ] 是否有已知的风险点？
- [ ] 是否有可参考的最佳实践？

**退出判断**：
- ✅ 全部覆盖 → 进入 Step 2
- ⚠️ 部分覆盖 → 补充搜集
- ❌ 关键信息缺失 → 向用户追问

**置信度评估**（主 agent 自己算）：
- 信息充分性 ≥ 0.7 → 可进入分解
- 信息充分性 < 0.7 → 补充搜集

---

## Step 2：任务分解（主 agent 执行）

**进入条件**：Step 1 信息充足（置信度 ≥ 0.7）
**退出条件**：产出 plan.md（结构化任务计划）

**操作步骤**：
1. 基于信息整理，明确目标、约束、依赖
2. 分解为可执行的子任务（每任务一个目标、一个产出、可独立验证）
3. 识别依赖关系，确定执行顺序
4. 写入 plan.md（格式见下方）

**plan.md 格式**：
```markdown
# Plan: [任务名称]

## 意图
[为什么做这个任务]

## 目标
[完成的标准是什么]

## 约束
[技术约束、时间约束、资源约束]

## 外部信息
[Step 1 搜集的关键信息摘要]

## 方法路径
[整体技术方案/实现思路]

## 子任务
- T1: [名称] - 类型：code/paper/data/research - 依赖：[] - 产出：[文件路径]
- T2: [名称] - 类型：code/paper/data/research - 依赖：[T1] - 产出：[文件路径]

## 执行计划
[子任务执行顺序和并行策略]
```

**退出判断**：
- ✅ plan.md 结构完整、子任务可执行 → 进入备份 + Step 3
- ❌ plan.md 不完整 → 回到 Step 1 补充信息

**置信度评估**：
- 计划完整性 ≥ 0.8 → 进入 2-loop
- 计划完整性 < 0.8 → 回到 Step 1

---

## Step 3：决策（主 agent 执行）

**进入条件**：Step 2 产出 plan.md

**操作步骤**：
1. 审查 plan.md（目标是否清晰？约束是否完整？子任务是否可执行？）
2. 决定是否进入 2-loop
3. 如果进入 → 执行 git backup，输出 ENTER 2-LOOP 信号
4. 如果不进入 → 回到 Step 1 补充信息

**退出条件**：ENTER 2-LOOP 或 回到 Step 1

---

## Step 4：执行

（由 2-loop 负责，这里只启动）
- 2-loop 完成后，产出执行结果

**退出条件**：2-loop 返回验证结果

---

## Step 5：验证（主 agent 执行）

**进入条件**：2-loop 返回执行结果

**操作步骤**：
1. 检查产出是否符合 plan.md 定义的目标和约束
2. 计算置信度：
   - 目标达成度（0-1）
   - 约束满足度（0-1）
   - 风险暴露程度（0-1）
   - 综合置信度 = 加权平均

**退出判断**：
- 置信度 ≥ 0.8 → ✅ 完成，向用户报告结果
- 置信度 < 0.8 → ⚠️ 回到 Step 1 补充信息，修复问题

**验证不通过时的处理**：
1. 明确失败原因（信息不足？方法不对？约束变化？）
2. 回到 Step 1，带着失败信息重新搜集
3. 根据新信息调整 plan.md 或修改子任务
4. 重新进入 2-loop

---

## 置信度计算规则

每步都有置信度评估，作为退出决策的依据：

| 置信度 | 含义 | 动作 |
|--------|------|------|
| ≥ 0.8 | 高置信 | 继续执行 |
| 0.6-0.8 | 中等置信 | 继续但保持警惕 |
| < 0.6 | 低置信 | 回溯到更早的步骤 |

**置信度驱动的退出决策**：
- 高置信 + 验证通过 → 完成任务
- 高置信 + 验证失败 → 回到 Step 1
- 中等置信 → 评估是否继续或回溯
- 低置信 → 必须回到 Step 1 重新搜集
