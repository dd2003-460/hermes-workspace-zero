# 04-verify（验证）

**输入**：执行产出（来自阶段 3）
**输出**：`verification-report.md`（验证报告）

---

## Agent 使用规范

验证阶段**必须使用独立 Agent 进行验证**。Commander 不自行验证——验证必须由独立 Agent 完成：

| 场景 | 使用 Agent | 原因 |
|------|-----------|------|
| 交付物存在性和完整性检查 | `Explore` Agent | Agent 遍历文件确认产出 |
| 质量自检 | `general-purpose` Agent | 独立 Agent 评估产出质量 |
| 置信度计算 | `confidence-judge` Agent | Agent 客观评估置信度 |

**强制要求**：
- 每个交付物的验证必须经过至少一个独立 Agent
- Commander 不做自证——验证结论由 Agent 给出
- **4 步核验，不可跳过**

### 🔑 核心能力：与 LLM 讨论验证（**重点强调**）
> **浏览器控制在验证阶段的作用不只是检查文件存在性，更重要的是利用 LLM 的推理能力发现深层疏漏。**
>
> 通过 `Explore` Agent 的浏览器控制能力，在验证阶段可以：
>
> 1. **让 LLM 检查公式推导**：将推导过程发给 LLM，请求它检查每一步的逻辑正确性、量纲一致性、边界条件合理性
> 2. **让 LLM 发现隐含假设**：将分析结果发给 LLM，请求它识别哪些假设被隐含使用但未验证
> 3. **让 LLM 做反面论证**：将结论发给 LLM，请求它尝试构造反例，判断结论是否可靠
> 4. **交叉验证物理一致性**：将推导结果与已知物理原理（如守恒律、对称性）对比，请求 LLM 判断是否存在矛盾
> 5. **检查与已有文献的一致性**：将关键结论与文献中的结果对比，请求 LLM 判断是否合理、是否有已知的反驳
>
> **为什么这个能力最重要**：LLM 的推理能力远超单纯的符号检查。一个有充分上下文的 LLM 可以发现人类忽视的逻辑漏洞、错误的物理直觉、以及推导中的隐含错误。这是 Commander 独自工作无法获得的。**验证阶段必须利用浏览器控制向 LLM 提问，利用其推理能力辅助判断。**

## 操作步骤

### Step 0：标注环节
输出开头声明：`[环节: verify]`

### Step 1：列出所有可验证交付物（Agent 辅助）
**通过 Agent 辅助**：`Explore` Agent 从 `acceptance-criteria.md` 中提取所有验收标准，转换为可验证交付物清单。

### Step 2：逐一核验（Agent 执行）
**通过 Agent 执行**：对每个交付物，Agent 检查：
- 有产出？→ 存在且完整
- 无产出？→ 标记未完成

### Step 3：质量自检（Agent 审查）
**通过 Agent 审查**：`general-purpose` Agent 对每个交付物检查：
- 有实质内容？（不是模板/空文件）
- 服务目标？（与 `task-definition.md` 一致）
- 无禁止动作？（符合 AGENTS.md 规范）

### Step 4：计算置信度（Agent 执行）
**通过 `confidence-judge` Agent 执行**：Agent 对每个交付物评分 [0,1]，加权平均得到总体置信度。

### Step 5：写入 verification-report.md（Agent 辅助整理）
**通过 Agent 辅助整理**：汇总 Agent 验证结果，写入 verification-report.md。
```markdown
# Verification Report
## 交付物核验
| 交付物 | 存在 | 完整 | 质量 | 置信度 |
|--------|------|------|------|--------|
| [交付物1] | [x] | [x] | [x] | [0.9] |

## 总体置信度
[加权平均值]

## 未通过项
- [如有，列出]

## 结论
**验证通过**（置信度 > 0.6）/ **验证未通过**（置信度 ≤ 0.6）
```
