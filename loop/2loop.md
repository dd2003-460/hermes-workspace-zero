# 2-loop：执行循环（精简版）

> 2-loop 是 1-loop 产出 plan.md 后的执行引擎。每个子任务走单循环：执行 → 验证 → 基于验证决策。

## 进入条件

- 收到 plan.md（1-loop 产出）
- 主 agent 发出 ENTER 2-LOOP 信号

## 退出条件

- 所有子任务完成（置信度 ≥ 0.8）
- 或 2-loop 返回 1-loop（需要重新规划）

## 循环流程

每个子任务严格按以下流程执行：

### Step 0：预检（主 agent 执行）

**操作**：
1. 检查依赖子任务是否已完成
2. 检查输入文件是否存在
3. 通过 → 进入 Step 1；不通过 → 标记 BLOCKED，跳过或等待

### Step 1：备份（固定触发点）

**触发条件**：主 agent 接受 subagent 反馈后，任何子任务执行前

**操作**：
```bash
git add -A && git commit -m "[2-loop] backup: <task-id> pre-execution"
```

**约束**：backup 失败不阻塞执行，但记录到日志

### Step 2：执行

**操作**：
1. 按 plan.md 中定义的子任务执行
2. 产出到 plan.md 定义的文件路径
3. 写入执行日志：

```markdown
# 执行日志: [task-id]

## 意图
[要做什么]

## 方法
[具体做了什么]

## 产出
- [文件路径] - [说明]
```

**约束**：
- 增量修改（Edit 而非重写）
- 每步都 commit

### Step 3：验证（主 agent 执行）

**操作**：根据任务类型选择验证方式

| 类型 | 验证方式 |
|------|----------|
| code | 运行测试套件（pytest/单元测试/功能验证） |
| paper/writing | 全文传给网页 LLM 评审 |
| data_prediction | 用实际数据/已知基准验证预测结果 |
| research | 外部信息交叉验证 + LLM 逻辑完整性检查 |

**产出**：
```markdown
# 验证结果: [task-id]

## 验证方法
[做了什么验证]

## 验证结果
- [验证项1]：PASS/FAIL
- [验证项2]：PASS/FAIL

## 关键问题
[如有问题，列出关键疑点]

## 置信度
[综合评分 0-1]
```

### Step 4：基于验证的决策（主 agent 执行）

**操作**：根据验证结果决定下一步

| 验证结果 | 置信度 | 动作 |
|----------|--------|------|
| PASS | ≥ 0.8 | ✅ git commit，标记 COMPLETED |
| PASS | 0.6-0.8 | ✅ 继续，但警惕 |
| FAIL | 任意 | ⚠️ 分解修复 → 回到 Step 1 |
| UNCERTAIN | 任意 | ⚠️ 标记 AT_RISK，触发人类确认 |

**修复流程**（FAIL 时）：
1. 写入 fix-plan.md：修复意图、方案、修复子任务
2. 修复子任务也遵守单循环（Step 0-4）
3. 修复后覆盖原产出
4. 原任务重新走完整循环

**置信度驱动的循环决策**：
- 即使验证通过，如果置信度 < 0.8，主 agent 判断是否需要回到 1-loop 的信息搜集
- 高置信度 + 验证通过 → 继续下一个子任务
- 低置信度 → 无论验证结果如何，都要回到 1-loop
