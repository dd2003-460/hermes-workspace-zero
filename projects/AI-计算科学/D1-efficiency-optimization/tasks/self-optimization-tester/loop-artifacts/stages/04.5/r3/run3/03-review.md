## 缺陷 1：§3.0 链路硬依赖 arena 通道，与降级条款作用域错配 → 无 arena 的环境整条链路无合法出口

- **引用**：L22 `**自主探索循环（标准链路，每次 goal 必须走通）**：`（"每次"=无一例外）；L24 `→ 找到目标` … L30 `→ 根据 arena 调研结果/建议：交叉验证`；对照 L39 `**验收降级条款**：arena/网络不可用时，baseline 锚点 = pfb 自有 rubric 既有分数，外部对比标 unverified（不虚构）；回执仍必须落盘…`
- **执行者卡点**：逐句照做时，链路 L24–L34 每一步都隐含 arena 在场（L26 找通道 / L28–L29 arena 会话 / L31 "让 arena 推理" / L33 发布仓库）。一个无浏览器、无 arena 登录、无网络的 subagent（如本 run）照读到 L26 即无动作可做；而 L39 的降级条款只规定了 **baseline 锚点与回执**的降级，**没有规定链路本身可整体跳过 arena 的本地等价链路**——降级条款作用域 ≠ 链路作用域，照做者会停在"必须走通"（L22）与"没有 arena"之间，无法判断自己是该 blocked 还是该降级继续。
- **最小修改（≤3 行）**：在 L39 降级条款后追加一条作用域条款：
  ```
  + - **链路降级条款（作用域=整条 §3.0 链路）**：arena/ego-browser 不可用时，L26–L30 的 arena 步骤整体替换为本地等价
  +   （调研=读仓库+文献目录；交叉验证=本地双源复核）并全程标注 unverified，不视为未走通链路；仅当本地也无任何信息源时才 blocked。
  ```

## 缺陷 2：L32 bench 步骤的量化基准自引用（未定义先引用）→ 逐句照做时该步永远无法判定"达标"

- **引用**：L32 `→ 在 0.9 比例的指标数量和总加权分数上，优化到高于开源相关方案的 bench（bench 落点固定：loop-artifacts/stages/04.5/bench.md，指标表+权重+baseline 锚点；下轮 goal 直接引用不重定）`
- **执行者卡点**：逐句照做的 agent 在该步要同时知道三件事：(a) "0.9 比例的指标数量"相对**哪个指标全集**算 0.9；(b) "开源相关方案的 bench" 指哪个/哪些 baseline，如何选取；(c) 加权分数阈值是多少。三者都指向 `bench.md`，而 `bench.md` 的内容恰恰是该步的**产出物**——基准先于存在被引用（自引用）：无既有文件时"下轮直接引用不重定"无对象可引，该步**无终止条件**。本 run 实证卡点：run3 任务书要求 bench-row 自估，但任务书未给 0-100 的打分 rubric，只能反推自既有 bench.md 指标表（存在时依赖前序 run 落盘；缺失时连反推对象都没有）——"引用不重定"与"自估 0-100"之间的换算规则模板未给。
- **最小修改（≤3 行）**：给 L32 补"引用对象缺失/口径换算"分支：
  ```
  ~ L32 …（bench 落点固定：loop-artifacts/stages/04.5/bench.md，指标表+权重+baseline 锚点；下轮 goal 直接引用不重定）
  +   bench.md 缺失时本步 = 初始化落盘：按当前 goal 指标全集定义 指标表+权重（0.9 比例的分母=该全集）+ baseline 锚点（外部不可验证标 unverified）；
  +   任务书要求"自估 0-100"时，换算口径 = bench.md 指标表定义分（不得另造 rubric）；"高于开源方案"在 baseline 全 unverified 时退化为"高于本地既有 rubric 分数"并记录该退化。
  ```

## 缺陷 3：L28 "中转模式"步骤名与触发条件错配 → 执行者无法判断何时走中转、何时直连

- **引用**：L27 `→ 连接对应 GitHub repo（有则连，无则先 gh repo create 再连；验证：git ls-remote 返回 hash + arena 会话内可达）`；L28 `→ 中转模式动作序列（pfb 等中转仓库）：pull → rsync loop/prompt-first → cp sop → 写 tasks/<id>.md（含 §强制段）→ commit+push → ls-remote 验证 → arena 新会话 @repo 读任务书`
- **执行者卡点**：L27 说"有则连"（直连目标仓库），L28 紧跟一个无条件排布在链路中的"中转模式动作序列"——逐句照做者读完 L27 不知道什么时候该走 L28：若目标仓库已连接（L27 完成），是否仍须先 pull/rsync pfb 再中转？链路把它画成必走步骤，而它的实际触发条件（arena OAuth 只绑定 pfb、目标仓库未授权，见 §2.4 L105–L108）写在另一个章节，§3.0 内无指针。照做者要么误把中转当必走（在已直连时多做一轮无意义中转），要么跳过中转（在未授权时 arena 根本读不到任务书 → 断点 B）。**触发条件缺失 = 二义性步骤**。
- **最小修改（≤3 行）**：把 L28 改为条件步骤并加指针：
  ```
  ~ L28   → 中转模式动作序列（pfb 等中转仓库）：pull → rsync …
  +   → [条件：仅当目标仓库未对 Arena OAuth 授权时走中转；授权状态按 §2.4 检查] 中转模式动作序列（pfb 等中转仓库）：
  +     pull → rsync loop/prompt-first → cp sop → 写 tasks/<id>.md（含 §强制段）→ commit+push → ls-remote 验证 → arena 新会话 @repo 读任务书
  +     （已授权 → 跳过本步，arena 直连目标仓库）
  ```
