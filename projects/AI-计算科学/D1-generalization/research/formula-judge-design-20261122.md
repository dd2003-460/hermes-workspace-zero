# 公式 judge 方案：机械形式验证器替代 LLM-judge（2026-11-22）
# origin: ai · 触发：D 问"能否用公式当节点结果判定 + 机械公式验证器 judge"
# 背景：qqbot 评估"离顶会发表质量还差很远"，judge 机制是 gap 之一

## 一句话
把 judge 从"LLM 判"换成"机械公式验证器判"：每题预置可形式化的数值/公式检查点，
SymPy 精确符号值 + 容差比对，reward 只给二元对错（不给正确值），LLM 据此自查自修。

## 为什么（打中 LLM-judge 三大失败）
LLM-judge 三大失败（调研 S6 共识）：self-preference / phantom / 判 surface-compliance。
机械验证器三者全消：
- 无偏好（对任何来源的答案同判）
- 无幻觉（判据是数学，不是模型"觉得"）
- 无 surface 偏差（只认数值对不对，不认表述漂不漂亮）
这正是我们约束（本地 27b、无湿实验、纯信息任务）逼出的方案，
也是顶会 agent/reliability track 的空白点（Jin 线用湿实验兜底，我们用公式兜底）。

## 设计（D 的 5 条全部采纳，各对应一个防 hack 机制）
| D 的提议 | 实现 | 防什么 |
|---|---|---|
| 公式当节点判定 | 每题预置 5 检查点（SymPy 符号值） | judge 可靠性 |
| 无反馈二元判定 + 自修复 | reward 只给 对/错，不给正确值；≤5 轮自修 | 逼真懂而非背答案 |
| 大空间瞎猜不可能 | 2000 次模拟：全 5 项对 0 次（概率≈0） | 防蒙对 |
| 数值代入 | 检查点 = 具体数值（形式难判时） | 适用域扩到数值题 |
| 带根号 + 多检查点 | W=2√5 GB（4 个检查点带 √5） | 防 memorization + 防单点 shortcut |

## 可测的新维度（reward-only 自修复）
- 无反馈 one-shot 通过率（A）vs 二元反馈自修复通过率（B）→ 自修复增量
- rounds_to_pass 分布 → 修复效率
- 这是"模型能否从最小反馈（对/错）自我修正"的测量——泛化新维度，
  且 reward-only 排除了"模型抄了 judge 给的正确值"的混淆

## 边界（修正 2026-11-22 D 纠正）
- ~~公式 judge 只判可形式化核，判不了"解释对不对"，GPU 题只有数值核可机判~~
- **修正**：GPU 题每个节点都有可计算检查点（D 指出）。"可形式化核" = **可查证规格（datasheet 锚点）+ 由规格导出的计算**，两类都能机械判：
  - 查证锚点：BF16/FP8 TFLOPS、HBM 带宽、互联带宽、显存容量（datasheet 可核验）
  - 推导检查点：算术强度、decode 吞吐上限、ridge point、KV cache 大小、14x 误读是否跨口径（可算/可判）
- → **不用换题域**，GPU 题直接扩成多检查点公式 judge 题（每节点 1-2 个检查点）
- 真正判不了的是"非数值解释"（如"为什么这个架构更好"），但这类节点在调研题里占比低
- 带根号防 memorize 的前提：题面参数是新的（27b 没见过 2√5 GB 这个设定）；GPU 题用真实规格，防 memorize 靠"多检查点组合 + 推导链"而非单值

## 集成进 verify+judge pipeline（2026-11-22 D 指令，已实现）

**verify 和 judge 是同一个机械操作的两层**：verify = 逐检查点判，judge = 聚合检查点成总分。
现有 pipeline 的 judge 层是"人工读 final_answer + 关键词脚本"（fp8_scoring.py 那种，
有 self-preference/phantom 风险），机械公式验证替换掉这层。

**三层架构（各判各的，不混）**：
1. **27b solver**：做题（搜索/推理/计算），输出 JSON 或自由文本
2. **机械层（formula_judge.py，本模块）**：verify 逐检查点 + judge 聚合
   - 不依赖 LLM → 三大失败全消
   - 检查点类型：calc（SymPy 符号精确值+容差）/ fact（查证锚点，gold 预置）/ bool（0/1 判定）
   - 双接口：`verify(spec, output)` 返回逐点明细（给人工复核）；
     `judge(spec, output)` 返回总分 + **reward-only 反馈串**（只给对/错不给正确值，直接喂回 27b 自修复）
   - spec 与题面分离：`spec-<题>.json` 预置 gold，模型输出可以是自由文本（自动抽 JSON）
3. **人工层（Lead）**：只判机械层覆盖不到的"非数值解释"（占比低）

**落点**：`decomp/experiments/autoresearch-r1/run/formula_judge.py` + `spec-h100.json`
**实测**：H100 真实 run 输出 5/5 判对（rel_err ≤0.00011），reward 串格式正确
**用法**：`python3 formula_judge.py spec-h100.json <模型输出.json|txt>`（exit 0=pass）

## 连接点：qqbot 发现 2（方向反转）→ 验证器设计修正（2026-11-23）
# 来源：② qqbot 会话 20261118_201149_969e0ffb 补充 29（pfb commit 97d6bb96e，15 run/3849 节点 GPU 域）

**qqbot 的实测**：模型不是"发现缺口→主动检索"(a)→(b)，而是"按 harness 固定节奏检索→检索后批判标缺口"(b)→(a)。
证据：缺口节点 66% 是 search 源（非缺口 27.5%，z=+15.55，15/15 run 全成立）；证据文本全是检索后批判（"[质询]…参考来源仅提供了概述"）。
含义：(a) 在跑（模型能批判），但 (a)→(b) 触发链不存在——检索是 harness 节拍，不是 gap 信号驱动。

**对验证器设计的三个修正**：
1. **不测"会不会主动查"**：若 bench 让模型"自己决定查不查"，测到的是 harness 设计不是模型能力（qqbot 已证模型不自主触发检索）。验证器应把"检索结果"当给定输入。
2. **测"检索后批判得准不准"**：这是模型实测最强的元认知行为（qqbot 证据文本模式）。检查点：
   - bool：模型是否识别出"来源不足/只给概述"
   - fact：模型是否准确说出缺的是什么（gold 预置那个缺失事实）
3. **秩亏题设计修正（直接改 P3 任务）**：
   - 原设计：缺一个关键事实，测模型"正确报信息不足 vs 幻觉出缺的事实"
   - 修正后：给模型**不完整的检索结果**（只给概述、不给那个关键数值），测它能否批判出"来源不够"并准确定位缺口
   - 对齐 qqbot 观察到的真实行为模式，而非假设一个模型不会做的行为（主动检索）

**为什么这个修正重要**：原秩亏题隐含假设"模型会主动去查缺的东西"——qqbot 证明该假设不成立。按原设计出题，模型大概率不触发检索，测出的是"模型不查"（harness 问题）而非"模型批判不准"（能力问题）。修正后测的才是目标 AGI 维度：**给定信息，批判/判定的准确性**（= 满秩类比里"信息充分性判定"那条腿）。
