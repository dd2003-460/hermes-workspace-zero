Subject: MoLRSI at small-model scale: where does the memory loop break?

Dear Prof. Jin,

I'm D, a physics-background researcher building local LLM research agents (27B-class, prompt+hook only, no weight changes). I read MoLRSI (2610.39714) in full — the experience-guided MCTS over workflows plus the three memory streams (solution/refinement/execution) is the cleanest statement of agent-level recursive self-improvement I've seen.

One dimension your line hasn't tested: every backbone in SAGA and MoLRSI is a frontier API model. I work with a 27B local model, and I'd like your read on where the memory loop would break at that scale. In my A/B pilot, the same 27B model with only search snippets inferred a specific benchmark number from a truncated result — right by luck, unverifiable. Given a tool to read full pages, it started attributing every figure to a source and refusing to cite what it couldn't verify. My read: at small-model scale, unverified intermediates written into execution memory are the main contamination risk, and much of it is a tooling gap rather than a capability gap.

Two questions: (1) In MoLRSI, what decides which execution feedback is trusted enough to persist — is there a verification gate, or does the loop assume the backbone's judgment? (2) Which modules of your scaffold exist primarily to compensate for the backbone's inability to verify sources? If the model had a full-source-reading tool, which modules would become redundant?

A 15-minute chat or a one-line answer would both be very useful.

If you're willing, I'm happy to send the endorsement link and a copy of the paper. If not, no obligation at all.
