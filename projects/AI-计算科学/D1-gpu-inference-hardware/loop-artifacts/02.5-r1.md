## 证据与备注

### 研究目标

矩阵硬件计算（matrix / tensor 运算的硬件实现与算力模型），当前 GPU 硬件优化空间，目标：推理场景下硬件还可以怎么优化

### 目标分解

推理场景 GPU 硬件优化可分解为以下 6 个正交子方向，每个子方向对应不同的硬件设计维度，后续 02 阶段将逐一调研：
1. 内存带宽优化：HBM/DRAM 带宽是推理最大瓶颈（compute/bandwidth ratio 低），优化方向包括 HBM3e/HBM4 升级、近存计算、权重流式传输
2. 计算单元利用率：Tensor Core 在推理 workload 上的实际利用率远低于峰值（稀疏性不足、算子融合不足），优化方向包括算子融合、动态精度切换、稀疏加速
3. 低精度与稀疏化：FP8/INT8/INT4 推理精度支持，结构化/非结构化稀疏，硬件级稀疏矩阵乘法
4. 互连与多卡扩展：NVLink/PCIe/CXL 互连带宽对多卡推理的瓶颈，集合通信硬件加速
5. 功耗/热设计约束：推理场景的 PUE 和 TDP 限制，动态电压频率调节 (DVFS)，功耗感知调度
6. 架构特异性优化：针对 Transformer/MoE/RNN 等不同模型架构的硬件特化（如注意力机制专用单元、MoE 路由硬件）

证据：
- loop-state.json authoritative_inputs (user prompt)
- 领域知识：GPU 推理硬件优化空间可归纳为 6 个正交方向

### 研究背景

现有 GPU 推理硬件基线认知：
1. 内存墙：H100 峰值算力 989 TFLOPS (FP8)，但 HBM3 带宽仅 3.35 TB/s，compute/bandwidth ratio ~300，推理场景（尤其是大 batch 或小模型）实际受限于带宽而非算力
2. Tensor Core 利用率：实际推理 workload 中 Tensor Core 利用率通常 30-60%，远低于峰值，原因包括算子碎片化、控制流分支、内存访问模式不连续
3. 低精度趋势：FP8 (E2M1) 已在 H100 支持，INT8 广泛部署，INT4/FP4 在研究中；稀疏性（2:4 结构化）在 H100 硬件级支持
4. 推理 vs 训练差异：推理不需要反向传播、optimizer state、gradient checkpointing，可释放大量内存和计算用于前向加速
5. 自定义加速器竞争：Google TPU v4/v5p 在特定模型上能效比 GPU 高 2-5x；Groq 的 LPU 消除内存墙；Cerebras 的 wafer-scale 架构
6. 模型架构演进：Transformer 主导但 MoE 架构兴起，MoE 的稀疏激活模式对硬件设计提出新要求（路由效率、专家并行）

证据：
- 领域知识：当前 GPU 推理硬件 landscape
- NVIDIA H100/A100 规格文档（FP8/FP4/稀疏性支持）
- AMD MI300X/MI250X 规格
- Custom AI accelerator (TPU v4/v5p, Groq, Cerebras)

### 约束条件

推理场景硬约束（默认全范围，后续 02 阶段可针对特定场景细化）：
1. 时延约束：p50 < 100ms（短回复），p99 < 2s（长回复），首 token 时延 (TTFT) < 50ms
2. 吞吐约束：单卡 QPS 需支持并发请求，典型 100-10000 QPS 范围
3. 功耗约束：单 GPU TDP ≤ 700W（H100 级别），数据中心 PUE ≤ 1.2
4. 成本约束：$ per 1M tokens 需持续下降，硬件 ROI 周期 ≤ 3 年
5. 精度约束：FP16/BF16 为基线，FP8/INT8 可接受但需验证精度损失 < 1%，INT4 需量化感知训练
6. 批量约束：dynamic batching 支持，max batch size 受显存限制
7. 模型规模约束：覆盖 7B-175B 参数模型，上下文长度 4K-128K tokens
8. 兼容性约束：需支持主流框架（vLLM, TGI, TensorRT-LLM）和模型格式（HuggingFace, GGUF）
