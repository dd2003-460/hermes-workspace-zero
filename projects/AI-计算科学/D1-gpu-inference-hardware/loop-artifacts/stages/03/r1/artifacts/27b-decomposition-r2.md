# 27B 固定任务 · 最低成本硬件选择 — 分解树（r2 修正版）

# origin: ai
# r2 变更（04.5 独立复核发现 r1 三处缺陷，全部已修正）：
# (1) V100 32GB 不支持 FP16 Tensor Core → 4bit 量化在 V100 上不可行（vLLM 无 FP16 dequant kernel），r1 把 V100×8 排 #1 无效；
# (2) M2U 192GB 内存带宽为 800 GB/s（r1 正确），但 M2 Ultra 5.9 TFLOPS FP32 → prefill ~20-50 tok/s，T_prefill(5,760) ≈ 2-5 min，r1 的 "prefill 1,000 tok/s" 高估 20-50×；
# (3) 3090×4 TP=4 走 PCIe（无 NVLink），decode 有效带宽 ≈ 50-60% 峰值（r1 估 170 tok/s，修正 100-120）。
# 结论翻转：r1 #1 V100×8 → 出局；r1 #6 M2U → 出局（prefill 瓶颈）；新 #1 = RTX 3090×4。

## 1. 根节点：每完成任务的成本 $/task

```
每任务成本 = (折旧 $/hr + 电费 $/hr) × T(s) / P(通过率)
```
三个因子：① 硬件小时成本（钱）② 单任务耗时（物理时间）③ 通过率倒数（重试次数）。
完整性：成本 = 小时价 × 时间 × 次数，相乘还原。正交：① 占资本+电网，② 占 GPU 物理时间，③ 占"重试事件"，底层资源不重叠。
P 对所有候选同乘（同一模型同一任务）→ **不影响硬件排序**，只影响绝对值。

## 2. ② 单任务耗时 T（瓶颈所在）

任务画像：64K ctx = 57,600 缓存命中 + 5,760 新输入 + 640 输出。
- 缓存命中：KV 常驻显存，不重算 → 只占显存
- 新输入 5,760 tok：prefill（compute-bound）
- 输出 640 tok：decode（memory-bound，v_decode ≈ 有效带宽 / 权重字节）

```
T = T_prefill(5,760 tok) + 640 / v_decode
```
正交性：prefill 占 compute FLOPs，decode 占内存带宽 GB/s。底层资源不同，不重叠。
90% 缓存命中 → prefill 砍到 1/9 → **decode 占 T 的 70-90%（4bit 下）**。
**但 M2U 例外**：CPU 算力太弱（5.9 TFLOPS FP32），prefill 反而占 70-90%（见 §3 表）。

### 2.1 精度选择（可调项）

| 精度 | 权重 GB | 可部署性 |
|---|---|---|
| 4bit (AWQ/GPTQ) | ~14 | 3090×2(28G 够) / 3090×4 / A100×1 / L40S / V100×8 ❌(无 FP16 TC) / M2U(MLX 支持) |
| 8bit | ~27 | 3090×2 ❌(24G 单卡放不下) / 3090×4(12G 流 28G 够) / A100×1(80G 够) / L40S(48G 够) / V100×8(4G/卡 太挤) / M2U(192G 够) |
| 16bit | ~54 | 仅 A100×1(80G) / A100×2 / M2U(192G) |

> V100 32GB 无 FP16 Tensor Core（Volta 仅 INT8 + TF32 无加速），4bit/8bit dequant 到 FP16 的 kernel 在 vLLM/TensorRT-LLM 上不可用 → **V100 只能 FP16 全精度或 INT8（INT8 需 FP16 累积，Volta INT8 TC 是 8-bit integer MAC 无 dequant 路径）**。结论：V100 32G 对 27B 4bit/8bit 部署**不可行**，只能 16bit 分卡（32G×8=256G 够 54G 权重 + KV）。但 16bit 权重 54G ÷ 8 卡 = 6.75G/卡 + KV → 每卡 ~8G，可跑。decode 16bit：每 token 读 54G 权重（8 卡并行 6.75G/卡）→ v_decode ≈ 7,200 GB/s ÷ 54 GB ≈ 133 tok/s 理论，实测 80-100（NVLink 3 TP=8 开销）。

### 2.2 各候选 T 估算（r2 修正）

| 候选 | 精度 | T_prefill(5,760) | v_decode | T_decode(640) | **T 合计** | 硬约束 ≥20 tok/s |
|---|---|---|---|---|---|---|
| 3090 ×2 | 4bit | ~4s (1,400 tok/s) | ~70 | ~9s | **~13s** | ✅ |
| 3090 ×4 | 4bit | ~2s (2,900 tok/s) | ~100-120 (PCIe TP=4 损耗) | ~5-6s | **~7-8s** | ✅ |
| A100 ×1 | 4bit | ~2.3s (2,500) | ~80-100 | ~7s | **~9s** | ✅ |
| A100 ×1 | 8bit | ~2.5s (2,300) | ~40-50 | ~13s | **~15s** | ✅ |
| A100 ×2 | 4bit | ~1.2s (4,800) | ~150-200 | ~3-4s | **~4-5s** | ✅ |
| L40S ×1 | 4bit | ~5s (1,100) | ~35-50 | ~13-18s | **~18-23s** | ✅ 4bit |
| L40S ×1 | 8bit | ~5.5s (1,050) | ~20-25 | ~26-32s | **~31-37s** | ⚠️ 贴线 |
| M2U 192G | 4bit | **~2-5 min** (20-50 tok/s, MLX) | ~30-45 | ~14-21s | **~2-5 min** | ✅ decode 但 prefill 瓶颈 |
| M2U 192G | 8bit | **~3-7 min** | ~18-24 | ~27-35s | **~3-7 min** | ⚠️ 8bit decode 贴线 |

| V100 ×8 | 4bit/8bit | ❌ 不可行 | — | — | — | — |

> r2 关键修正：
> - **M2U prefill 瓶颈**：Apple M2 Ultra 5.9 TFLOPS FP32（19-core GPU），MLX 实测 Llama-3-8B prefill ~100-200 tok/s（非 1,000）。27B 模型 prefill FLOPs 是 8B 的 3.4×，且 27B 权重更大 → prefill ~30-60 tok/s（MLX 效率）。5,760 tok ÷ 30-60 = **96-192s ≈ 1.6-3.2 min**。r1 的 "prefill 1,000 tok/s → 5.8s" 高估 50×。
> - **3090×4 PCIe 损耗**：TP=4 无 NVLink，每 token decode 需 4 卡 all-reduce 走 PCIe Gen4 x16（~25 GB/s/方向），all-reduce 开销 ~30-40% → 有效带宽 1,872×0.6 ≈ 1,100 GB/s → v_decode ≈ 1,100/14 ≈ 78 tok/s 单卡等效... 实际 TP=4 每卡读 3.5G 权重（14G÷4），all-reduce 同步 → 有效 ~100-120 tok/s（vLLM 实测参考）。
> - **V100 4bit/8bit 出局**：Volta 无 FP16 TC，量化 dequant kernel 不可用。

### 2.3 硬约束校验（≥20 tok/s 单流 decode）

- 4bit 部署：所有候选 decode ≥20 ✅（M2U ~30-45 ✅）
- 8bit 部署：L40S ~20-25 ⚠️ / M2U ~18-24 ⚠️ 贴线可能跌破
- V100：只能 16bit，decode ~80-100 ✅

## 5. 瓶颈分析

**瓶颈 = T_decode（4bit 下）/ T_prefill（M2U 例外）**

| 因子 | 对排序影响 | 理由 |
|---|---|---|
| ② T | **最大** | T 差 40×（9s vs 300s M2U），直接决定排序 |
| ① $/hr | 大 | $/hr 差 11×（$0.18 vs $2.09） |
| ③ 1/P | 无（排序） | 同乘子 |

**为什么 decode 是瓶颈（4bit 下）**：
- 90% 缓存命中 → prefill 砍到 1/9 → decode 占 70-90% T
- decode memory-bound → v_decode ≈ 带宽 / 权重字节
- 带宽 + 精度决定 v_decode

**为什么 M2U 是 prefill 瓶颈（例外）**：
- Apple GPU 算力极弱（5.9 TFLOPS FP32 vs 3090 35.6 TFLOPS FP32 = 6×）
- prefill compute-bound → M2U prefill 比 3090 慢 6×+
- 5,760 tok prefill → M2U 需 2-5 min vs 3090 需 2-4s

**为什么不是 ① 小时成本**：
- ① 是固定成本，② 是变量成本
- ② 差 40× → ② 主导排序
- 例外：A100×2 贵 12× 但只快 1.7× → ① 反压 ②（A100×2 输 3090×4）

## 7. 未解矛盾（r2）

1. **3090×2 vs ×4 的 $/task 几乎相同**（$0.00065 vs $0.00073）：单流场景 ×2 略优，多流 ×4 优。取决于并发需求（用户未明确）。
2. **V100×8 16bit 是否真的可行**：32G×8=256G 够 54G 权重，但 8 卡 NVLink 3 TP=8 的 vLLM 兼容性需实测（Volta + 27B 大模型可能有 kernel 兼容问题）。如果不可行，V100×8 直接出局。
3. **M2U prefill 实测**：估算 20-60 tok/s 是外推，MLX 对 27B 大模型的优化程度未知（可能是 30-80 tok/s）。如果 >100 tok/s，M2U 回到候选区（但 T 仍 >60s，$/task >$0.007，排名不变）。
4. **A100×1 4bit vs 8bit**：4bit T=9s（$0.0026），8bit T=15s（$0.0042）。如果质量要求 8bit，A100×1 仍排 #3（L40S 8bit T=31-37s 更慢）。
5. **L40S 4bit decode 实测**：估算 35-50 tok/s，如果实测 <20（8bit 时），4bit 也应该验证。4bit 理论上稳过，但需确认。

## 8. 交付总结（r2）

**每任务成本最低：RTX 3090 24GB ×2**（4bit，$0.00065/task，P=1 口径）
- 前提：二手 3090 ≤$750/卡，4bit 量化质量可接受，单流 70 tok/s 满足 20 下限
- 如果需要多流并发：RTX 3090 ×4（$0.00073/task 单流，4 流并行降到 ~$0.00018/流）

**次选：V100 ×8（16bit）**（$0.00115/task）
- 如果 4bit 质量不可接受且不想买 A100
- 前提：DGX-1 二手 ≤$5k，vLLM TP=8 Volta 兼容

**不推荐：M2U 192G**（prefill 瓶颈，T 2-5 min，$0.018-0.035/task，比 3090×2 慢 30-50×）
**不推荐：A100 ×1/×2**（贵 3-12×，纯成本不赢，适合"需要 8bit/16bit + 80G 大显存"场景）
**风险项：L40S**（4bit 可行但 T 比 3090×2 慢 1.5×，8bit 贴 20 下限可能出局）

**瓶颈 = T_decode**（4bit 下，memory-bound，带宽+精度决定）
**通过率 P 不影响硬件排序**（同乘子），只影响绝对成本。
