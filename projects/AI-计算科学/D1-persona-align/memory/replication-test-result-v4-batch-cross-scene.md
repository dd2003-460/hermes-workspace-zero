# 4 场景 × 4 prompt 格式（flat16/axioms5/structured/prose）× 3 轮，8787 qwen3.8-27b，temperature 0.3

## 核心结论
**prompt 格式在 27b 上零差异。** 四个场景（A 磁盘清理陷阱 / B 引用链陷阱 / C 规则抽象 / D bug 猜测-验证）
全部四臂同分。瓶颈在任务难度，不在 prompt。

## 场景性质区分（D 2026-11-20 指出，修正原"跨场景零差异"的混同）
- **A/B = bench 型**：离散任务、pass/fail 判分，和官方 eval（SWE-bench 式 bug 修复、文件操作类）同物种。
  零差异 = 饱和（27b 做这些太稳），是评测结论，不是研究结论。
- **C/D = research 型**：C 是规则归纳+压缩+泛化（从 12 例压出规则、测未见例），D 是猜测-验证闭环
  （先猜 bug 再修，真执行 reward）。零差异 = 模型抽象能力对 prompt 格式不敏感的 null result，
  性质不同——bench 零差异说明任务太浅，research 零差异说明格式杠杆在 27b 这个能力点上不显现。
- 两个物种的"下一步"也不同：bench 型加难度/换模型即可；research 型要立成研究问题
  （压缩率、泛化曲线、跨模型对比、对标已有 rule induction / 压缩研究）。

## 27b 能力画像（本批实测）
- 前提质疑：100%（数据矛盾一眼看出）
- 引用链识别：100%（config 指向文件的关系自己发现）
- 规则抽象：能压出"可重建则删"并泛化到矛盾边界例
- bug 定位：连别名共享（`[[x]*n]*m`）、原地修改、状态污染这类"测试报错定位不了"的 bug 都能一次修对
- 27b 的天花板不在这些任务上——需要更难的任务才能拉开 prompt 差异

## 踩过的坑（driver 层，非模型层）
1. 场景文本里写明提示 = 把答案递到嘴边（v1 陷阱全过且无差异）→ 提示必须藏在数据里
2. 后台进程（terminal background）绑当轮进程组，turn 切换被回收 → 短批量（<10min）前台跑，skip 机制保证幂等
3. 任务描述歧义（"完整函数代码"）→ 模型只输出改的函数，测试全挂。改成"必须含所有函数可直接执行"后全过
4. 测试期望值格式要匹配 json.dumps 输出（tuple 变 list）
5. 有状态 bug 的测试必须同一进程顺序跑（sequential 模式）
