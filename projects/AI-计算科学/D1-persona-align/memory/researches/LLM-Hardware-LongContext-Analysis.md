## Phase 1: 问题澄清

### 真正的问题

用户问的是"长文本下有什么硬件比较合适"。这不是一个简单的问题，需要澄清：

1. **"长文本"定义**: 
   - 短上下文: < 8K tokens
   - 中长上下文: 8K-128K
   - 长上下文: 128K-1M
   - 超长上下文: > 1M tokens
   - **我们的场景**: 对话记忆 + 研究报告 + 学术论文 → 预估 100K-500K tokens

2. **"合适"定义**:
   - 不是"最快"，是"性价比最优 + 对齐成璐需求"
   - 延迟: 推理速度（tokens/sec）
   - 显存: 需要容纳 KV cache + model weights
   - 成本: 硬件价格 + 电费
   - 可用性: 能否本地运行还是必须云端

3. **"什么硬件"**:
   - GPU (消费级/数据中心级)
   - CPU (大内存)
   - FPGA (专用加速)
   - CXL 扩展内存
   - 光子加速 (前沿)

### 验收标准

- 支持 100K-500K context length
- 推理延迟 < 5 tokens/sec (可接受)
- 成本 < 可控范围
- 可本地部署 or 合理云端

- 我们需要运行中等大小的模型（7B-70B parameters）

## Phase 2: 分层分析

### 2.1 物理机制层面

**核心瓶颈**: 注意力操作需要读取 KV cache，成本为 O(n) memory bandwidth cost (Park & Park, 2026, arXiv:2603.21576)。

这意味着：
- **推理瓶颈不在计算 (compute)，而在内存带宽 (memory bandwidth)**
- 上下文越长，KV cache 越大，读取 KV cache 的时间越长
- HBM (High Bandwidth Memory) 的带宽远高于 DDR

**关键公式**:
```
推理延迟 ≈ model_compute_time + KV_read_time + output_gen_time
KV_read_time ∝ context_length / memory_bandwidth
```

当 context_length 增大时，KV_read_time 主导总延迟。

### 2.4 前沿技术层面

**5 篇关键论文 (2024-2026)**:

1. **PRISM (arXiv:2603.21576)**: 光子注意力引擎，O(1) block selection vs O(n) 电子扫描。突破 O(n) 内存墙。
2. **TRACE (arXiv:2509.03377)**: CXL 扩展内存，lossless compression + precision scaling。解决上下文超出 GPU 显存的问题。
3. **FAST-Prefill (arXiv:2602.20515)**: FPGA 加速稀疏注意力，liveness-driven caching。
4. **Adaptive KV Cache Reuse (arXiv:2605.24022)**: 选择性重用 KV cache，减少冗余计算。
5. **Hydragen (arXiv:2402.05099)**: 共享前缀优化，batch 处理时消除冗余。

**洞察**: 这些论文一致指向 **内存带宽是核心瓶颈**，不是计算能力。

### 2.5 替代解释层面

**是否有其他因素更重要？**

1. **模型大小**: 小模型 (7B) 在同样硬件上支持更长 context。但能力可能不足。
2. **量化**: 4-bit 量化可将显存需求减半，但精度损失。
3. **KV cache 压缩**: 最近研究 (Adaptive KV Cache Reuse) 显示，不是所有 token 的 KV cache 都同等重要。

## Phase 3: 边界检查

### 结论成立条件

- "HBM GPU 是长上下文最佳选择" 成立条件：
  - 需要频繁推理（云端 cost 可接受）
  - 需要超长 context (>200K)
  - 需要生态兼容性（vLLM, PagedAttention）

- "Apple Silicon 是性价比之选" 成立条件：
  - 可接受中等 context (100K-200K)
  - 偏好本地部署
  - 对推理速度要求不极端

### 结论失效条件

- 如果 context < 32K，GPU vs CPU 差异不明显
- 如果模型 < 7B，任何硬件都支持很长 context
- 如果 context > 1M，需要 CXL/光子等前沿方案

## Phase 5: 综合结论

### 主要结论

**对于 100K-500K context 的 LLM 推理：**

| 优先级 | 方案 | 适合场景 | 理由 |
|--------|------|---------|------|
| 1 | **Apple Silicon (M4 Max, 128GB+)** | 本地推理，预算有限 | 统一内存架构天然适合大 context，MLX 生态成熟，成本最优 |
| 2 | **NVIDIA H100/A100 云端** | 超长 context (>1M) 或高频推理 | HBM 带宽最高，vLLM 生态最佳，按量付费灵活 |
| 3 | **AMD MI300X** | 需要本地 + 大显存 | 128GB 显存，价格低于 H100，但生态仍在改善 |
| 4 | **CXL 扩展 (TRACE)** | context > GPU 显存 | 前沿方案，研究阶段，但解决核心瓶颈 |
| 5 | **FPGA 加速 (FAST-Prefill)** | 特定场景优化 | 能耗比 GPU 低，但需要专门编程 |

### 不确定性与后续

1. **量化精度**: 4-bit 量化是否影响成璐的推理需求？需要实际测试。
2. **多 agent 并发**: Ralph Loop 的多 agent 场景需要多少并发推理能力？
3. **光子/CXL 未来**: 这些方案在 1-2 年内是否实用？

### 边界条件

- 如果 context < 32K：任何现代 GPU 都够
- 如果 context > 1M：需要 CXL 或光子方案
- 如果预算无限：H100 集群是最佳选择
- 如果追求性价比：Apple M4 Max 128GB 是最佳选择
