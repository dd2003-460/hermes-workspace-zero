# S2/S3 质疑（r2 · 2026-10-22）

## S2（arena 失败模式集）矛盾点

### 矛盾 1：F1"回复未落页"的根因可能不是 arena
- **假设**：arena agent mode 页面异常 / GitHub outage / 后端超时
- **矛盾**：本会话 4 次 arena 失败中，有 2 次是 **ego-browser 侧** 的 `page.fill` 故障（16ffc349 closing: "The page.fill didn't work. Let me try using page.keyboard to type the text instead."）——不是 arena 没响应，是 **ego-browser 没成功提交**。
- **影响**：F1 的修复方向（三档超时）只解决"提交了但没响应"，不解决"根本没提交"。需要加 **F0 提交失败**（page.fill 静默失败 → 提交前 snapshot 验证输入框有内容 + 提交后 snapshot 验证 URL 变化/页面有"已提交"标记）。

### 矛盾 2：F2"agent 没跑"的判据"30s 内无新 DOM 节点"可能误判
- **假设**：提交后 30s 内无新 DOM 节点 → 判定"没跑"
- **矛盾**：arena agent mode 是 **多步推理**，前 30s 可能在"思考"（DOM 无变化但后端在跑）。本会话 decomp organizer 空等 20min+，前 30s 可能确实在思考，不是"没跑"。
- **影响**：30s 快检可能 **误杀** 正在思考的 agent。建议改为 **30s 无新 DOM 节点 + 无 loading spinner → 判定"没跑"**（loading spinner 是"在跑"的信号）。

### 矛盾 3：F5"多会话冲突"的假设"同一 taskSpace 内开多 page 并发提交"在本会话从未发生
- **假设**：同一 ego-browser taskSpace 内开多 page 并发提交 → 冲突
- **矛盾**：本会话所有 arena 操作都是 **串行** 的（1 个 subagent 1 个 page 1 个任务），从未并发。F5 是 **纯理论推演**，无实证。
- **影响**：F5 的严重度应为 **极低**（理论可能，但本会话未触发），不需要单独 SOP。合并到 F1（串行提交是默认行为，不是异常处理）。

### 矛盾 4：F8"交付物未落盘"的根因可能不是"任务卡未强制"
- **假设**：subagent 结束前未执行写文件步骤 / 任务卡未强制
- **矛盾**：memory-hooks researcher 结束未写文件，但 **任务卡里有落盘要求**（"写入 research/xxx.md"）。问题不是"没要求"，是 **subagent 上下文溢出**（读了太多文件，写文件步骤被挤出 context window）。
- **影响**：F8 的修复方向（任务卡硬约束）不够。需要加 **subagent 侧的 checkpoint 机制**（每读 N 个文件先写 checkpoint，避免 context 溢出后丢失写文件步骤）。

## S3（分解标准）矛盾点

### 矛盾 5："3-7 正交子领域"的"正交性"判据"输入/输出/时间轴重叠 <30%"无法机检
- **假设**：正交性判据 = 输入/输出/时间轴重叠 <30%
- **矛盾**：
  - **输入重叠**：两个子领域都读 loop-state.json 是常见情况（S1 本地证据 + S4 上下文管理都读），但读的是 **不同字段**（S1 读 iteration/last_action，S4 读 current_task/stage），重叠度应该是 **字段级** 而非 **文件级**。
  - **输出重叠**：两个子领域都产出 markdown 表格是常见情况，但表格的 **列定义** 不同（S1=事件/来源/时间/严重度，S2=失败模式/实证/触发条件/SOP 覆盖），重叠度应该是 **列定义级** 而非 **标题级**。
  - **时间轴重叠**：S1（过去证据）和 S2（外部先例）在时间轴上确实不重叠（一个看过去，一个看外部），但 S3（方法论标准）和 S2（外部先例）都看"规范"，时间轴重叠度可能 >30%。
- **影响**：30% 阈值 **不可操作**。建议改为 **字段级/列定义级** 的重叠度判据（可 grep 文件路径 + diff 表头行）。

### 矛盾 6："≤15min 短任务 / 15-30min 中任务 / >30min 长任务"的阈值本会话无实证
- **假设**：≤15min 全部落盘，>20min 挂 2 次
- **矛盾**：本会话 4 个任务的时长/结果：
  - S1 ~3min ✅ 落盘
  - persona researcher 87min ⚠️ 落盘（但无中间痕迹）
  - decomp organizer 20min+ ❌ 空等
  - memory-hooks ~10min ⚠️ 未落盘
  - **10min 的任务也挂了**（memory-hooks），>20min 不是唯一失败条件。
  - **87min 的任务也落盘了**（persona researcher），时长不是决定性因素。
- **影响**：时长阈值 **不是充分条件**。真正的失败因素是 **任务复杂度**（子领域数量 × 每个子领域的 claim 数）× **通道稳定性**（arena vs 本地）。建议改为 **二维矩阵**（复杂度 × 通道），而非一维时长。

### 矛盾 7："arena 通道拆 2 subagent（主调研 + 交叉验证）"的假设"即使挂了一个，另一个还能落盘"可能不成立
- **假设**：arena 失败率高，拆开后即使挂了一个，另一个还能落盘
- **矛盾**：本会话 arena 失败是 **系统性** 的（4 次全部失败），不是随机性的。如果 arena 通道挂了，**两个 subagent 都会挂**（都走 arena）。拆分只防 **随机失败**，不防 **系统性失败**。
- **影响**：拆分策略应 **区分失败类型**：
  - 随机失败（page.fill 故障/超时）→ 拆分有效（1 个挂了另一个还能跑）
  - 系统性失败（arena 后端 outage/登录态过期）→ 拆分无效（都走 arena 都挂）→ 需要 **通道降级**（arena → ego 直抓 → 自答），不是拆分
