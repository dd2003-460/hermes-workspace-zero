## A. arena 多模型能力（关键结论）

**agent mode 无模型选择器（arena 路由）；Direct 模式可自选 1 个模型（127+）；Side by Side 可同时跑 2 个自选模型。** 操作路径与模型清单、截图（4 张，`loop-artifacts/arena-launch/arena-models-20261022*.png`）见前序文件 A 段。

**对消融的用法**：
- 研究/调研类任务 → arena agent mode（主要通道，用户指定）；
- 需要指定具体模型的 run → Direct 模式自选模型跑同一任务书；
- 同一 (题, 变体) 的强弱模型对照 → Side by Side 双模型并行省时间。
- 注意：Direct/Side by Side 无仓库执行层，输出需手动落盘 + push（由 Lead/子代理代做）。

## D. 仓库级工作执行框架（1000 轮机械推进）

### D1. 仓库目录结构

```
prompt-first-bench/
├── bench/
│   ├── tasks/            # 任务卡（001 起编号；调研类+研究类分开标）
│   ├── runs/<task>/<V-k>-<model>/
│   │   ├── run1.md       # 完整输出（非摘要）
│   │   ├── run1-score.md # D1-D4 分值 + 判定
│   │   ├── run2.md / run2-score.md / ...（每格 ≥3 runs）
│   │   ├── meta.json     # {variant, task, model, runs:[{date,score,commit}], degraded:bool, notes}
│   │   └── summary.md    # 本格 3 runs 的 mean±σ + 判定
│   ├── results/          # 聚合 CSV/JSON（从 runs/ 生成，可重算）
│   ├── ablation-matrix.md  # ★ 总览表：行=V0/V1a/V1b/V2/V3/V4/V5，列=题1-5×(强/中/弱)，格=mean±σ (n=3) + 显著性*
│   ├── research-tasks/   # 研究能力题（BrowseComp/GAIA2-3/HLE 选题记录 + 答案清单，盲评用）
│   ├── verify/           # 002 调研交付（已存在，保留）
│   └── FINAL-REPORT.md   # 最终报告（引用 ablation-matrix）
├── tasks/                # 001/002 历史卡（保留原位不迁移，bench/tasks/ 放新卡）
├── rubric/scoring.md     # 不动（100 分制权威）
├── loop/ + sop/          # 不动
```

迁移原则：**不破坏 git 历史**——001/002 留在 `tasks/`，新任务卡进 `bench/tasks/`；`bench/runs/` 按 001 卡已定义的命名（`<task>/V<k>-<model>/runN.md`）执行，002 的 `bench/verify/` 原位保留。

### D2. 一轮（round）标准动作（机械推进）

1. **选单元**：按 ablation-matrix 空缺优先级取下一个 (变体 × 题 × 模型) 单元。填充顺序：先 V0 全格基线（5 题 × 3 模型）→ V1a/V1b（task1-2）→ V1 全格 → V2 → V3 → V4 → V5 → 研究能力题（V0 vs V4 对照）。
2. **派 arena**：agent mode 发任务卡（含"执行前必读"强制段，断点 C 门禁）；需指定模型时 Direct 模式自选模型跑同一任务书，输出由 Lead/子代理落盘。
3. **验收**：对照 `rubric/scoring.md` 逐 run 评分（≥80 success）；检查完整性（完整输出非摘要、来源可验证）。
4. **push**：commit message 规范 `[bench] <V-k> × <题> × <model> run#N: <分数>/100`；`git ls-remote` 验证 HEAD 更新（断点 A 门禁）。
5. **更新矩阵**：`bench/ablation-matrix.md` 本格写入 mean±σ (n)，n 满 3 时判显著性（vs V0，p<0.05 标 *）。
6. **决定下一轮**：回到 1。

### D3. 每轮 push 的验收标准（交付物长相）

- `bench/runs/<task>/<V-k>-<model>/` 新增 ≥1 个 run 的 `runN.md` + `runN-score.md`
- `meta.json` 更新（含 degraded 标记）
- `ablation-matrix.md` 对应格更新
- commit 已 push 到 main（ls-remote 验证）

### D4. 完成判据（"大量且完整的各种变量的消融结果"= 以下全部）

1. **消融矩阵填满**：7 变体（V0/V1a/V1b/V2/V3/V4/V5）× 5 题 × 3 模型（强/中/弱，厂商分散，建议 claude-sonnet-5-high / gemini-3.1-pro-preview / qwen3.6-plus 或按 Direct 列表实际调整）= **105 格**（V1a/V1b 只 task1-2 → 实际 6+24+60=90 格），每格 **≥3 runs**（约 270+ runs），每格 mean±σ + vs V0 显著性；
2. **研究能力对照**：BrowseComp / GAIA L2-3 / HLE 各选 **10 题**（共 30 题），V0 vs V4（正交+完备+交叉验证+反方复核）对照，各 ≥2 runs，按"新结论维度"单独评分（prompt 没给出的新结论数量/质量，评分锚点写进 `bench/research-tasks/rubric-research.md`）；
3. **FINAL-REPORT.md 产出**：回答三问——① 拆解对成功率影响（V1-V0）② 正交完备及每个具体要求的边际（V1b-V1a, V3-V2, V4-V3, V5-V4）③ 强弱模型差异化；每结论带 n + conf；
4. 全部 commit push 到 main。

模型档位暂定（Direct 列表内，强/中/弱各 1，执行前按实际可用性核对）：强 = claude-sonnet-5-high，中 = gemini-3.1-pro-preview，弱 = qwen3.6-plus。

### D5. 失败降级

- arena 不可用/中断 → 本地 subagent 跑同一实验单元（**loop 照跑，降通道不降流程**），`meta.json` 记 `degraded: true` + 原因；
- 下一轮优先补跑 degraded 的格子；
- 登录态失效 → 报告 Lead（需用户重新登录 ego-lite），做其他可推进工作，不阻塞。

### E2. 机制建议

- **max_goal_rounds = 1000**（用户指定）。
- **完成判据显式写进 objective**（§验收标准字段本来就是硬规则，照写即可）——防止 1000 轮跑偏或过早停止。
- **"完成后自主探索新目标"不写进 objective**（写了 goal 永远不会 complete）。写法：完成判据达成 = goal complete；新目标探索由完成后的轮次按 goal-template 流程启动**新 goal**（一次定一个 goal 原则，§1.3）。

### E3. `agents/goal-template.md` 需新增的节（均 ≤5 行，# origin: ai，不改 AGENTS.md）

- **§3.1 仓库级 push 门禁**：目标含"每步 push 到仓库"时，objective 必须写明：目标仓库 URL + commit message 规范（`[bench] <单元>: <分数>`）+ 每轮 `git ls-remote` 验证 + 落盘位置（runs/meta/矩阵）。
- **§3.2 长目标完成判据**：max_goal_rounds > 50 的 goal，【验收标准】必须可机器检查（格数/runs 数/文件路径/阈值），禁止"完整/充分/详细"等不可测词；每 N 轮（建议 100）回读一次本判据防漂移。
- **§3.3 新目标探索准则**：goal 完成后，由后续轮次按本模板启动新 goal；探索准则落盘 `projects/<项目>/tasks/new-goal-criteria-<日期>.md`（# origin: ai），准则需含：候选方向 ≥3 + 产投比排序 + 每个方向的验收草案。
- **§4 维护**：追加本次变更行。
