# subagent 上下文隔离机制调研（源码级 · 20261023）

# origin: ai

用户问题（m00051）：「如果 subagent 在 dsh 有上一级 agent 上下文，那会不会泄漏任务信息，怎么解决」。
本文为源码级机制结论，补齐并**修正** `tasks/subagent-leak-experiment/`（同目录，10-23 已有实验报告）中「fork 是否继承父对话历史」的未决项：该实验探针**看不到**父历史，与文档矛盾；本文用 DSH 打包产物源码直接裁定。

## 1. 机制结论（证据：DSH 0.11.1 打包源码，解出自 app.asar → /tmp/dsh-asar/）

### 1.1 subagent_fork = 完整继承父会话日志前缀（确定性行为，无脱敏/截断选项）

源码 `node_modules/@deepseek-ai/dsh-subagent-fork-in-process/lib/index.js`（DSH 0.11.1 内）：

- 文件头注释（:5-10）：*"registers a SubagentProvider ... that runs each child as a child Agent SEEDED with a prefix of the parent's session log — so the child inherits the parent's conversation context instead of starting fresh. The seed ends at the last `turn/end`."*
- 实现（:23-28）：

```js
function completedTurnPrefix(parent) {
  const events = parent.session.snapshotEvents();
  const lastEnd = events.findLast((e) => e.type === "turn/end");
  if (lastEnd === void 0) return [];
  return events.slice(0, lastEnd.seq + 1);
}
```

  即 seed = 父会话从 seq 0 到**最后一个 `turn/end`（含）**的全部事件。当前未完成的 in-flight turn 不含（不完整、无法重放）；若尚无已完成 turn，seed 为空 → 子会话全新。
- Provider 声明（:44）：`inheritsParentContext = true`。
- seed 注入（:48-51）：`startInProcessRun(request, { seed })`。

**没有任何配置项可以关掉/截断/脱敏这个继承**：该包的 Config 只有 `{ providerName }`（:14）；`~/.dsh/profiles/desktop/cordis.patch.yml` 里 subagent 相关行只有 model-selection-settings 与 `@deepseek-ai/dsh-subagent` 注册，无 context 长度限制、无继承开关、无脱敏选项。继承的是**事件**（session log 原始事件流），父会话的压缩（compress 块）以 `surfaceOp:replace` 事件形式也在流里，所以子会话看到的就是父会话当时的完整上下文状态（含压缩摘要）。

- 驱动层 `node_modules/@deepseek-ai/dsh-subagent-in-process-driver/lib/index.js`（:161-189）：`startInProcessRun` 用 `seed` + `inheritedEventCount` 建子会话；`applyChildComposition(childCtx, parent, { persona, toolFilter })` 表示 persona/toolFilter 是作用在继承之上的**叠加**，不是替代。
- 子会话 header 带 `isSeeded` + `inheritedEventCount`（`dsh-subagent/lib/index.js:470-479` childSessionMeta），会话文件可据此区分。
- **KV cache 设计意图**（`dsh-base/cordis.patch.yml:377-380`）：*"Fork omits model selection so provider/model stay equal to the parent and the inherited history remains eligible for KV Cache reuse."* —— fork 与父同模型同前缀是**刻意设计**，进一步坐实继承是核心语义。
- **深度上限**：`dsh-subagent/lib/index.js:2822` maxDepth 默认 **1**（子不能再往下 fork）；:2866-2867 执行时校验。

### 1.2 对比：`subagent`（spawn）与 `spawn_teammate`（Team 模式）

- `node_modules/@deepseek-ai/dsh-subagent-spawn-in-process/lib/index.js`：`inheritsParentContext = false`，`start(request) { return startInProcessRun(request, {}) }` —— **不带任何 seed**，子会话只有工具调用时传入的 prompt。这是干净的隔离通道。
- Team 模式 `node_modules/@deepseek-ai/dsh-experimental-tool-agent-team/lib/index.js`：`spawn_teammate` 的 `context: "fresh" | "fork"`（:62、:263）：:290 `provider: context === "fork" ? config.forkProvider : config.freshProvider` —— fork 走的就是上面的 fork provider（继承），fresh 走 spawn provider（不继承）。两个通道语义完全对称，反证 fork = 继承、fresh/spawn = 不带。

### 1.3 会话存储观察（本机只读，~/.dsh/sessions/）

- 目录结构：`~/.dsh/sessions/<工作区路径打平>/session-<uuid>/session.v4.jsonl.zstd`（zstd 压缩的 JSONL 事件流，`zstd -dc` 可读）。
- 本机 `default-workspace` 工作区当前 2 个顶层会话（ec2f…、fbd9…），header 均 `"isSeeded":false,"delegationDepth":0` —— 顶层会话不继承（符合 1.1：seed 只发生在子会话）。
- 顶层会话事件类型实测（fbd9… 为例）：`user/message` 5 条、`assistant/message` 45 条、`tool/call|result` 各 50 条、`step/start|end` 46 条、`usage` 53 条、`agent/inbox/spliced` 2 条；**没有 `subagent/descriptor` 事件**（该事件只在子会话首个 turn 追加，见 driver :145）。
- **限制**：in-process 子会话（本会话的 subagent_fork 产物）不写 `~/.dsh/sessions/`（该目录只含顶层会话）；且本会话（外包高手 Lead）运行于另一 DSH 实例（GUI http://127.0.0.1:43129，其 ~/.dsh 不在本机可见范围），故无法直接 dump 父 Lead 日志比对 seed。机制结论以 1.1 源码为准。

### 1.4 与 subagent-leak-experiment 的关系（修正记录）

`tasks/subagent-leak-experiment/experiment-results.md` 探针 Q1 显示 fork 组「看不到之前的用户消息」，与文档矛盾、标为未决。**源码裁定：矛盾来自探针侧，不是机制侧** —— fork seed 是否含可见用户消息取决于父 Lead 当时上下文：若父会话历史已被压缩（ACP 的 replace 事件），seed 里就是压缩摘要块而非原始用户消息，模型回答「看不到之前的用户请求」完全符合源码行为。即：**泄漏的是父会话的完整上下文状态（压缩后的形态），不是"无"。**

## 2. 泄漏场景分析

**泄漏方向**：fork 是**父 → 子**的继承（父的上下文进子），不是子 → 父。子 → 父只有显式的最终结果（`send_message` / 工具返回值）——这个方向本来就是设计用途，不算泄漏。

| 场景 | 结论 |
|------|------|
| a) 父 Lead 上下文进 subagent？ | **会，且全部**。fork 子带父日志前缀（到最后一个 turn/end）+ 继承父的 provider/model + 叠加 persona。DSH 外包高手模式（Lead 持续 subagent_fork）意味着 Lead 上下文里的一切（任务书、AGENTS.md 注入、压缩摘要、中间决策）都进了每个 fork 子。 |
| b) subagent 之间互相可见？ | **不会**。每个 fork 是独立 sessionId 的子会话，seed 只来自各自的直接父（Lead）；子 A 看不到子 B 的任何内容。隔离粒度 = 会话级。 |
| c) bench V0 对照纯净性？ | 见 §3-2。两条通道分开看：① 本地 `subagent_fork` 跑 V0 → 对照被父 Lead 上下文**污染**（fork 全继承，无截断开关）；② arena 网页 Direct 模式 → 待 ego-browser 核实（见下）。 |
| c-i) arena Direct 会话机制 | `bench-目标调研-20261022.md` §A 未记录 arena Direct/agent mode 是每轮新建会话还是延续上一轮；§D2 说 agent mode 发任务卡、Direct 模式自选模型跑同一任务书，无会话重置的说明。**待 ego-browser 核实**（arena.ai/agent 每轮 prompt 是否新会话、agent mode 是否有跨轮记忆）。这是 V0 纯净性的关键未决项。 |
| d) 用户账号维度 | ego-browser 复用 ego-lite 已登录态，arena 网页 LLM 的任务内容会留痕在**用户自己的**账号/历史里 —— 这是「自己的账号记自己的任务」，风险等级**低**（内部研究项目、自有账号）；真正的对外泄漏面是 arena agent mode 把任务卡+仓库内容发给了外部 LLM 服务（LMArena 路由），这由 arena 的 ToS 决定，不在 DSH 机制层。 |

**另外两条与 fork 无关但同属泄漏面的**（subagent-leak-experiment 已确认，此处引用）：① 系统提示层注入（AGENTS.md 全文 + git status 快照）进入**所有** DSH 子 agent（spawn 也有）；② 文件系统旁路（共享 cwd，子可读 workspace 文件）。

## 3. 解决方案（具体到动作）

**1. 需要隔离的任务改用 `subagent`（spawn），不要用 `subagent_fork`。**
spawn provider `inheritsParentContext = false`，子只拿到 prompt —— 把敏感/对照信息**只写进 prompt 和仓库文件**，不写进 Lead 对话。Team 模式同理选 `context: "fresh"`。fork 只在「子确实需要 Lead 决策上下文」（续写/跟进类）时使用。

**2. bench V0 对照纯净性措施：**
- 本地通道跑 V0：一律 spawn（或本地 CLI 一次性 `claude -p`），prompt 只含 V0 任务卡原文；**禁止** V0 run 与 V1-V5 run 交叉引用同一输出文件；每 run 独立目录 `bench/runs/<task>/V0-<model>/runN.md`（该结构 D2 已定义）。
- arena Direct 通道：先 ego-browser 核实会话机制（§2 c-i）；若 Direct 每轮新会话则 V0 天然干净，若延续则每轮 run 前强制新开会话/清上下文；在 `bench/tasks/001` 任务卡加一条强制段：「本 run 禁止引用本任务卡之外的上下文」。
- 降级通道（D5：arena 不可用 → 本地 subagent）：降级时**必须**用 spawn 且 `meta.json` 记 degraded + 通道名，防止 fork 降级静默污染对照。

**3. 信息分级（强化 AGENTS.md 既有雏形「subagent 无网络，读文件不读 Lead 上下文」）：**
- 只进仓库文件（不进 Lead 对话）：对照 prompt 原文、评分锚点、未公开结论、跨项目敏感材料 —— subagent 靠读文件拿到，Lead 上下文里不留全文（只留路径指针）。
- 可进 Lead 对话：任务状态、路径、决策摘要、结论指针。
- fork 使用时额外规则：Lead 在 fork 前确认上下文里没有「不该让子看到」的内容（fork 无法选择性继承；要选就 spawn + 文件传递）。
- 落地建议：把「fork/spawn 选择标准 + 信息分级」写进 `sop/goal-template.md`（已有 §2.4 子代理隔离 SOP，追加本节结论即可）。
