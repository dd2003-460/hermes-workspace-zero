## 分解总览

本文件将综述 `00-综述.md` 中的流程规范分解为可执行步骤，使用 `R{轮次}-D{深度}-S{步骤}` 编号。

每个步骤按统一格式：
- **类型**：任务种类
- **输入**：前置产出
- **输出**：本步骤产出
- **继续条件**：进入下一步
- **回退条件**：需返工
- **继续输出**：下一步所需数据
- **回退输出**：失败原因 + 需补充内容
- **Gold Case**：正确执行示范（如有）
- **Bad Case**：典型错误示范

## 阶段 1：信息获取

### R1-D1-S1 目标澄清

- **类型**: clarification
- **输入**: 用户原始请求（free-text）
- **输出**: `loop/1-loop/target-clarification.md`
- **继续条件**: 用户确认 OR 综合置信度 ≥ 0.7（搜索已覆盖所有可查项）
- **回退条件**: 用户回答矛盾 / 回答不完整 / 置信度 < 0.5
- **继续输出**:
  - 明确的目标描述（1-3 句）
  - MUST/SHOULD/MAY 假设清单
  - 必须问用户的未决问题及推荐选项
- **回退输出**: 问题清单 + 矛盾说明 + 需用户补充的内容
- **Gold Case**:
  - 面对模糊请求，先搜索已有上下文（tasks.md、memory、已有产出）
  - 将问题组织为选择题 + 推荐项，而非开放问答题
  - 一次性问完所有关键假设，不反复追问
- **Bad Case**:
  - 直接假设目标，不做搜索验证
  - 每次只问一个问题，反复来回
  - 把 "你觉得呢？" 当作澄清

### R1-D1-S2 约束确认

- **类型**: information-gathering
- **输入**: `target-clarification.md`
- **输出**: `loop/1-loop/constraints.md`
- **继续条件**: 所有 MUST 类约束已识别
- **回退条件**: 关键约束（时间/资源/数据）未覆盖
- **继续输出**:
  - 分类约束表：时间、资源、数据、技术、质量、范围、合规、依赖
  - 每个约束的验证方法
- **回退输出**: 未覆盖约束清单
- **搜索优先级**: 项目文件 → 依赖文件 → 代码 → 数据目录 → 工具文档 → 外部信息
- **Gold Case**:
  - 从已有文件自动推导约束（如 CLAUDE.md 中的红线、TASKS.md 中的阻塞项）
  - 区分 "已有约束" 和 "待确认约束"
- **Bad Case**:
  - 列出 "无约束" 当实际上有隐含约束
  - 把 "不限时间" 当作约束列出

### R1-D1-S3 技术背景搜集

- **类型**: information-gathering
- **输入**: `target-clarification.md` + `constraints.md`
- **输出**: `loop/1-loop/tech-research.md`
- **继续条件**: 信息覆盖可搜索领域
- **回退条件**: 关键领域无可用信息（标注而非回退，不回退标记为 "信息不足"）
- **继续输出**:
  - 每个搜索结果标注：来源 URL/路径、时间、置信度
  - 信息缺口清单
- **回退输出**: 标注为 "信息不足" 的领域
- **Gold Case**:
  - 搜索与综述中各阶段对应的参考实现（如 GitHub 上的 loop 框架）
  - 列出已验证可用的信息和纯推测的内容
- **Bad Case**:
  - 引用超过 2 年的技术信息（AI 领域）
  - 不加时间标注的搜索

## 阶段 2：分解

### R1-D2-S1 选择领域模板

- **类型**: decomposition
- **输入**: `target-clarification.md` 中的任务类型
- **输出**: `loop/plan.md` + 选定模板 ID
- **继续条件**: 模板与任务类型匹配
- **回退条件**: 无现成模板可用
- **继续输出**: 模板路径 + 选择理由
- **回退输出**: 模板缺失说明
- **Gold Case**:
  - 根据任务性质匹配：研究 → paper-001，写作 → writing-001，分析 → data-analysis-001，工具 → code-001
  - 如任务跨领域，使用多个模板的组合
- **Bad Case**:
  - 随意选择模板，不看领域特性
  - 模板与产出物类型不匹配

### R1-D2-S2 生成任务 DAG

- **类型**: decomposition
- **输入**: 选定模板 + `tech-research.md`
- **输出**: `loop/plan.md` — 包含完整任务 DAG
- **继续条件**: 每个任务都有统一格式的输入/输出/条件
- **回退条件**: 有任务缺少必要字段
- **继续输出**: 完整的任务 DAG，每个节点符合统一任务格式
- **回退输出**: 缺失字段清单 + 回退到 R1-D1-S3
- **Gold Case**:
  - 每个任务定义后，自问："如果我是一个执行者，仅凭这个定义能完成吗？"
  - 标注并行节点和串行依赖
  - 对每个任务标注置信度预估
- **Bad Case**:
  - 定义 "做研究" 但无输入输出条件
  - 任务之间无 DAG 关系
  - 把 "探索一下" 当任务

### R1-D2-S3 验证分解完整性

- **类型**: verification
- **输入**: `loop/plan.md`
- **输出**: `loop/1-loop/decomposition-verify.md`
- **继续条件**: 所有任务可通过验证
- **回退条件**: 有任务不能独立验证
- **继续输出**: 分解验证报告，标记有问题的任务
- **回退输出**: 具体问题清单
- **检查项**:
  - [ ] 每个任务有输入 AND 输出
  - [ ] 每个任务有继续条件 AND 回退条件
  - [ ] 任务 ID 唯一
  - [ ] DAG 无环
  - [ ] 每个 MUST 类约束被至少一个任务覆盖
- **Gold Case**:
  - 对每个节点执行 "执行者模拟"：仅凭定义能否执行？
- **Bad Case**:
  - 只检查数量不检查质量
  - "都定义了" 当实际定义不完整

## 阶段 3：执行

### R1-D3-S1 按 plan 执行子任务

- **类型**: execution
- **输入**: `loop/plan.md` 中定义的每个子任务
- **输出**: 各子任务的产出文件
- **继续条件**: 子任务产出通过验证标准
- **回退条件**: 产出不符合输入/输出定义
- **继续输出**: 可验证的产出（文件/代码/数据）
- **回退输出**: 产出失败原因 + 具体不满足定义的位置
- **Gold Case**:
  - 执行前：重读该任务的定义，确认理解一致
  - 执行中：遇到问题及时记录，不回退时编造
  - 执行后：产出文件包含自检声明
- **Bad Case**:
  - 定义要代码但只给规划
  - 回退时编造理由
  - 产出文件无版本/时间戳

### R1-D3-S2 子任务验证

- **类型**: verification
- **输入**: 子任务产出 + plan.md 中该任务的定义
- **输出**: `loop/2-loop/verify-{task-id}.md`
- **继续条件**: 验证通过（置信度 ≥ 0.8）
- **回退条件**: 验证失败（置信度 < 0.8）
- **继续输出**: 验证报告，验证方法 + 结果
- **回退输出**: 失败原因 + 建议修复方向
- **检查方法**:
  - 直接验证：grep/code run/check（对代码）
  - 交叉验证：对比多来源（对研究）
  - 逻辑验证：自检一致性和假设（对规划）
- **Gold Case**:
  - 验证方法透明：可复现
  - 验证不通过的节点，给出修复建议
- **Bad Case**:
  - "已完成" 当未实际验证
  - 用 "看起来没问题" 当测试实际可运行

## 阶段 4：验证

### R1-D4-S1 整体验证

- **类型**: verification
- **输入**: `loop/plan.md` 目标 + 所有子任务产出 + 各验证报告
- **输出**: `loop/1-loop/integrity-verify.md`
- **继续条件**: 整体置信度 ≥ 0.8 → 进入 2-loop
- **回退条件**: 置信度 < 0.5 → 回退到分解阶段（新轮次 R2）
- **继续输出**:
  - 置信度计算及依据
  - 遗留问题清单（如置信度 0.5-0.8）
  - 对下一步（2-loop）的指导建议
- **回退输出**:
  - 失败原因分析
  - 建议新轮次如何调整分解
- **置信度计算**:
  - 基础置信度 = 已通过验证的子任务数 / 总任务数
  - 修正因子：信息缺口 × 0.1 / 验证深度 × 0.05 / 假设覆盖 × 0.15
  - 最终置信度 = min(1.0, 基础置信度 + 修正因子)
- **Gold Case**:
  - 诚实标注不确定性
  - 置信度 < 0.8 时，明确告诉 Commander 哪些环节需要加强
- **Bad Case**:
  - 置信度 "看起来很高" 当实际验证不足
  - 把 "未尝试" 当 "已通过"

### R1-D4-S2 决策

- **类型**: branch-check
- **输入**: `integrity-verify.md`
- **输出**: 决策结果
- **继续条件**: 置信度 ≥ 0.8 → 进入 2-loop
- **回退条件**: 置信度 < 0.5 → 新轮次 R2
- **继续输出**: 进入 2-loop 的指令 + 上下文
- **回退输出**: R2 分解建议 + R1 失败教训
- **Gold Case**:
  - 决策依据透明，Commander 可复现判断
- **Bad Case**:
  - 跳过决策直接进下一步

## 分支处理规范

### 回退到分解（R+1）

- **输入**: R{N} 的 `integrity-verify.md` + 所有失败分析
- **输出**: `R{N+1}/plan.md` — 带着失败信息重新分解
- **继续条件**: R{N+1} 的分解覆盖了 R{N} 的失败原因
- **回退输出**: R{N+2} 失败信息追加

### 并行处理

- 无数据依赖的子任务可并行
- 并行节点产出在下一步之前合并
- 并行失败的节点不影响其他节点继续

## Gold/Bad Case 校准库

### Gold Case：综述分解的正确示范

**R1-D2-S2 生成任务 DAG 的正确做法**:
```
<thought>
用户要求分解综述。但我发现综述中有些定义不够具体——比如置信度计算只有阈值没有公式。
我应该：1) 把不明确的定义标注为 "待补充"；2) 基于常识给出默认公式；3) 在 plan.md 中注明这是我的补充。
不应该：假装综述定义是完整的，直接跳过澄清。
</thought>
```

产出格式示例：
```markdown
### R1-D2-S3 生成验证策略
- **类型**: decomposition
- **输入**: plan.md 中已定义的任务
- **输出**: `loop/1-loop/verify-strategy.md`
- **继续条件**: 验证策略覆盖所有 MUST 类任务
- **回退条件**: 有任务无法验证
- **继续输出**: 每个任务的验证方法（grep / code run / 交叉验证 / 逻辑验证）
- **回退输出**: 不可验证任务清单
```

### Bad Case：典型错误

**分解不彻底**:
```markdown
### S1 执行研究
- **类型**: execution
- **输入**: 用户请求
- **输出**: 研究报告
- **继续条件**: 研究完成
- **回退条件**: 信息不足
```
问题：输入输出太模糊，无验证方法，无置信度标注，"完成" 无标准。

**过早假设**:
```markdown
### S1 做文献搜索
- **类型**: information-gathering
- **输入**: 无（自主决定搜索什么）
- **输出**: 搜索结果
```
问题：搜索范围由执行者主观决定，无搜索项定义，无质量要求。

**验证敷衍**:
```markdown
### S3 验证结果
- **类型**: verification
- **输入**: 所有产出
- **输出**: "验证通过"
```
问题：无验证方法，无置信度，无失败时的具体修复建议。
