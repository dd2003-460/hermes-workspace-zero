# D1-goal-investigation — 执行输出：Agent Loop 自主设计指南

> 本文件基于 Codex/Hermes 对比分析（01-信息搜集 + 02-任务分解）产出，将研究结论提炼为可操作的 D1 设计指南。

## 研究目标

理解主流 Agent 框架的任务管理机制，验证 D1-goal-investigation 自主设计的 loop-state.json + ACTIVE.md 导航系统的合理性。

## 对比框架

| 框架 | 任务管理机制 | 状态持久化 | 会话恢复 |
|------|------------|-----------|---------|
| Anthropic API (claude-code) | 客户端驱动 tool_use 循环 | 无（依赖外部） | 需外部状态文件 |
| LangGraph | 服务端驱动图遍历 | Checkpoint（每节点） | resumable_from_checkpoint |
| OpenAI Codex | 服务端任务队列 | 隐式（平台管理） | 自动恢复 |
| AutoGen | 多 Agent 消息队列 | 需外部存储 | 无内置恢复 |
| CrewAI | YAML 声明式任务 | 无 | 无 |

## 关键发现

### 发现 1: LangGraph Checkpoint ID ≡ D1 loop-state.json

LangGraph 的 durable execution 模式与 D1 方案**同构**：

| D1 组件 | LangGraph 对应 | 功能等价性 |
|---------|---------------|-----------|
| `loop-state.json` | Checkpoint | 持久化循环中间状态 |
| `ACTIVE.md` | Checkpoint ID 索引 | 导航入口的导航入口 |
| `ralph-sync.sh` | resumable_from_checkpoint | 跨会话状态恢复 |
| 导航链: INDEX → ACTIVE → loop-state.json | Checkpoint ID → 任意执行节点 | 精确导航到执行点 |

**意义**: D1 的设计被工业级框架验证为正确路径。

### 发现 2: 客户端驱动架构是 loop-state.json 的根源

- **Anthropic API**: tool_use 循环是**客户端驱动** — 每轮 AI 自主决定下一步
- **LangGraph**: 循环由**图定义** — 服务端控制遍历路径

D1 选择客户端驱动意味着无法依赖服务端 checkpoint，必须自行持久化状态。loop-state.json 不是多余，是**架构必然**。

### 发现 3: JSON 状态文件是设计空间中的正确位置

| 位置 | 代表 | 优缺点 |
|------|------|--------|
| 纯配置 | CrewAI YAML | 人类友好但表达能力弱 |
| **JSON 状态 (D1)** | loop-state.json | **人类可读 + 机器可操作 + 脚本可自动化** |
| 纯代码 | LangGraph Python | 表达力强但需要编程能力 |

JSON 状态文件在"可编辑性"和"可编程性"之间取得了最佳平衡。

## 设计指南总结

### 原则 1: 状态文件优于代码定义（对于跨会话导航）

跨会话恢复需要**人类可读**的状态。JSON 文件同时满足：
- AI 可读可写（自然语言理解）
- 脚本可操作（bash/python/jq）
- 人类可审查（Markdown 兼容）

### 原则 2: 导航链长度 < 3 步

D1 导航链: INDEX.md → ACTIVE.md → loop-state.json（3 步）
LangGraph 导航: Checkpoint ID → 任意节点（1 步）

D1 的 3 步导航可接受，因为每步都提供**人类可读**的上下文。LangGraph 的 1 步导航对人类不可读。

### 原则 3: 脚本自动化是核心能力

ralph-sync.sh 和 aggregate-active.sh 构成了状态管理的自动化核心。这比纯代码定义更灵活：
- 可审计（每次同步有日志）
- 可修改（脚本本身是文档）
- 可组合（与 bash 工具链集成）
