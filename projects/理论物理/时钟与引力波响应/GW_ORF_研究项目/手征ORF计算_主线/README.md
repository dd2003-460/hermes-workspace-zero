## 一、总体设计哲学

整条计算流水线是一条"从几何抽象到探测器读数"的单向链条，分成 **4个大阶段**。
每个阶段内部包含若干个**地位平等的组件**（用字母 A、B、C…编号，不分主次），
每个组件文件夹下再按**脚本性质**分为最多三类子文件夹：

- `推导/`：从物理/数学原理出发构造公式结构、或诊断发现新现象的脚本（不一定产出最终数值结果）
- `具体计算/`：真正跑符号/数值运算、得到解析或数值结果的核心脚本
- `数值验证/`：用独立方法（通常是数值积分/蒙特卡洛/直接暴力求和）交叉核对上面两类脚本结果的脚本

不是每个组件都需要全部三个子文件夹——如果某组件目前还没有独立的"推导"环节，
就不建这个子文件夹（等真正产出内容时再建），**空文件夹不占位、不预建**，
这样看目录时能立刻知道"这个组件目前进展到哪一步"。

## 二、四大阶段总览

```
阶段1_单向链路ORF核心积分/     ← 目标: 算出 Γ_one(α,β_u,β_v,ŝ,û,v̂)，两条一般单向链路间的ORF母函数
阶段2_ORF组装_GammaOne/       ← 目标: 把阶段1的四个积分I1~I4按系数(±e^{iβ}等)组装成完整Γ_one
阶段3_具体探测器ORF/          ← 目标: 用Γ_one做线性叠加，得到PTA/GbLI/SbLI/混合网络的具体Γ_IJ(f)
阶段4_探测器ORF反解与探测统计量/ ← 目标: 用算好的Γ_IJ(f)，模拟数据、反解背景谱S_h(f)、验证、算灵敏度
```

**阶段间是严格的单向依赖**：阶段2依赖阶段1的产出，阶段3依赖阶段2，阶段4依赖阶段3。
下游阶段的脚本永远只调用上游阶段的**已完成、已验证**的产出，不允许跳级引用
（比如阶段3不能绕过阶段2直接从阶段1的零件里现拼一个新公式）。

## 三、阶段1 详解（当前项目主要进展所在）

**目标**：算出两条一般单向链路（$\{\vec r_u,L_u,\hat u\}$ 和 $\{\vec r_v,L_v,\hat v\}$）之间的
手征/强度ORF母函数 $\Gamma_{\rm one}$。参照《整合方案》文档，这个母函数在数学上被层层拆解：

$$\Gamma_{\rm one}=\frac{1}{32\pi}\Big[\underbrace{I_1}_{\text{终点-终点}}-e^{-i\beta_u}\underbrace{I_1(\alpha_2,\hat s_2)}_{=I_2\text{,起点-终点}}-e^{i\beta_v}\underbrace{I_1(\alpha_3,\hat s_3)}_{=I_3\text{,终点-起点}}+e^{i(\beta_v-\beta_u)}\underbrace{I_1(\alpha_4,\hat s_4)}_{=I_4\text{,起点-起点}}\Big]$$

而 $I_1$ 本身又是通过复围道积分+留数定理算出来的，拆成5个极点的留数之和：

$$I_1=2\pi i\Big[\int dx\,e^{-i\alpha x}R_0(x)+\int dx\,e^{-i\alpha x}R_1(x)+\cdots+\int dx\,e^{-i\alpha x}R_4(x)\Big]$$

**对应到文件夹的5个组件（注意：组件不分主次，都是平级）**：

| 组件 | 内容 | 当前状态 |
|---|---|---|
| **A_基础设施** | 坐标系、被积核 $\xi_I,\xi_V$ 的构造 | ✅ 完成（BUG-001已修正）|
| **B_I1积分的留数分量** | $R_0,R_1,R_2,R_3\_R_4$ 四个子文件夹，算的是"留数值"（还未对x积分） | ✅ 全部完成（BUG-001已修正，R3_R4现已有符号解）|
| **C_I1完整封闭解** | 把B算出的5个留数各自乘 $e^{-i\alpha x}$ 对 $x$ 积分，拼出 $I_1$ 完整解析式 | ⏳ 待开始（阻塞项已清除）|
| **D_I2_I3_I4_替换导出** | 用PRD论文的矢量替换规则，从C的$I_1$结果直接导出 $I_2,I_3,I_4$（不需要重新做积分） | ⏳ 待开始 |
| **E_核心发现** | 跨组件的规律性发现（比如"±i比例关系"），不属于流水线的某一步，而是对整条流水线的洞察 | ✅ 已推广到全部4个一阶极点，持续更新 |

**⚠️ 重要澄清（很容易搞混的一点）**：组件B算出的 $R_0^V,\ldots,R_4^V$ 是"关于$x$的函数在留数意义下的值"，
**不等于** $I_1^V$ 本身——$I_1^V$ 需要组件C把这5个留数再对 $x$ 做一次积分才能拿到。
这就是为什么本次重构专门把"C_I1完整封闭解"设成一个独立组件、留出空位，
而不是把它和B混在一起。

## 四、跨组件/跨阶段调用规则（最重要的一条规则）

**规则1：下游永远调用上游的"已验证产出"，不重复推导上游已经做过的事。**
比如阶段2组装 $\Gamma_{\rm one}$ 时，直接 `import` 或读取阶段1组件C、D产出的 $I_1,I_2,I_3,I_4$
结果文件（`.pkl`），不允许在阶段2的脚本里重新写一遍留数计算的代码。

**规则2：每个"具体计算"脚本的开头，必须用注释写清楚它依赖哪个上游产出（给出相对路径）。**
示例（这是强制的写作规范，后续所有新脚本必须遵守）：

```python
"""
【依赖】本脚本使用了以下上游产出，运行前确保它们存在：
  - ../../阶段1_单向链路ORF核心积分/组件B_I1积分的留数分量/R1/具体计算/R1V_CORRECTED.pkl
  - ../../阶段1_单向链路ORF核心积分/组件B_I1积分的留数分量/R2/具体计算/R2V_expr.pkl
"""
```

**规则3：产出的中间结果（`.pkl`等）保存在产出它的"具体计算"文件夹里，
下游需要用时"拷贝一份"到自己的文件夹（而不是用相对路径远程读取上游文件夹）。**
这是为了保证每个组件文件夹本身是自包含、可独立运行的（当你只想看某一个组件时，
不需要连带检出上游一整条链路）。拷贝时不改文件名，脚本注释里注明"来源"。

**规则4：同一个组件下，`推导` 产出物理/数学结论（通常是文字+少量符号验证），
`具体计算` 产出可复用的解析式或数值结果（`.pkl`/`.npy`），
`数值验证` 只读取`具体计算`的产出去做交叉核验，不产出新的可复用结果。**

**规则5：新增一个组件/子步骤时，先检查它算的是"谁"、属于哪个阶段哪个地位平等的环节，
再决定往哪建文件夹——原则是"这个新脚本产出的东西，下一步谁会来调用它？"
如果暂时没有明确的下游需求，先放进最贴近的现有组件里，不要新建阶段。**

**规则6：每个有实质产出（不是纯空骨架）的组件文件夹下，必须有一份
`结论与推导过程.md`，作为该组件的"人类可读版"结论汇总，与代码互为印证。**
这份文档不是代码注释的简单复制，而是**按叙事逻辑重新组织**的说明，必须包含：

1. **这个组件要解决什么问题**（一两句话，物理/数学目标）
2. **推导/计算过程**：分步骤描述做了什么（对应哪些脚本、哪一步发现了什么），
   picture级别的推导链条，让不看代码的人也能看懂逻辑
3. **关键结果的解析表达式**：凡是符号计算（sympy）产出的公式，必须用
   `sympy.latex()` 把最终表达式转成 LaTeX 贴在文档里（用 `$$...$$` 包裹），
   **这是为了方便与草稿纸/论文原文手工推导的公式直接核对**，不能只放
   `print(expr)` 的原始 sympy 字符串（那种格式肉眼比对容易出错）。
   写法示例（在脚本里加一行拿到 LaTeX 字符串，再手动贴到 md 里）：
   ```python
   print(sp.latex(sp.factor(final_expr)))   # 复制这行的输出，贴进结论md的公式块
   ```
4. **数值结果**：验证用的具体数值（比如"8组随机参数最大相对误差1e-12"），
   直接贴运行输出，不要只写"通过"两个字
5. **如果有失败/未解决的部分，同样如实写清楚**（呼应整个项目"如实汇报"的风格）

`结论与推导过程.md` 与代码的关系：**代码是唯一的真值来源（跑得出结果才算数），
文档是给人看的整理版**——文档里贴的每一条数值和公式都必须能在对应脚本的
实际输出里找到出处，不能凭记忆/印象转述。若后续代码有修正（比如BUG修正类
的重算），对应的 `结论与推导过程.md` 也必须同步更新，不能留旧结果误导人。

## 五、如何查找/复现某个具体结果

1. 先看 `00_总览与汇报/README_目录导航.md`，找到你要的量属于哪个阶段哪个组件
2. 进组件文件夹，先看有没有 `说明.md`（记录该组件的现状、卡点、下一步建议）
3. 按 `推导→具体计算→数值验证` 的顺序阅读/运行脚本（文件名前的数字表示组件内的执行顺序）
4. 如果要复现，直接在该文件夹内运行，不需要 `cd` 到项目根目录
