## 质疑 1: P0-3 + P1-2 是 RIGHT pair 吗？

**风险等级**: HIGH — 任务选择可能偏离最大影响路径

指挥官选择 P0-3 (Hu PRD 关键公式详细推导) + P1-2 (JCAP Gamma^V 数学推导) 并行执行。从优先级排序来看：

### 被忽略的 -2 任务

| 任务 | 优先级 | 指挥官选择？ | 影响 |
|------|--------|-------------|------|
| **P0-2**: Hu PRD vs 项目代码对应关系 | CRITICAL | NO | 直接定位代码 bug，SNR 错误的工程根源 |
| **P0-3**: Hu PRD 关键公式推导 | MEDIUM | YES | 理论理解，但不直接修复论文 |
| **P1-2**: JCAP Gamma^V 推导 | MEDIUM | YES | 补全 P1-1 缺失的推导链 |
| **P1-3**: JCAP 数值结果分析 | MEDIUM | NO | 确认手征灵敏度阈值 |
| **P2-2**: 构型不变性证明 | LOW | NO | 理论完整性 |
| **P2-3**: OLC 数值结果对比 | LOW | NO | 经验验证 |

### 核心问题：P0-2 为什么被忽略？

P0-2 是 **唯一直接连接理解材料与代码实现** 的任务。SNR 21 阶数量级差距的工程根源就在这个连接点上：

- **代码使用 L = 10m，论文使用 0.17-3 Gm** — 传输函数差了 10^8 倍（已在 SUB-5.1 确认）
- **gamma_olc = -0.188 硬编码，来源不明** — 已在 SUB-5.1 确认
- **Gamma = 0.5 是强度 ORF 的天区平均，但代码用 gamma_olc = -0.188** — 概念混淆
- **(1/16) 因子在代码和论文中的处理方式不一致**

这些是 **P0-2 的核心工作内容**。P0-3 (理论推导) 可以回答 "公式是什么"，但只有 P0-2 能回答 "代码是否正确地实现了公式"。

**我的判断**: P0-2 的影响 > P0-3 和 P1-2 的总和。理解 Hu PRD 的公式推导并不能直接修复代码中的 L 值错误、gamma_olc 硬编码、或 (1/16) 因子处理。

### P1-2 的合理性

P1-2 比 P0-3 更有理由被选择。P1-1 的 QC 明确指出 **Gamma^V 的 5 步推导链完全缺失**。P1-2 直接修复这个缺陷。所以 P1-2 是可以接受的。

### 建议的替代组合

如果指挥官坚持在 -2 任务中做选择，优先级应为:

1. **P0-2 + P1-2** (代码对应 + 手征推导) — 一个修复工程 bug，一个修复理论理解缺口
2. **P0-2 + P1-3** (代码对应 + 数值分析) — 一个修复工程 bug，一个确认物理结论

**P0-3 应该是第四优先级，而非第二。**

## 质疑 2: Agent prompts 能产生实际推导还是又一篇模糊文章？

**风险等级**: CRITICAL — 这是 v27 的教训，可能重蹈覆辙

P3 (交叉对比) 产出了 291 行，QC 判定 **FAIL** — 因为缺少 unified formulas 和 explicit derivations。指挥官接受了这个 critique，但 P0-3 + P1-2 的 Agent prompts 是否足以避免同样的问题？

### P3 失败的模式

P3 的问题不是 Agent 不够努力（291 行），而是:
1. **Prompt 没有强制输出格式** — 没有要求 "必须包含至少 3 个完整的 unified formula"
2. **Prompt 没有验收门槛** — Agent 可以生成模糊的对比描述而不写公式
3. **QC 在产出后才发现问题** — 无法在任务分配时预防

### 如果 P0-3 / P1-2 的 prompt 同样模糊

P0-3 的产出是 `note/P0-3-hu-formula-derivation.md`，包含 "从第一性原理推导 ORF 通用公式"。但 "推导" 可以被任何程度的模糊实现：

- **真正的推导**: 从作用量/测地线方程开始，逐步推导出 Eq.(8)，每一步标注假设
- **弱推导**: 引用 Hu 的公式，然后说 "这与经典 Tomassini 公式的区别在于..." — 这才是 P3 产出的类型

**当前 task-decomposition-v2.md 中的 P0-3 产出格式要求**:
> 1. 原文引用 (至少 5 处公式/段落)
> 2. 详细推导 (至少 3 个中间步骤)
> 3. 物理直觉 (每个关键公式)
> 4. 与项目的关系
> 5. 不确定之处

这些要求仍然没有 **强制结构化输出** — 没有要求 "必须输出 unified R = R^I + iR^V 公式"，没有要求 "必须包含 Hu Eq.(8) 到最终 Gamma_{IJ} 的完整 5+ 步推导"。

### 建议: 强制结构化 prompt

如果启动 P0-3 + P1-2，prompt 必须包含:
- **明确输出模板**: 必须包含带编号的推导步骤（Step 1, Step 2, ...），每个步骤必须标注引用的公式编号
- **量化门槛**: 至少 5 个中间推导步骤（不只是"3 个步骤"这种模糊要求），至少 2 个 unified formulas
- **验收可自动化**: 输出中必须包含特定公式（如 Hu Eq.8、JCAP Eq.2.9-2.10）才能算通过

**否则 P0-3 + P1-2 产出 200-300 行但缺乏严格推导的风险非常高。**

**从第 9 轮重置到第 28 轮，已经 20 轮了。P4（论文修正）尚未启动。**

### "理解" 本身能修好论文吗？

我们目前知道:
1. **gamma 约定不匹配**: Hu sky-averaged intensity ORF (Gamma ~ 0.5) vs Orlando E-variable ORF (gamma = -0.188)
2. **H0 约定不匹配**: (3H_0^2/2pi^2) vs (2H_0^2/pi^2)，差异 0.5625 在 SNR^2 空间
3. **缺少 (1/16) 因子**: 来自应变到投影的转换
4. **f^{-6} 被 |T|^4 替换而非相乘**: 已在 iteration 17 确认
5. **L 值错误**: 代码用 10m，论文用 Gm 级
6. **gamma_olc = -0.188 硬编码**: 来源不明

这些是 **已经明确诊断的 bug**。它们不依赖 P0-3 或 P1-2 来修复 — P0-1 已经足够理解 Hu PRD 框架，P1-1 已经足够理解手征物理。

**理解材料与论文修复之间的关系**:
- 理解材料告诉我们 "什么是对的"
- 但修复论文需要 "在哪里改，改成什么"
- P0-3 + P1-2 提供更多"什么是对的"，但不会自动转化为"在哪里改"

- 然后 P4: 3-5 轮 → 迭代 41-43

**预估: 需要到迭代 40+ 才能开始修论文。从第 28 轮算起还有 12+ 轮。**

这个收敛速度是可以接受的吗？取决于:

2. 这些 -2 任务是否真的必要（见质疑 4）

## 质疑 4: 有没有更短的路径？

**风险等级**: HIGH — 可能省略了不必要的中间步骤

我们已经知道:
- gamma 约定不匹配
- H0 约定不匹配
- 缺少 (1/16) 因子
- L 值错误
- gamma_olc 硬编码

**可以直接修复这些 bug 而不经过 P0-3 + P1-2 吗？**

### 直接修复 vs 先理解

| 已知 bug | 需要的理解 | 能否直接修复？ |
|----------|-----------|---------------|
| gamma 约定 | 需要知道正确的 ORF 值 | P0-1 已提供足够理解 |
| H0 约定 | 需要知道正确的 H0 定义 | 基础物理常识，不需要 P0-3 |
| (1/16) 因子 | 需要知道因子来源 | 已确认来源，可直接决定 |
| L 值错误 | 需要知道 OLC 实际臂长 | 楼论文已提供，不需要 P0-3 |
| gamma_olc 硬编码 | 需要知道正确的 ORF 计算 | P0-2 可以定位，不需要 P0-3 |
| f^{-6} 替换 | 需要知道标准 PTA 公式 | SUB-5.2 已分析过 |

**结论: 所有已知 bug 都可以在不完全完成 -2 任务的情况下修复。**

P0-3 (从第一性原理推导 ORF) 的价值是:
- 加深理论理解
- 发现新的概念性错误

但 **目前我们没有概念性错误 — 只有工程性 bug**。工程性 bug 应该用工程手段修复（代码审查 + 独立验算），而不是理论推导。

### 更短路径建议

1. **P4-1 (直接修复已知 bug)** — 不需要等待 -2 任务完成
   - 修正 gamma 约定: 使用 Hu sky-averaged ORF 值
   - 修正 H0 约定: 使用 (3H_0^2/2pi^2)
   - 决定 (1/16) 因子: 纳入公式或声明为 upper bound
   - 修正 L 值: 使用论文中实际的 Gm 级臂长
   - 修正 gamma_olc: 删除硬编码，使用计算值

2. **P0-2 + P1-2 在 P4 之后或同时进行** — 确保理解材料与修复后的论文一致

3. **P0-3 + P1-3 + P2-2 + P2-3 可以作为 "理论加固" 任务** — 但不是 P4 的前置阻塞条件

**核心论点: "理解优先" 是正确的方向，但"完全理解"不是"开始修复"的必要条件。** 我们在迭代 9 重置时犯了错误 — 从零开始理解所有三篇文献。但在迭代 28，我们已经有了足够的基础知识来修复已知的工程 bug。

## 质疑 5: 整个 RALPH Loop 过程的盲点

**风险等级**: MEDIUM — 方法论层面的系统性问题

### 盲点 1: "理解材料" 产出物的质量波动

从 v20 至今，理解材料的 QC 结果:
- P0-1: QC PASS (confidence 0.97)
- P1-1: QC Iter1 FAIL → QC Iter2 PASS (confidence 0.87) — 但 invented formulas 已被修正
- P2-1: QC Iter1 FAIL → QC Iter2 PASS (confidence 0.90)
- P3: QC FAIL (no unified formulas, no explicit derivations)

**模式**: 每次 QC 都在产出后发现问题，然后 rework。这种 "produce → QC → rework" 循环消耗了大量迭代但不产生新信息。

**更优策略**: 在 prompt 中定义明确的产出模板，在任务分配时就预防 QC 失败，而不是事后 rework。

### 盲点 2: 2-loop 结构的工程性任务适配性

2-loop 的 6 个阶段 (pre-check → backup → execute → QC → confidence → fork) 是为 **代码开发任务** 设计的。但当前任务（文献理解、公式推导）不是代码开发:

- **pre-check**: 检查 Python/依赖/磁盘 — 对理论推导无用
- **backup**: git 备份 — 对 markdown 产出物的价值有限
- **execute**: 写代码/跑脚本 — 但理解任务需要的是 "写推导" 不是 "写代码"
- **QC**: 基于代码测试的验证 — 但理论推导的质量评估是定性的，不是二进制的

**建议**: 对于非代码任务，应使用简化的 2-loop 变体:
- pre-check → 确认理解材料的基础 (已读文献、笔记草稿)
- execute → 产出理解材料
- QC → 基于结构化 rubric 的质量评估（不是代码测试）
- confidence → 综合置信度
- fork → completed / needs_rework

### 盲点 3: 副脑 critique 的迭代效应递减

从 v16 到 v27，sub-brain  critiques 的质量在下降:
- v16: 独立的 43.7 阶差距分析，打破闭环验证 — **高价值**
- v20/v21: convention cascade 分析 — **中等价值**
- v23: N_sat 表的数值检查 — **低价值**（已经在 v16 基础上修修补补）
- v27: 确认 P3 QC FAIL，建议 P0-3 + P1-2 — **中等价值**

**趋势**: sub-brain 越来越倾向于 "修补" 指挥官的决策，而不是提出根本性问题。这是 sub-brain 角色退化为 "yes-but" 机制的早期信号。

### 盲点 4: 1-loop → 2-loop 结构的过度工程化

1-loop 有 6 个阶段 (clarifier → decomposer → gatherer → verifier → decision-maker → fork)，2-loop 也有 6 个阶段。对于一个 "修改论文中的几个数字" 的任务，这相当于用战斗机打蚊子。

**问题不在于 1-loop/2-loop 本身**，而在于它们的阶段被当作 **必须全部执行的 checklist**，即使某些阶段对当前任务没有实际价值。

## 总结: 三个最关键的发现

### 发现 A [HIGH] — P0-2 的优先级被系统性低估

P0-2 (Hu PRD vs 项目代码对应分析) 是唯一直接针对 SNR 21 阶差距的工程根源（L 值错误、gamma_olc 硬编码、(1/16) 因子处理）的任务。P0-3 和 P1-2 是理论理解任务，不直接修复代码/论文中的 bug。

**建议替代决策: P0-2 + P1-2 而不是 P0-3 + P1-2。**

### 发现 B [HIGH] — 所有已知 bug 不需要 P0-3/P1-2 即可修复

我们已识别的 6 个主要 bug 都可以通过以下方式修复:
- 使用 P0-1 提供的 Hu PRD 理解 (已完成)
- 使用 P1-1 提供的手征物理理解 (已完成)
- 直接使用基础物理常识 (H0 值)
- 使用楼论文提供的 OLC 臂长参数

P0-3 + P1-2 产出的是"更深层次的理解"，但 **深度理解不是修复已知 bug 的必要条件**。

### 发现 C [MEDIUM] — Prompt 设计缺陷导致产出质量不稳定

P3 的 291 行产出 QC FAIL，因为没有结构化公式输出。P0-3 + P1-2 的 prompt 如果沿用同样的非结构化要求，很可能产出类似的模糊理解文档。

**建议: 对所有 -2 任务的 Agent prompt，强制包含结构化输出模板和量化验收门槛。**
