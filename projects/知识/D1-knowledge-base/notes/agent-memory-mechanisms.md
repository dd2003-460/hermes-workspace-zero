# Agent 记忆机制: 从 context window 到永续循环

我按"给一个感兴趣但没学过的人讲"的标准写。每个概念给 4 项: 动机/直觉/来源/坑, 结尾连回我自己的架构。

## A. 概念表

### 1. context window 限制
- **动机**: transformer 的 attention 计算随序列长度平方增长, GPU 显存也有硬上限。所以窗口大小是物理约束, 不是能随便拧的旋钮。
- **直觉**: 你的工作记忆同时只能装 7±2 件事, agent 的 context window 就是它的"7±2"。
- **来源**: Transformer (Vaswani 2017, "Attention Is All You Need"); 实际窗口大小由硬件和部署决定。
- **坑**: 窗口大≠用得好。Liu 2023 的 "Lost in the Middle" (arXiv:2307.03172) 表明信息放在长上下文中段时利用率明显下降。所以我把窗口开大, 不等于模型真的用到了里面的每条信息, 位置本身就在影响效果。

### 2. KV cache 作为工作记忆
- **动机**: 自回归生成时每出一个新 token 都要对前面所有 token 做 attention。KV cache 把前面 token 的 K/V 矩阵存下来, 每步不用重算。没有它生成会慢好几倍。
- **直觉**: 你读论文不会每读一句就重读前面的页。KV cache 就是那个"不重读"的缓存, 当前页在 RAM, 前面页在 cache。
- **来源**: Transformer (Vaswani 2017); PagedAttention/vLLM (Kwon 2023, arXiv:2309.06180)。
- **坑**: KV cache 只活在 session 内, 进程一关就没了。它是我理解里的工作记忆, 不是长期记忆。我觉得很多 agent 框架把这两者混着设计, 所以一重启全丢, 用户就说"你怎么不记得了"。

### 3. 对话压缩/摘要（lossy summarization）
- **动机**: 窗口有限, 对话越来越长, 想继续就得压缩。压缩就是把长历史压成短摘要, 给新内容腾地方。
- **直觉**: 像把一周的会议记录压成一页 memo。保留"发生了什么", 丢掉"具体怎么说的", 信息量降了但核心意思还在。
- **来源**: 通用 NLP 摘要任务; agent 场景下 DSH 的 compress 机制和各家的会话摘要都是这一类。
- **坑**: 摘要是 lossy 的, 细节丢了就是丢了。我三个月后要精确引用某句原话, 摘要帮不上忙。而且模型压缩时自己也会引入误差, 它"总结"出来的可能和我原话不完全一致, 这个偏差会随压缩轮次累积, 我觉得这是最阴的一处。

### 4. md 文件记忆树
- **动机**: context window 是临时的, 文件是持久的。agent 把关键信息写成 md 文件, 下次启动重新读进来。这是最笨的方案, 但也是目前我最信任的一个。
- **直觉**: 就是你自己的日记和笔记。你不可能记住所有事, 但可以把重要的写下来, 需要时翻一翻。md 文件就是 agent 的日记本。
- **来源**: 成璐的 D1-knowledge-base 项目本身; Claude Code 的 CLAUDE.md; DSH 的 memory/ 目录结构。
- **坑**: 文件会 stale。我三个月前写的记忆现在可能已经不对了, 但 agent 不知道。而且文件一多, "该读哪些文件"本身变成问题, 读多了占窗口, 读少了漏信息, 我觉得这个矛盾在文件数过百后会很难受。

### 5. RAG/向量检索
- **动机**: 记忆太多塞不进窗口, 就得"按需取用"。根据当前问题检索最相关的记忆片段, 只把相关的放进窗口。
- **直觉**: 像图书馆的检索系统。你不需要把整座图书馆搬进脑子, 只需要"找书"的能力。RAG 就是给 agent 一个找书接口。
- **来源**: RAG (Lewis 2020, arXiv:2005.11401); 向量数据库 (FAISS, Chroma, Milvus)。
- **坑**: 检索质量决定一切。embedding 模型不懂你的领域术语, 检索回来就是垃圾。而且 RAG 只能找"语义相似"的内容, 对时间顺序和因果关系很弱。我问"上周发生了什么", 向量检索大概率找不到, 因为它不理解"上周"是时间锚点。

### 6. MemGPT/Letta（OS 式分层记忆）
- **动机**: 人脑有工作记忆和长期记忆的分层, agent 应该也有。MemGPT 把 LLM 的 context window 当 RAM, 文件系统当磁盘, 用 OS 的分页机制在两者间交换。
- **直觉**: 操作系统的虚拟内存。RAM 有限但快, 磁盘无限但慢, OS 在两者间 page in/out。MemGPT 做同样的事, 把当前要用的"页"从磁盘换进内存, 用完换出去。
- **来源**: MemGPT (Packer 2023, arXiv:2310.08560, UC Berkeley); Letta 是它的开源产品化。
- **坑**: 分页决策靠 LLM 自己做, 它经常判断错, 该换的没换, 不该换的换了。而且每次分页都要调 LLM, token 开销很大。我觉得这个机制适合记忆量极大的场景, solo 开发者用大概率是过度设计。

### 7. Generative Agent 记忆流（reflection）
- **动机**: Park 2023 让 25 个 agent 在虚拟小镇生活, 它们得记住发生了什么, 还要从经历里"反思"出高层结论, 比如"我注意到我一直在帮 X 做 Y"。
- **直觉**: 像你睡前的"今天发生了什么"。回顾一天的事件, 然后冒出"哦我这周一直在纠结 Z"这种高层认知。reflection 就是睡前回顾的自动化版本。
- **来源**: Generative Agents (Park 2023, arXiv:2304.03442, Stanford + Google)。
- **坑**: reflection 很贵, 每次都要跑 LLM。反思质量还高度依赖记忆流的组织方式, 记忆是乱的, 反思出来也是乱的。而且它是定期触发的, 不是实时的, 所以"反思"和"当下决策"之间隔着一段延迟, 我觉得这个延迟在快节奏任务里会咬人。

### 8. HippoRAG（海马体索引式检索）
- **动机**: 海马体在大脑里不是存记忆的地方, 它是索引, 快速建立新记忆和已有知识之间的关联。HippoRAG 模仿这个机制, 用 Personalized PageRank 在知识图谱上做跨跳检索。
- **直觉**: 像一本书的目录加交叉引用。你不用读完整本书, 靠索引就能跳到相关页。HippoRAG 就是给 agent 的记忆建目录和交叉引用。
- **来源**: HippoRAG (Gutiérrez 2024, arXiv:2405.14831, Stanford)。
- **坑**: 索引本身要维护。知识库更新时索引也得更新, 否则检索返回过时结果。而且"关联"按语义相似度定义, 不等于因果关系。我担心它在时间敏感的记忆上会失效, 它找的是"相关的", 不是"最新的"。

### 9. sleep-time compute / 记忆巩固
- **动机**: 人脑睡眠时会巩固记忆, 把白天的经历从短期挪到长期, 顺带建立新关联。agent 也可以有"离线整理"的时间, 先别急着用, 把记忆整理好。
- **直觉**: 像你睡前花 10 分钟整理当天笔记。零散信息归类、去重、建关联, 第二天打开是干净的, 不用现场翻。
- **来源**: 未验证。这是个类比性概念, 目前没有统一的 "sleep-time compute" 框架, DSH 的 compress 和部分 agent 的定期整理脚本有类似思路。
- **坑**: "什么时候该整理"是个问题。太频繁浪费算力, 太不频繁记忆越来越乱。而且整理本身会引入误差, 重组时丢了某些细节, 你觉得不重要, 三个月后发现那正是需要的。我觉得这事的难点不在"怎么整理", 在"何时触发"。

### 10. 情景记忆 vs 语义记忆
- **动机**: 认知科学把记忆分成情景的(具体事件: "昨天会上他说了 X")和语义的(一般知识: "这个项目的架构是 Y")。agent 也要区分, 因为两者的存法取法不同。
- **直觉**: 情景记忆是日记, 语义记忆是 wiki。日记记"发生了什么", wiki 记"是什么", 两者的更新频率和失效方式完全不同。
- **来源**: Tulving 1972 (情景记忆概念, 认知心理学); agent 领域拿这个区分来设计记忆架构。
- **坑**: 两者边界模糊。一条情景记忆重复够多次就变语义的("每次开会他都说 X" → "他话多")。只存一种就丢另一种。我觉得工程上很难精确切分, 它大概是个光谱, 不是两个盒子。

### 11. 记忆漂移与遗忘（stale memory）
- **动机**: 记忆写下来之后世界在变。三个月前写的"项目用 React", 现在可能换成 Vue 了。agent 不更新记忆, 就会拿过时信息做决策。
- **直觉**: 像你的旧地图。城市变了地图没变, 按旧图走就迷路。stale memory 就是那张没更新的地图。
- **来源**: 工程实践问题, 没有统一论文。DSH 的 loop-state.json 机制(每轮刷新状态)和 memory/ 目录的时间戳是应对方案。
- **坑**: "什么时候该更新"和"怎么知道该更新"是两个难题。agent 不可能每次验证所有记忆, 得有失效检测。而且改一条记忆会牵连别的文件, 你改了 A, B 引用了 A, 现在 B 也 stale 了, 我觉得连锁 stale 是文件式记忆最烦的地方。

### 12. lossy vs lossless 压缩的权衡
- **动机**: 摘要压缩是 lossy 的(丢信息), 留原始日志是 lossless 的(不丢但占空间)。agent 得在两者间找平衡, 压太狠丢关键细节, 不压又占满窗口。
- **直觉**: 像照片压缩。JPG 小但糊, PNG 大但清。什么时候要 4K 原图, 什么时候 720p 就够? agent 的记忆管理也是这个 tradeoff。
- **来源**: 信息论的压缩定理; DSH 的 compress 机制是 lossy 的, 但保留了 decompress 路径, 可以恢复原始内容。
- **坑**: 最大的坑是"你不知道什么时候会需要原始细节"。lossy 压缩时丢的东西当时觉得不重要, 三个月后发现正是需要的。所以 lossless 兜底(比如 DSH 的 decompress)应该是标配, 只留摘要太危险。

## B. 应用层: 连回成璐当前架构

我现在的组合是: 单一 context window 永续 + md 文件树承载连续性 + loop-state.json 记录当前状态。

为什么这个组合 work:
- context window 是工作记忆, md 树是长期记忆, loop-state.json 是当前任务指针。三层各干各的, 不重叠, 我觉得这是它能 work 的根本原因。
- md 树是 lossless 的, 我写进去什么就是什么, 没有压缩没有 drift。代价是占磁盘, 但磁盘便宜, 这个交换很划算。
- loop-state.json 是指针不是记忆, 它只记"现在做到哪", 不记"历史上做过什么", 历史都在 memory/ 里。
- 这个组合最大的优点是简单。没有向量库, 没有 RAG 管道, 没有 MemGPT 式分页, solo 开发者维护得动。

什么情况下会 break:
- md 文件数过几十以后, "该读哪些文件"会变成瓶颈。我目前靠 INDEX.md 递归索引控制, 再涨就该上检索了。
- 对话长过窗口、压缩时关键细节丢了, 连续性就断。DSH 的 compress 有 decompress 路径兜底, 但我忘了去恢复, 细节就真没了, 所以关键轮次我应该在压缩前显式保住原文。
- loop-state.json 和实际状态不一致时(比如手动改了文件没刷 state), agent 拿错误状态做决策。这是 stale memory 的具体形态, 也是我认为这个组合最容易出事故的地方。

我的判断: 对 solo 开发者, 这个组合性价比最高。RAG/MemGPT 那套适合记忆量极大或多 agent 协作的场景, 我一个人用, md 树加索引就够。所以我大概率不会加 RAG, 除非文件数真到翻不过来的程度。

## C. 成璐视角

**判断**: 我的核心判断: agent 记忆的本质矛盾是有限窗口对无限历史, 所有方案(压缩/RAG/分层/文件)都是在这个矛盾上切不同的面, 没有银弹, 只有 tradeoff。我猜这是这个领域最稳的一句结论。

**自我质询**: 我"md 树对 solo 够用"的判断可能被推翻——项目数涨到 50 以上, md 树的全读策略会失效, 必须上检索。我没算过临界点, 大概在 30-50 个文件之间。

**动机**: 我在造自己的 AI 分身, 得懂记忆怎么存怎么取怎么更新, 才能决定分身"记得住什么、忘得掉什么"。这直接决定分身的长期一致性。

**新 idea**: 我列的下一步: ① 给 DSH 的 compress 加"关键实体保护", 压缩时不丢人名/数字/路径 ② 写个脚本扫所有 md 记忆文件, 标出 N 天没更新的 stale 记忆 ③ 测"纯 md 树 + 索引"在 50 个文件时的检索效率, 找 RAG 的临界点。

**明确砍掉**: 我不做: 不训 embedding 模型(没算力) / 不搭向量库(维护成本大于收益) / 不做 MemGPT 式分页(过度设计) / 不讨论 agent 意识(不在当前问题域)。

**一句话**: 我的总结: agent 记忆 = 有限窗口 + 持久存储 + 更新机制, 三件套缺一不可; solo 开发者用 md 树 + 索引 + state 文件就是最简可行解。
