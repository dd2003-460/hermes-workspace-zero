# 窗口越来越大，还值得建向量库吗

上一篇（vector-database-cosine-similarity）钻到 HNSW 和 recall 地板就停了，留了个口子：模型变强后 recall 地板能不能放低。这篇接那个口子往下钻——把问题从"检索怎么做"抬到"还要不要做"。我的素材还是自己项目里的真实工件：decomp 的 RAG vs 长上下文拆解题（gold tree 26 节点 + qwen3.8-27b 直跑的两份 run，各 16/18）、正在跑的 LoCoMo 长对话记忆实验（full01，479 题已判）。我要讲的顺序是：先说两个方案各自在赌什么。再说它们各自的致命黑盒。然后落到成本结构和决策规则。收尾回到我自己的系统里该站哪边。每个块讲清是什么、为什么、边界在哪，关键声明带 conf。

## A. 概念块

### 1. RAG 到底在赌什么
- **是什么**: Retrieval-Augmented Generation，检索增强生成。管道我拆过一遍：切块→嵌入→检索 top-k→塞进 prompt 生成。它赌的是：答案相关的信息只占整个知识库的一小撮。把这小撮精准捞出来，模型就能答对。
- **为什么存在**: 模型的上下文装不下整个知识库（500 万 token 的语料装不进任何窗口），所以必须先粗筛。我认为 RAG 的本质是把"模型记不住"的问题转成"索引找得到"的问题——前者无解，后者有工程解法。
- **边界**: 它的命门在检索环节不在生成环节——上游漏掉相关信息，下游再聪明也是零分。我 T17 那份 gold tree 把这条写成 ctx_recall 因子链：切块质量 × 嵌入相关性 × 重排增益，三步任何一环漏了正确率直接乘掉一块。整条链没有闭式解，只能在自己的黄金问题集上实测。conf 0.95

### 2. 长上下文方案在赌什么
- **是什么**: 不建索引，直接把相关文档（甚至全部文档）塞进大窗口模型（128K-1M token），让模型自己在上下文里定位答案。我理解它赌的是：模型读得完也找得到，省掉整个检索层的建设成本。
- **为什么诱人**: 零建设、召回理论上等于 1（文档全在里面了）、实现就是字符串拼接。我对小规模知识库（总量小于有效窗口）的判断：这是最简可行解，没有任何理由不上。
- **边界**: 标称窗口 ≠ 有效窗口。这是这个方案最常被高估的能力——128K 的模型不是 128K 都同样好使，中段定位能力会衰减（所谓 U 型曲线，首尾好中间差），衰减曲线没有解析式且随模型而异。我的 gold tree 里给它单独一个黑盒 B2：有效上下文大概只有标称的 0.3-0.8 倍。没测过 B2 之前，"能装下"和"能用"是两回事。conf 0.9

### 3. 大海捞针与位置偏差
- **是什么**: Needle-in-a-Haystack 测试：往一堆无关文本里埋一个事实，问模型能不能找到。把 needle 放在不同位置（开头/中间/结尾）画一条准确率曲线，就是定位衰减曲线。
- **为什么必须测**: 它是长上下文方案唯一的"体检报告"。我看过不少"我们的模型完美通过 1M needle test"的宣传，很多只测了单一位置或单一长度。真实问答里相关信息落在哪里是随机的。位置偏差意味着你实际能用的上下文可能比标称小一半以上。
- **边界**: needle 测试本身也有坑——单跳事实查找比真实多跳推理简单得多，过了 needle 不代表真实任务行。我猜真实任务的定位难度显著高于 needle，所以 B2 的有效窗口估计要往保守端取。LoCoMo 实验（长对话记忆问答）算是更接近真实的代理指标，但它的对话结构又和知识库文档不同，两边都不能直接外推。conf 0.8

### 4. 镜像黑盒：两个方案各自的死穴
- **是什么**: RAG 的死穴是检索召回（B1：切块/嵌入/重排能不能把相关段落捞回来），长上下文的死穴是定位衰减（B2：塞进去之后找不找得到）。两个黑盒互为镜像——一个管"进得来"，一个管"找得到"。
- **为什么强调双向验证**: 只测 B1 会高估长上下文（以为 128K 全能用）。只测 B2 会高估 RAG（以为切块检索总能召回）。我的做法是选型前两个都在自己数据上测一遍，各花一天左右。这是管道选型特有的结构。硬件选型只要测带宽显存这些客观量，管道选型要测两个互相抵消的黑盒。
- **边界**: "测一遍"不等于"测一次"——B1 依赖你的查询分布（换一批问题召回率可能大变），B2 依赖文档结构（连续叙事和碎片化 FAQ 的定位难度不同）。所以这两个数字都是条件性的，绑定在你的具体语料和问题集上，别人的 benchmark 数字只能当量级参考。conf 0.9

### 5. 成本结构的分裂：建设成本 vs 边际成本
- **是什么**: 两个方案的钱花在不同地方。RAG 有 upfront 成本（切块+嵌入+建库+调参，一次性）。每次问答的边际成本低（只送 top-k 片段）。长上下文零建设，但每次问答的输入 token 是 RAG 的 10-100 倍，边际成本高。
- **为什么不能只看一边**: 只看边际成本会无条件选 RAG，漏掉它的建设账单。只看建设成本会无条件选长上下文，漏掉它的 token 账单。我定的根标量是"每千次正确回答的成本" = 总成本 / 正确率。建设和边际都放进分子，正确率放进分母。不正确的回答再便宜也是零价值。
- **边界**: 决定谁赢的不是技术优劣，是问答量 Q。Q 小（低频问答）时建设摊销占主导，长上下文赢；Q 大（高频）时边际 token 成本占主导，RAG 赢。我在 gold tree 里把 Q 标成翻转项（对应硬件题里的利用率 u）——没估清问答量之前，"RAG 更省"和"长上下文更省"这两句话都可能对。conf 0.95

### 6. 混合架构：为什么两头都要
- **是什么**: RAG 粗筛（把 500 万 token 压到 top 几十段）+ 长上下文精读（模型在可控长度的上下文里定位作答）。我用 RAG 解决"装不下"，用长上下文解决"召回碎片化"。
- **为什么是正解**: 文档规模 doc_scale 这个参数同时走三条路径。逼你用 RAG（总量超窗口）、让 RAG 更难（文档越多召回越难）、让长上下文更贵（塞得越多 token 越贵）。三条路径方向一致但作用的方案不同。我在 gold tree 里给它标了 SHARED。不显式记录这个耦合会推出互相矛盾的结论。只看约束会说"文档大→用 RAG"，只看 B1 会说"召回差→用长上下文"。混合架构是唯一同时满足两条的解。
- **边界**: 混合不是免费的午餐——它保留了 RAG 的全部建设成本，还额外付长上下文的 prefill 延迟（精读阶段的输入 token 比纯 RAG 大）。它的适用区是"文档超窗口但单问题相关文档集中"的中频场景；如果相关文档高度分散（一个问题要跨十几篇拼答案），混合也会退化成"召回不够"的老毛病。conf 0.85

### 7. 可引用性：被低估的硬约束
- **是什么**: 答案给出可核验出处的能力。RAG 天然带 chunk 来源（检索回来的段落有 id）。长上下文需要模型自己标注引用位置——而模型自标引用是出了名的不可靠（编造页码、张冠李戴）。
- **为什么权重高**: 企业知识库场景几乎都要求"答案可追溯"。这不是加分项是准入项。它直接改变决策规则。如果出处准确率不达标，长上下文方案无论多便宜都出局。
- **边界**: RAG 的"天然可引用"也有水分——chunk 粒度太粗时用户拿到的是半页而不是那句话，太细时出处失去上下文。可引用性的真实水平取决于切块粒度和引用格式约定，同样是实测项不是理论保证。conf 0.9

### 8. 幻觉率的不对称
- **是什么**: 两个方案的失效模式不同，幻觉率不可直接比。RAG 在"检索到相关但不够的片段"时会强行基于残缺上下文作答产生幻觉。长上下文信息全所以基础幻觉低，但受定位衰减影响。needle 没找到时模型可能拿邻近的错误信息顶替。
- **为什么必须分开测**: 不存在"哪个方案幻觉少"的先验公式。两个失效模式互相独立，只能在同一组问题上分别统计"含上下文外编造事实"的比例。
- **边界**: 我的判断是 RAG 的幻觉更多来自"沉默失败"（检索漏了但模型不知道漏了，自信地编），长上下文的幻觉更多来自"错位失败"（找到了相邻的错信息）。前者难检测（答案看起来合理），后者相对好抓（对照原文能发现张冠李戴）。这对"怎么验收"有影响：RAG 系统的评测集要专门加"库里没有答案"的负样本题。conf 0.75

### 9. 更新频率与增量索引
- **是什么**: 知识库不是静态的。周更文档意味着 RAG 侧要有增量索引流程（新文档切块+嵌入+入库，旧文档失效删除）。长上下文侧则"每次重新塞"。没有状态，反而没有更新负担。
- **为什么是个隐藏变量**: 大部分选型讨论假设知识库静态。但真实系统的维护成本里更新流程占大头。RAG 的增量索引听起来简单，实际坑在版本一致性（新旧 chunk 混在一起时的去重、软删除、引用失效）。这些工程细节没人写进教程。
- **边界**: 更新频率越高，长上下文的"无状态"优势越明显（反正每次都重新塞，永远最新）；更新频率低（月更年更）时 RAG 的增量成本可以忽略。所以这一项和问答量一样是业务侧参数，不是技术参数。conf 0.8

### 10. 回到我的系统：agent 记忆该站哪边
- **是什么**: 我把自己的 agent 记忆体系套进这套框架。我的记忆 = 有限窗口 + 外置存储（md 文件树，正交分类）+ 检索通道（关键词 grep + 结构化扫描 INDEX.md/loop-state + session_search 翻历史对话）。按这篇的判据看我的"知识库"（工作区 ~500 文件）：总量远小于窗口、更新频率高（每天改）、查询分布偏结构化（目录即分类）。三个条件全指向"长上下文/全文塞入 + 关键词扫描"，不需要向量层。
- **为什么这样站队**: 上一篇的判断是"结构化存储下向量检索边际价值小"。这篇给了它决策规则层面的支撑。不是玄学偏好，是 doc_scale × Q × 更新频率三个业务参数落到了长上下文那一格。真正需要向量检索的场景在我系统里只有一个：conversation-raw-materials 那种几万条非结构化对话的语义查找。
- **边界**: LoCoMo 实验正在检验这个判断的普适版。qwen3.8-27b 在长对话记忆上的"检索+定位"端到端答对率（mem0 抽取记忆 + qdrant 检索，top_10 口径目前 438 题 overall 0.395）vs 全文塞入的差距。smoke 阶段有个反直觉信号：top_10/20/50/200 四个 cutoff 准确率完全相同（60%）。说明检索深度不是瓶颈，瓶颈在 mem0 的记忆抽取质量（temporal 类全错）。如果全量跑完"检索管线"和"全文塞入"差距 <15pp，我"27B 级别 in-context 定位足以替代大部分检索需求"的判断成立。>15pp 则翻转为"检索是硬瓶颈"。实验还在跑（~2.1 题/分，预计还需 ~20h）。结论出来前这块标 conf 0.7。conf 0.7

## B. 成璐视角

**判断**: "要不要 RAG"这个问题的第一变量不是技术（哪个模型强、哪个索引快），是 doc_scale × 问答量 × 更新频率这三个业务参数的组合。文档装得下且问答少 → 长上下文。装不下或问答多 → RAG/混合。在测清 B1/B2 之前，"RAG 比长上下文先进"这句话没有决策意义。两个方案各自的致命黑盒都没量化，比较的是想象不是测量。

**自我质询**: 我第 10 块把自己系统当案例站了长上下文队。这是在用自己的特殊性冒充普遍规律吗？反例就在手边：LoCoMo 的对话记忆是非结构化的、总量远超窗口的。那里检索管线就是必需品，而且 smoke 结果显示它的瓶颈在记忆抽取不在检索深度。修正：我的站队应限定为"对已正交分类、总量小于窗口的工作区知识，全文+关键词优先"。对非结构化大规模语料，检索管线不可替代，优化重点在抽取/切块质量而非检索深度。两条不矛盾，但混在一起说就会误导。

**动机**: 前两篇（agent-memory-mechanisms + vector-database）分别是"记忆的外壳"和"检索的内脏"，这篇补的是"什么时候不用内脏"——把三篇连起来才是完整的 agent 记忆认知：外壳（有限窗口+外置存储）→ 内脏（向量检索怎么做）→ 存废（什么时候不需要内脏）。KB 的 C 区 #10 到这里基本闭合。

**idea (conf 0.6)**: 我想给 LoCoMo 实验加一个对照组。同一批问题用"会话全文截断塞入"（不走 mem0 抽取）跑一遍，直接量"记忆抽取+检索"管线相对全文塞入的净损失。判死条件：如果净损失 <5pp，说明 mem0 那套抽取管线在 27B 级别模型上是负资产（还不如直接塞原文），我 agent 记忆的"结构化抽取"路线要重新评估。如果 >20pp，说明抽取有价值但当前实现烂，优化方向是抽取 prompt 不是换索引。这个对照组的成本约等于再跑一遍 full01（~20h）。等本轮 full01 跑完我再决定值不值得。

**明确砍掉**: 不写具体产品的 benchmark 对比（LlamaIndex/LangChain 之类）——版本敏感且营销污染重，给判据不给排名；不写 1M 上下文模型的营销话术辨析——那是新闻评论不是教材；不展开 multi-vector/late-interaction（ColBERT 系）——我的规模用不上。

**一句话**: 检索 vs 长上下文不是技术路线之争，是业务参数（规模×频率×更新）落在哪个象限的问题；两个方案各有致命黑盒（召回 vs 定位衰减），选型前双向验证缺一不可——和我 GPU 选型那篇同构：先判可行域，再比成本，别信标称值。

## C. 可证伪预测（带判死条件）

1. **预测**: LoCoMo full01 跑完后，mem0 检索管线（记忆抽取+qdrant 检索+定位）相对"会话全文截断塞入"的端到端答对率净损失 > 5pp。
   **判死**: 若净损失 ≤5pp，说明在 27B 级别模型上"结构化记忆抽取"是负资产（抽取丢的信息比检索找回的多），我 agent 记忆里"外置存储要结构化"的原则降级为"仅对跨会话长期记忆必要，会话内直接塞原文"，第 10 块的 conf 0.7 相应下调。前置：需先跑全文塞入对照组（~20h），等 full01 收口后排期。
2. **预测**: 在同一个 answerer 模型下，把检索 cutoff 从 top_10 提到 top_100，LoCoMo overall 准确率提升 < 3pp（smoke 阶段四档 cutoff 零差异支持此预测）。
   **判死**: 若 top_100 相对 top_10 提升 ≥10pp，说明"检索深度不是瓶颈"的 smoke 结论是小样本假象，瓶颈其实在召回数量，agent 记忆设计要把 k 当一级调参项。全量数据自带这个检验（run 配置含多个 cutoff），无需额外实验。
