# 向量检索: 为什么"找对信息"比"聪明回答"更决定成败

我按"给一个感兴趣但没学过的人讲"的标准写这篇。素材是我自己项目里的真实工件——decomp 的 RAG vs 长上下文拆解题（gold tree + qwen3.8-27b 直跑的两份 run）、正在跑的 LoCoMo 长对话记忆实验、以及前几篇 note 里留下的"agent 记忆的检索环节还没往下钻"这个口子。我要讲的顺序是：先文本怎么变成点，再点之间怎么比，然后规模大了怎么办，收尾落到我自己的系统里该不该用。每个块讲清是什么、为什么、边界在哪，关键声明带 conf。

## A. 概念块

### 1. embedding：文本怎么变成一个点
- **是什么**: 用一个专门的模型把一段文本压成一个固定长度的数字列表（向量），比如 1536 个浮点数。意思相近的文本，向量在空间里距离近。这就是"语义变成几何"的那一步。
- **为什么需要它**: 关键词匹配只能抓字面重合，"内存带宽瓶颈"和"decode 慢的原因"字面零重合但说的是同一件事。embedding 把"像不像"从字符串比较变成向量距离比较，这一步不做，后面所有检索都是查字典不是查意思。
- **边界**: 维数是模型的属性（常见 384/768/1536），不是你能随便调的旋钮；换嵌入模型等于换坐标系，旧索引全部作废要重建。我的 T17 拆解里两个 run 都提到 BGE-M3 和 Ada-002 这类模型的 recall 差距可达 5-10%——嵌入选型是检索质量的第一变量。conf 0.95

### 2. 余弦相似度：为什么比欧氏距离更适合比语义
- **是什么**: 两个向量的夹角余弦值，范围 [-1,1]，1=同向完全一致。公式上就是点积除以两个模长的乘积。
- **为什么用它**: 除以模长这一步把"长度"因素除掉了——只比方向不比长短。语义上"这段话很重要"和"这段话非常重要"方向几乎一样但模长不同，余弦把它们判成近邻，欧氏距离会被长度差异干扰。另外高维空间里向量长度方差大，余弦天然归一化了这个问题。
- **边界**: 余弦假设"方向承载语义、模长不承载"。有些场景模长是有信息的（比如强度），这时余弦会丢信息。实际系统里很多库默认存归一化向量，余弦退化成点积，更快。我猜大部分 RAG 场景用余弦就够了，模长信息基本是噪声——这个判断我会在 LoCoMo 实验里间接检验：如果归一化和不归一化的检索命中率没差别，就坐实了。conf 0.9

### 3. top-k 检索：RAG 的"召回"环节到底在做什么
- **是什么**: 拿问题的向量，去库里找最相似的 k 段文本（chunk），把这 k 段塞进 prompt 让模型基于它们回答。k 通常取 3-20。
- **为什么是这个结构**: 模型上下文装不下整个知识库（500 万 token 的例子装不进 128K 窗口），所以必须先"粗筛出可能相关的几段"再让模型精读。top-k 就是这个粗筛。我的 gold tree 里把它写成 ctx_recall 因子链：切块质量 × 嵌入相关性 × 重排增益——三步任何一环漏了，正确率直接乘掉一块。
- **边界**: k 太小漏掉相关信息（recall 损失），k 太大塞进无关段落浪费 token 还可能引入误导（precision 损失）。选 k 的标准动作是画 recall@k 曲线找拐点，不是拍脑袋——我自己做 T17 拆解时就把这条写进了 gold tree 的完成判据。conf 0.9

### 4. 暴力搜索的墙：规模大了为什么必须近似
- **是什么**: 最朴素的检索是把问题向量和库里每条向量都算一遍余弦，取最大的 k 个。N 条记录就是 N 次点积。
- **为什么有墙**: 单次查询 O(N×d)。100 万条 × 1536 维，一次查询约 15 亿次乘法——CPU 上毫秒到秒级，并发一上来就崩。而人的耐心是百毫秒级。所以库过几十万条就必须换近似方法。
- **边界**: 小库（<10 万条）暴力搜索反而最优——没有索引维护成本，实现十行代码，延迟也够。我本地 agent 记忆的场景（几千条 note）根本不需要 ANN，numpy 一把梭就行。"什么时候该上 ANN"的答案是规模逼你的，不是架构洁癖逼你的。conf 0.95

### 5. HNSW：多层跳表式图索引的直觉
- **是什么**: Hierarchical Navigable Small World。建一张多层图：顶层稀疏（长边，跨大步跳转），底层稠密（短边，局部微调）。查询时从顶层入口开始贪心走——每一步跳到当前最近的邻居，直到走不动了降一层继续，底层给出 top-k。
- **为什么有效**: 本质是"小世界网络"性质——少量长边让任意两点的路径长度是对数级的。类比高德地图缩放：先看省界路网定大方向（顶层），再切到街道级微调（底层）。Malkov & Yashunin 2016 年提出（arXiv），现在是工业界默认选择（Qdrant/Milvus/pgvector 都内置）。
- **边界**: ① 建索引慢且吃内存——图要常驻 RAM，我的 run-b 里那个估算很直观：2 亿 token 的 1536 维向量原始就 1.2TB，HNSW 图常驻要 ~1TB RAM 的服务器，这是量级不是精确值。② 参数 M（每节点邻居数）和 efConstruction（建图搜索宽度）控制精度-内存权衡，调参经验大于理论。③ 增量插入会轻微破坏图质量，大规模动态库需要定期重建。conf 0.85

### 6. recall@k vs 延迟：ANN 的两个旋钮
- **是什么**: 近似检索永远在"找到真近邻的概率"（recall@k）和"多快返回"（延迟）之间交换。HNSW 的 efSearch 参数就是这条交换曲线的滑杆——调大 efSearch 搜得更广 recall 升但延迟涨。
- **为什么必须显式权衡**: 精确搜索 recall@k=100% 但慢；ANN 可以 95%+ recall 换 10 倍加速。RAG 场景里 recall 掉 5% 意味着 5% 的问题找不到相关段落，答案质量跟着掉——所以工程上的标准做法是先在黄金问题集上测 recall@k 曲线，定一个业务能接受的 recall 地板（比如 95%@k=10），再在这个地板上取最快配置。
- **边界**: "recall 多少够用"没有普适答案，取决于下游模型对残缺上下文的容忍度。我的判断是：模型越强越能扛漏检（长上下文模型甚至能靠 in-context 定位补救），所以强模型时代 recall 地板可以适当放低——这条我越想越觉得是 LLM 时代和传统 IR 最大的口径差异。LoCoMo 实验正在间接测这件事——同一个 answerer 在不同检索命中率下的答对率曲线就是这张容忍度表。conf 0.8

### 7. 重排 rerank：粗筛之后为什么要精排
- **是什么**: 两阶段检索。第一阶段用双塔模型（query 和 doc 各自独立编码，算余弦）快速粗筛 top-50~100；第二阶段用 cross-encoder（query 和 doc 拼在一起过一遍 Transformer）对这几十条逐条打分重排，取 top-3~5 进 prompt。
- **为什么值得加这一遍**: 双塔的"独立编码"是速度换来的精度损失——两段文本没机会互相 attend。cross-encoder 让 query 和 doc 充分交互，排序质量明显更好，但它慢（每条都要过一次完整前向），所以只对候选集用。我的 gold tree 里 rerank_gain 是独立叶子节点，判据是"rerank 前后 recall@3 差值是否值它的延迟"。
- **边界**: 候选集已经足够准时重排收益趋零还白付延迟；候选集烂到没包含正确答案时重排也救不回来（garbage in garbage out）。所以重排是放大器不是救命稻草，先保证粗筛 recall 再谈精排。conf 0.9

### 8. 切块 chunking：RAG 的头号失效模式藏在这里
- **是什么**: 入库前把长文档切成固定或语义相关的片段（常见 256-1024 token），每块独立 embedding。检索的最小单位是块不是文档。
- **为什么是头号失效模式**: 答案被切在两块里时，单块都不完整，检索回来的上下文是碎的，模型要么答不全要么编。我的 gold tree 原文写着"切块破坏段落完整性是 RAG 头号失效模式"。固定长度切块最简单但最粗暴；语义切块（按段落/标题边界）好一些但有实现复杂度。
- **边界**: 块太大→embedding 被稀释（一段话里三个主题，向量指向模糊）+ 塞进 prompt 的 token 多；块太小→上下文不足。最优块大小依文档结构而异，没有闭式解，只能在你的黄金问题集上实测"相关段落完整率"来定。overlap（相邻块重叠 10-20%）是缓解边界切断的廉价手段。conf 0.9

### 9. 本地方案成本模型：sqlite-vec / chroma / lancedb 各站什么位置
- **是什么**: 三个本地向量方案的量级定位——sqlite-vec：SQLite 扩展，向量列存表里，适合 <100 万条、单机、不想起服务的场景；chroma：嵌入式 Python 库，API 友好，自带 HNSW，适合原型到中等规模（百万条内）；lancedb：列式存储 + 向量索引，适合千万级以上或需要混合过滤（标量+向量联合查询）的场景。
- **为什么给判据不给排名**: 选型变量是 规模×查询频率×是否需要混合过滤×运维意愿。solo agent 记忆场景（几千到几十万条、低频查询、无并发压力）sqlite-vec 或 chroma 都绰绰有余，lancedb 的重型能力用不上。反过来要做产品级知识库（千万文档、p95<15s、混合过滤）才轮到 lancedb 或专用引擎。
- **边界**: 这些库的实时性能数字我不追精确值（benchmark 随版本变），只认量级：本地 SSD 上百万条 1536 维 HNSW 检索是毫秒级，索引内存占用 GB 级。真正会坑人的不是库本身而是配套——嵌入模型要不要 GPU、索引更新策略、备份恢复，这些工程细节才是成本大头。我按规模量级给的口径：几十万条以内 chroma 零运维最省心，过百万再考虑 lancedb 的列式过滤能力（KB 库本身没部署过向量层，这是推断不是实测）。conf 0.8

### 10. agent 记忆里的位置：检索是瓶颈还是噪声源
- **是什么**: 回到我自己的系统。agent 持续循环的记忆 = 有限窗口 + 外置存储（md 文件树）+ 检索（find-goal SOP 扫 tasks/loop-state、session_search 翻历史对话）。向量检索在这套体系里是可选增强，不是必需品——我现在的主检索通道其实是关键词+结构化扫描（git log、grep、INDEX.md），因为工作区的知识是高度结构化的（目录即分类、台账即索引）。
- **为什么这个判断重要**: 业界默认"agent 记忆=向量数据库"，但我撞过的数据墙说明：当存储侧已经是正交分类的文件树时，向量检索的边际价值很小，反而引入"相似但不相关"的噪声召回。向量检索真正的用武之地是非结构化语料（对话历史、网页快照）的大规模语义查找——session_search 那种"翻三个月前的某次讨论"的场景。
- **边界**: 我的 LoCoMo 实验（10 对话 300 题长对话记忆问答）正在给这个判断补实证——如果纯检索+定位的端到端答对率显著低于全文塞入，那"检索是瓶颈"成立；如果差距小，说明 27B 级别的模型 in-context 定位能力足以替代大部分检索需求。实验还在跑（~110s/题，预计 26h 全量），结论出来前这个判断标 conf 0.7。conf 0.7

## B. 成璐视角

**判断**: 检索这层的真相是"工程问题伪装成 AI 问题"——HNSW 的数学二十年前就有了（小世界网络），真正难的是 chunk 怎么切、recall 地板定多少、重排值不值，全是业务口径决策不是算法决策。LLM 时代唯一的新变量是下游模型变强后 recall 地板可以放低，这条正在被 LoCoMo 实验检验。

**自我质询**: 我第 10 块说"结构化存储下向量检索边际价值小"——这是在用自己系统的特殊性冒充普遍规律吗？反例：conversation-raw-materials 那种几万条非结构化对话确实只有向量检索能用。修正：判断应限定为"对已正交分类的工作区知识，关键词+结构扫描优先；对非结构化语料的语义查找，向量检索不可替代"。两条不矛盾。

**动机**: 这篇是 agent-memory-mechanisms（第二篇）留的口子——那篇讲到"外置存储+检索"就停了，检索内部没钻。现在钻完，KB 的 C 区 #10（agent 记忆基础设施）只剩 RLHF/训练机制侧没覆盖（那属于第一篇 llm-training 的地盘）。

**idea (conf 0.6)**: 给 workspace 的 session_search 加一层轻量向量索引（sqlite-vec 嵌进去，只索引对话摘要不索引全文），专门解决"三个月前哪次讨论提过 X"这类查询。判死条件：如果加了之后我在 keepalive 里"回忆失败→重新 grep"的频率没有下降，说明关键词扫描已经够用，这层是过度设计。

**明确砍掉**: 不写 IVF/PQ 的细节（FAISS 系）——我的规模用不上，写了也是百科腔；不写具体 benchmark 数字对比——版本敏感，给量级给判据。

**一句话**: 向量检索 = 把"找对信息"变成几何最近邻问题；型号之争（哪个库）远小于口径之争（切多大、recall 地板多少、重排值不值）——和 GPU 选型那篇的结论同构：组合比单品重要。

## C. 可证伪预测（带判死条件）

1. **预测**: 在我的 workspace（~500 文件，正交分类）上，对真实"回忆类"查询（keepalive 里实际发生过的），向量检索 top-3 命中相关文件的比例 ≤ 关键词 grep 命中比例 + 10%。
   **判死**: 若累计 ≥5 次同类事件顺手记录后，向量检索命中率显著超过 grep（>20% 相对提升），说明我对"结构化存储下向量检索价值小"的判断错了，session_search 加向量层的 idea 从 conf 0.6 升到 0.8 并立项。不专门跑 20 题的对照实验——事件驱动记录足够，避免预测变成永远不执行的空话。
2. **预测**: LoCoMo 全量跑完后，qwen3.8-27b 的"检索+定位"端到端答对率与"全文塞入"（截断到窗口上限）的差距 < 15 个百分点。
   **判死**: 若差距 > 15pp，说明 27B 级模型的 in-context 定位不足以替代检索，第 10 块的 conf 0.7 判断翻转为"检索是硬瓶颈"，agent 记忆设计要把 recall 地板当一级指标。
