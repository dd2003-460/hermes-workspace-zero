## 3. 正交维度拆解（必须拆到原子）

> **核心规则：只要某个子节点还可以继续拆解，就必须继续拆，直到每个叶子节点都是原子操作（不可再分、可直接执行）。**
> 拆到原子 = 每个叶子节点满足：①有明确的执行动作 ②有明确的完成判据 ③不需要再拆子步骤。

> 维度必须满足两个条件：
> - **正交**：任意两个维度能同时取不同值（能 = 正交；不能 = 有重叠，重拆）
> - **完备**：所有候选都能归入某个维度组合（有落空的 = 不完备，补维度）

### 3.2 分解树（拆到原子）

```
任务根节点
├── 子过程 A（可继续拆？→ 是 → 继续拆）
│   ├── A1（原子：执行动作=___，完成判据=___）
│   └── A2（原子：执行动作=___，完成判据=___）
├── 子过程 B（可继续拆？→ 是 → 继续拆）
│   ├── B1（原子）
│   └── B2（可继续拆？→ 是 → 继续拆）
│       ├── B2a（原子）
│       └── B2b（原子）
└── 子过程 C（已原子，不再拆）
```

**原子性自检**：逐个叶子节点检查——还能拆吗？能 → 继续拆。不能 → 标注"原子"并给执行动作+完成判据。

## 4. 拆解外包与交叉检验（必须走 arena，禁止 Lead 自己拆完就往下）

> **核心规则：拆解必须外包给 arena 执行，多个 agent 在同一个仓库里各自拆解，然后互相检验正确性。Lead 只负责派发任务和验收，不自己拆。**

### 4.1 派发拆解任务

按 `sop/arena-loop-pipeline.md` 派发拆解任务给 arena：
- 任务书包含：调研问题 + 本地背景（第 1 节）+ 候选全集（第 2 节）+ 拆解要求（正交+完备+拆到原子）
- 至少 2 个独立 agent 各自完成拆解
- 所有 agent 在**同一个仓库**工作，产出物落盘到仓库指定目录

### 4.2 交叉检验

| 检验项 | 方法 | 通过标准 |
|--------|------|----------|
| 正交性 | 逐对维度检查能否同时取不同值 | 全部正交 |
| 完备性 | 候选全集逐个过维度 | 无落空 |
| 原子性 | 每个叶子节点检查是否可再拆 | 全部原子 |
| 一致性 | 多个 agent 的拆解结果对比 | 差异项有解释 |

**不一致处理**：
- 2 个 agent 拆解结果一致 → 通过
- 有差异 → 记录差异点，派第 3 个 agent 仲裁，或 Lead 介入判断
- 仲裁后仍不一致 → 回退到第 2 节补充候选，重新拆解

### 4.3 检验通过标准

- [ ] ≥2 个 agent 独立完成拆解？
- [ ] 正交性检验通过？
- [ ] 完备性检验通过？
- [ ] 原子性检验通过？
- [ ] 差异项全部有解释/仲裁结果？

**全过 = 拆解定稿，可进入下一阶段。任一未过 = 回退重新拆解。**

## 5. 回退与修正机制

> **核心规则：执行过程中，任何阶段发现矛盾或新信息，必须回过头修改分解树——增删节点、调整维度、更新候选全集。分解不是一次性的，是活的。**

| 触发条件 | 回退到 | 修改动作 | 记录 |
|----------|--------|----------|------|
| 发现新候选（第 2 节漏了） | 第 2 节 | 补充候选 + 重新过维度 | 改动原因 + 时间 |
| 发现维度不正交/不完备 | 第 3 节 | 重拆维度 + 重建树 | 改动原因 + 时间 |
| 执行中假设被推翻 | 对应子过程 | 删/改/增节点 | 改动原因 + 时间 |

**回退规则**：
- 小改（增删 1-2 个叶子节点）→ 直接改，记录即可
- 中改（某个子过程整体推翻')→ 回退到该子过程重新拆
- 大改（某个节点的前提被矛盾推翻）→ **只重建该节点以下的子树**，以上结构不动。定位矛盾节点，剪枝，从该节点重新拆解
